# Knowledge-Nest

[English](README.en.md)

**手元の資料を、AI が出典を示して使える知識にする。コマンドをいくつか打つだけで、プログラムは書きません。**

資料のフォルダ（Markdown、PDF、Word、Excel、Web のページ …）を渡すと、Knowledge-Nest が AI の使える形に整えます。やりたいことに合わせて、次の3つから始められます。資料も索引も手元のフォルダに置いたまま、答えにもページにも、いつも出典が付きます。

## やりたいことから選ぶ

| やりたいこと | 始め方 | AI モデル | 見る・使う場所 |
|---|---|---|---|
| [**Claude に、手元の資料を調べさせたい**](#claude-に手元の資料を調べさせる) | `nest init mcp` | 要らない | Claude Desktop、Claude Code などのエージェント |
| [**資料から、読めるナレッジベースを作りたい**](#資料からナレッジベースを作るwiki) | `nest init wiki` | 要る（Ollama か API） | ブラウザ。エージェントからも引ける |
| [**溜まった資料とメモを、仕事ごとに整理したい**](#資料とメモを仕事ごとに整理するpara) | `nest init para` | 要る（Ollama か API） | ブラウザ。エージェントからも引ける |

迷ったら、モデルの準備が要らない1つ目から始めてください。同じ資料から、あとでほかの形も作れます。インストールは [こちら](#インストール)、順を追った説明は [入門](docs/getting-started.md) にあります。

### Claude に、手元の資料を調べさせる

社内の手順書や設計書を、Claude などのエージェントが自分で探して読み、出典付きで答えます。Knowledge-Nest の側に AI モデルは要りません。日本語の検索が手元ですぐに動き、資料は外に出ません。資料は [ポンプの保全手順](examples/manuals/maintenance.md) です。

```text
あなた   ポンプの点検って、いつやるんだっけ？
Claude   毎月最初の営業日です。点検の前にポンプを止め、電源が切れていることを確かめます。
         出典: maintenance.md 3行目、5行目
```

```sh
nest init mcp ./kb --source ./manuals          # 資料のフォルダを指定して作る
cd kb
nest build                                     # 資料を読んで索引を作る
nest search "ポンプの点検はいつ実施しますか"   # 試しに引いてみる
nest serve --print-config                      # エージェントの設定に貼る内容を出す
```

最後のコマンドが出す設定を、Claude Desktop や Claude Code の MCP の設定に貼れば完了です。資料を直したら `nest build` をもう一度実行します。変わった文書だけが処理され、動いているエージェントは次の質問から新しい内容を引きます。 [MCP 入門](docs/start-mcp.md)

**ほかの方法と比べて**

- **エージェントにフォルダを直接読ませるより。** PDF・Word・Excel・スキャンした資料も、日本語の語で引けます。返すのは答えのある箇所だけで、資料名と行が付き、決めた文字数に収まります。資料が何千件あっても、エージェントの文脈を埋めません。
- **ベクトル検索だけの検索サーバーより。** 型番、条番号、専門用語のように「その語で探したい」検索に強い日本語のキーワード検索が、埋め込みモデルなしで動きます。言い換えに強いベクトル検索を足して、ハイブリッドにもできます。
- **測って、最適化まで。** 質問と正解の引用を登録すると（質問の候補は AI にも作らせられます）、検索が根拠を拾えた割合を測れます。チャンクの大きさや検索の件数などの候補をまとめて試し、良い順に並べ、確かめた設定だけを提供に切り替えます。自分で組んだ検索では、この評価と調整の仕組みを別に用意することになります。 [検索を、測って最適化する](#検索を測って最適化するmcprag)

**自分のアプリやチャットボットに、出典付きの答えを返させたいとき**は、`nest init rag` で、同じ検索に回答用の AI モデルを足します。`nest ask "質問"` や HTTP で、出典付きの答えが返ります。LangChain などで組むのと違い、コードは書きません。HTTP は OpenAI の SDK がそのまま使える形なので、既存のアプリは接続先を変えるだけで呼べます。資料に根拠が見つからない質問には、答えを作らずに断ります。 [RAG 入門](docs/start-rag.md)

### 資料から、ナレッジベースを作る（Wiki）

散らばった手順書や議事録を AI が読み、テーマごとのページにまとめます。資料を足すたびに、関係するページが書き足されます。ページはブラウザで読め、エージェントも同じページを引けます。

```text
ポンプの保全
  ポンプの点検は毎月最初の営業日に行う。点検の前にポンプを停止し、電源が切れていることを確かめる。
  メカニカルシールは2年ごとに交換する。
  出典: maintenance.md
```

```sh
nest config set llm --provider ollama --model qwen3:4b   # ページを書く AI を決める（最初の1回）
nest init wiki ./wiki --purpose "設備保全の手順と部品情報をまとめる"
cd wiki
nest ingest ../manuals   # 資料を取り込む。Web のページは URL で渡せる
nest serve               # http://127.0.0.1:4319 をブラウザで開く
```

**ほかの方法と比べて**

- **AI に要約させるだけの道具より。** 各ページは、書くのに使った資料を出典として持ちます。本文の数字・日付・「」の引用が出典にあるかを、プログラムが照らします。資料が新しい版になれば、古い版から書いたページを `nest lint` が知らせます。
- **知識が、手元のファイルのまま。** ページは `wiki/` の HTML ファイル、原本は `raw/` のファイルです。サーバーがなくても開け、ほかの道具にも持っていけます。AI の変更は作業ごとに記録され、`nest undo` で取り消せます。原本は書き換えません。
- **人とエージェントが、同じページを使う。** 人はブラウザで読み、「点検前の確認事項を箇条書きに」のようにページへ指示します。エージェントは同じページを MCP で引きます。
- **ログインの要るページも取り込める。** nest 専用のブラウザでログインしておけば、スクリプトで描かれる社内のページや X の投稿も、原本として取り込めます。

Andrej Karpathy の LLM-Wiki の考え方に沿っています（[LLM-Wiki とは](#llm-wiki-とは)）。 [Wiki 入門](docs/start-wiki.md)

### 資料とメモを、仕事ごとに整理する（PARA）

調べものの資料やメモが溜まり、どこに何があるか分からなくなったときに使います。AI が資料ごとにノートを書き、Tiago Forte の PARA の4つの置き場所に振り分けます。テーマではなく「いまの仕事に使うか」で分けるのが PARA の考え方です（[解説](https://fortelabs.com/the-p-a-r-a-method-a-universal-system-for-organizing-digital-information-75a9da8bfb37/)）。

| 置き場所 | 入るもの | 例 |
|---|---|---|
| Projects | 期限のある取り組み | 来月のポンプ更新工事 |
| Areas | 続けて責任を持つ領域 | 設備の定期保全 |
| Resources | いつか役立つ参考資料 | 部品メーカーのカタログ |
| Archives | 終わったもの | 昨年度の点検記録 |

取り組みと領域は、人が `rules.md` に書きます。AI は、資料を使う場所をその中から選び、要点と使い道をノートに書きます。始め方は Wiki と同じで、`init wiki` を `init para` に読み替えます。 [PARA 入門](docs/start-para.md)

**ほかの方法と比べて**

- **ノートアプリで、手で振り分けるより。** 資料を入れるだけで、AI が「この取り組みにどう使うか」をノートに書き、使う場所に置きます。資料の写しもノートの隣に置かれます。
- **フォルダが勝手に増えない。** AI が置けるのは、あなたが `rules.md` に書いた取り組みと領域だけです。一覧にない場所に置こうとしたノートは保存せず、知らせます。
- **終わった取り組みを、一度で片付けられる。** `nest archive` が、ノート、資料の写し、ほかのノートからのリンク、`rules.md` の行をまとめて Archives へ移します。`nest undo` で戻せます。期限を過ぎた取り組みは `nest lint` が知らせます。

## どれにも共通すること

- **プログラムは要らない。** 使うのは `nest` のコマンドとブラウザの画面です。何をどう処理するかは `KnowledgeNestfile.yaml` に書き出され、変えたいときだけ触ります。
- **手元で完結する。** 資料も索引もプロジェクトのフォルダに保存されます。外へ送るのは、あなたが AI モデルを設定したときに、その処理に要るテキストだけです。
- **いつも出典が付く。** 検索結果も、答えも、ページも、元の資料を指します。
- **エージェントからも引ける。** どの形も MCP で提供するので、Claude などが同じ知識を使えます。

やりたいことごとに、よくあるほかの方法と比べた表と、ほかを選ぶほうがよい場合は [Knowledge-Nest が向いている構成](docs/comparison.md) にあります。

## 4つの形の違い

ここからは、形の違いを詳しく知りたい人向けです。上の「やりたいこと」で選べたなら、読み飛ばしてかまいません。

### 早見表

| | MCP | RAG | Wiki | PARA |
|---|---|---|---|---|
| できるもの | エージェント用の検索 | 出典付きで答える API | 出典付きの知識のページ | PARA 形式のノート |
| 使う人 | エージェント | 自分のアプリ | 人とエージェント | 人とエージェント |
| 資料を読むとき | 質問のたび | 質問のたび | 取り込むとき | 取り込むとき |
| エージェントが受け取るもの | 資料の該当箇所 | 資料の該当箇所（`/mcp`） | AI がまとめたページ | AI が整理したノート |
| AI モデル | 要らない | 回答に要る | 執筆に要る | 執筆に要る |
| 資料の更新 | `build` で、変わった文書だけ | `build` で、変わった文書だけ | `ingress` で、ページを書き足す | `ingress` で、ノートを書き足す |
| 提供のしかた | MCP | HTTP（回答・検索）と MCP | Web（ページと操作画面）と MCP | Web（ノートと操作画面）と MCP |

MCP と RAG は、質問のたびに資料を検索する形です。資料が多くても、更新が多くても、すぐ反映できます。Wiki と PARA は、先に AI が資料を読んで整理しておく形です。まとめ直された知識なので、人がそのまま読めます。

### MCP と RAG は何が違うのか

違うのは、**見つけた根拠から答えを書くのが誰か**です。

```text
MCP   質問 ─→ [エージェント] ─検索を依頼─→ Knowledge-Nest ─→ 根拠（資料の該当箇所）
                  ↑                                      │
                  └──────── 根拠を読んで、エージェントのモデルが答える ──┘

RAG   質問 ─→ Knowledge-Nest ─→ 検索 ─→ 根拠 ─→ Knowledge-Nest が呼ぶモデルが答えを書く ─→ 出典付きの回答
```

- **MCP** は、司書が棚から資料を出して、調べる人に渡す形です。エージェントが必要に応じて言い換え、何度も引きます。結果には資料名・行・見出しが付き、`knowledge.read` で原文まで読み戻せます。
- **RAG** は、司書が資料を読んで、答えを書いて渡す形です。質問を1回送ると、答えが1回返ります。応答は OpenAI の Responses API の形で、`/v1/responses`、`/v1/search`、`/mcp` を1つのポートで提供します。外に公開するときは、トークン認証と接続制限を設定できます。
- RAG の `serve` は MCP（`/mcp`）も出すので、MCP から RAG に移っても、エージェントからの検索はそのまま使えます。

日本語は Lindera と IPADIC で分かち書きします。「する」「こと」のような軽い語だけが合う文書は返しません。専門用語はユーザー辞書で足せます。ベクトルを足したハイブリッド検索、PDF・Office・HTML・OCR にも対応します。 [MCP と RAG](docs/mcp.md)

### LLM-Wiki とは

LLM-Wiki は、Andrej Karpathy が提案した、LLM で知識ベースを作る考え方です（[原文の gist](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)）。

RAG は、質問のたびに元の資料から断片を探し、その場で答えを組み立てます。読んだ結果は残りません。LLM-Wiki では、LLM が資料を読んだ結果を、相互にリンクした Wiki のページとして書き溜めます。新しい資料が来ると、関係するページを書き足します。知識は「一度まとめて、育てていく」ものになります。人がするのは、資料を選んで入れることと、問いを立てることです。

| LLM-Wiki の操作 | 内容 | Knowledge-Nest |
|---|---|---|
| 取り込み（ingest） | 資料を読み、関係するページを書いたり直したりする | `nest ingest` |
| 問い合わせ（query） | 元の資料ではなく、Wiki のページに対して質問する | `nest query` |
| 点検（lint） | 孤立したページ、リンク切れ、矛盾、古い記述を見つける | `nest lint`（出典・原本の版・数字と引用・リンク）、`--content`（ページ同士の矛盾） |

LLM が書いた文は、もっともらしい誤りを含むことがあります。Knowledge-Nest は、この弱点を出典との照合で埋めています。PARA も、出典との照合、原本を書き換えない保管、作業の取り消し、Web と MCP での提供を Wiki と共通に持ちます。 [Wiki・PARA の使い方](docs/wiki.md)

## 検索を、測って最適化する（MCP・RAG）

「チャンクを小さくすれば当たるようになる？」を、勘ではなく数字で決められます。質問と正解の引用の組で、検索が根拠を拾えた割合（回収率）を測り、変えたい所を書くだけで、候補の設定を作って順に測ります。途中までが同じ候補は作ったものを使い回すので、何通り試しても速く済みます。

```sh
nest eval-data import cases.json   # 質問と、答えになる引用の組を入れる
nest eval                          # いまの設定で回収率を測る
nest optimize tune.yaml            # 変えたい所を書いた指示から、候補を作って順に測る
nest results tune                  # 候補を、回収率の高い順に並べる
nest release tune/010              # 選んだ索引に、提供用の名前を付ける
```

`results` の表示の例です（一部の列を省いています）。

```text
Trial  Recall  To base  What
010    1.000   +0.333   chunking=length(size=200),search=top10
000    0.667   -        base
```

作り直しても、評価しても、最適化しても、提供する索引は変わりません。確かめてから `release` したときだけ切り替わります（毎回切り替えたいなら `nest build --release`）。

外れた質問を見るための道具もあります。評価の結果は、根拠が検索、統合、文脈の予算のどこで落ちたかと、質問の種類ごとの成績まで分けて出します。評価用の質問の候補は `nest eval-data generate` で AI に作らせ、確かめてから使えます。

`optimize` と `release` は開発中の新しい仕組みで、いまはテキストと Markdown、キーワード検索に対応しています。`serve` はまだこの仕組みの索引を提供しません。ベクトル検索やリランクを含む設定は、`nest eval` と `nest report compare` で1つずつ比べられます。手順と対応範囲は [検索を数字で良くする](docs/guide.md) と [検索評価とユーザー辞書](docs/evaluation.md) にあります。

## 構成を組み替える、足りなければ足す（MCP・RAG）

MCP と RAG の処理は、読み込み、チャンク分け、索引、検索、回答の段ごとに、モジュールを並べた設定（`KnowledgeNestfile.yaml`）でできています。プログラムを書かずに、並びと引数を変えるだけで構成を組み替えられます。

- **組み替える。** キーワード検索にベクトル検索とリランカーを足す、チャンクの切り方を見出しに沿わせる、といった変更は設定を数行書き換えるだけです。`nest modules list` で使えるモジュールを、`nest validate` で設定の誤りを、実行前に確かめられます。 [モジュール](docs/modules.md)
- **読めない形式は、手持ちの変換ツールで。** `loader.command` に変換コマンドを書けば、標準で読めない形式（図面、独自形式など）も、そのコマンドの出力を本文として取り込めます。
- **モデルは差し替えられる。** 埋め込みと回答のモデルは、手元の Ollama か OpenAI などの API から選べます。リランカーは、`/v1/rerank` か `/rerank` を出すサーバー（llama.cpp、vLLM、Infinity、Text Embeddings Inference）につなげます。
- **新しいモジュールを足したいときは、どうぞ。** モジュールは `src/registry.rs` の登録表に、役割、入出力、引数を定義して足します。本体は MIT ライセンスで、手順は [開発と変更の確認](CONTRIBUTING.md) にあります。プルリクエストを歓迎します。

## インストール

npm への公開は準備中です。現在はソースからビルドします。Rust 1.95 以降と、Node.js 22.20 以降の 22 系または 24.12 以降の 24 系が必要です。

```sh
git clone https://github.com/hachiware-labs/knowledge-nest
cd knowledge-nest
npm ci
npm run build
npm link
nest --help
```

## 開発

```sh
npm ci
npm run build
npm test
npm --prefix tools/rag ci
npm --prefix tools/rag test
npm run test:package
npm run bench -- 1000 300
```

`test:package` は `dist/packages/` に tarball を作り、空のプロジェクトへオフラインでインストールして検索と本文取得を試します。ベンチマークは合成データで索引作成、検索レイテンシ、メモリ、Recall@10、nDCG@10 などを計測します。変更前の確認と CI の起動方法は [開発と変更の確認](CONTRIBUTING.md) にあります。

## 現在の状態

- バージョン 0.5.0 の開発版です。コマンドや設定の形は変わる可能性があります。
- `knowledge-nest` は仮のパッケージ名です。npm への公開は準備中です。本体のライセンスは MIT です。
- 動作を確認している環境は、Windows x64、Linux x64（glibc）、macOS arm64 と x64 です。
- 版の保管と、それを使うコマンド（`list`、`results`、`optimize`、`release`）は `data-management` ブランチで実装中です。コマンドは、読む設定ファイルの形で仕組みを選びます。

|---|---|---|

| 検索 | キーワード | キーワード、ベクトル、ハイブリッド、リランク、ユーザー辞書 |
| 版の記録と再利用、`list`、`results`、`optimize`、`release` | ○ | — |
| `serve`（MCP・HTTP）、`ask` | まだ | ○ |

Wiki と PARA は、どちらの形とも別の仕組みで、いつでも使えます。2つの形の詳しい違いは [検索を数字で良くする](docs/guide.md#10-従来の流れで使うもの) の10章 にあります。
