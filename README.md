# Knowledge-Nest

[English](README.en.md)

**手元の資料を、AI が出典を示して使える知識にする。コマンドをいくつか打つだけで、プログラムは書きません。**

資料のフォルダ（Markdown、PDF、Word、Excel、Web のページ …）を渡すと、Knowledge-Nest が AI の使える形に整えます。資料も索引も手元のフォルダに置いたまま、答えにもページにも、いつも出典が付きます。

## 1つの道具で、4通りの文書データベース

ふつうは、ベクトルデータベース、RAG のフレームワーク、Wiki の道具、ノートアプリをそれぞれ選んで組み合わせます。Knowledge-Nest は、同じ資料フォルダから、その4通りを1つで作れます。

```text
                                  ┌─ MCP    エージェントが引く検索
資料フォルダ ──→ Knowledge-Nest ──┼─ RAG    アプリに返す、出典付きの答え
(Markdown、PDF、Word、Excel …)    ├─ Wiki   みんなで使う知識のページ
                                  └─ PARA   自分の仕事を整理するノート
```

| やりたいこと | 作るもの | AI モデル | 使い方 |
|---|---|---|---|
| Claude などのエージェントに、手元の資料を調べさせたい | **MCP**：エージェントが引く検索 | 要らない | [MCP 入門](docs/start-mcp.md) |
| チャットアプリや社内ツールで、資料に基づく答えを返したい | **RAG**：出典付きで答える API | 回答に要る | [RAG 入門](docs/start-rag.md) |
| 資料を、チームで使う知識のページにまとめたい | **Wiki**：みんなで使う知識のページ | 執筆に要る | [Wiki 入門](docs/start-wiki.md) |
| 自分の仕事の資料とメモを、取り組みごとに整理したい | **PARA**：自分の仕事を整理するノート | 執筆に要る | [PARA 入門](docs/start-para.md) |

- **覚えることは1通り。** インストールは1つ、始め方は `nest init <形>` の1つです。資料の読み込み、出典の付け方、設定ファイル（`KnowledgeNestfile.yaml`）、`nest serve` での提供は、どの形でも共通です。
- **同じ資料から、目的に合わせて増やせる。** まず検索を作り、あとから答えの API や Wiki を、同じ資料フォルダから足せます。作り直しも乗り換えも要りません。
- **どの形も、エージェントから引ける。** 4つとも MCP で提供するので、Claude などは、資料そのものも、AI がまとめた知識も、同じつなぎ方で使えます。
- **手元で完結する。** 資料も索引もプロジェクトのフォルダに保存されます。外へ送るのは、あなたが AI モデルを設定したときに、その処理に要るテキストだけです。

迷ったら、モデルの準備が要らない MCP から始めてください。インストールは [こちら](#インストール)、順を追った説明は [入門](docs/getting-started.md)、4つの形の詳しい違いは [4つの形の違い](docs/forms.md) にあります。

## どのデータベースも少ない手間で

まとめて作れるだけではありません。どの形も、ほかのライブラリで同じものを作るときの面倒な作業を、Knowledge-Nest が引き受けます。ほかを選ぶほうがよい場合も含めた比較は [Knowledge-Nest が向いている構成](docs/comparison.md) にあります。

### MCP：エージェントが引く検索

MCP の良さは、**検索が、資料と使い方に合わせて育つ**ことです。入れて終わりではなく、測りながら、当たるようにしていけます。

| 育ち方 | 何が起きるか | 使う仕組み |
|---|---|---|
| 資料を足す・直す | 変わった文書だけを処理する。動いているエージェントは、止めずに次の質問から新しい内容を引く | `nest build` |
| 当たり具合を測る | 質問と正解の引用を溜め、検索が根拠を拾えた割合を測る。質問の候補は AI に作らせ、人が確かめて加える | `nest eval-data generate`・`review`、`nest eval` |
| 言葉を覚えさせる | 外れた質問から、分かれてしまう専門用語の候補を出し、ユーザー辞書に足す | `nest dictionary suggest`・`add` |
| 構成を良くする | チャンクの大きさ、ハイブリッド検索、リランカーなどを試し、前の結果と比べる。候補をまとめて試して最適化もできる | `nest report compare`、`nest optimize` |
| 安全に切り替える | 試しても、提供中の検索は変わらない。確かめた結果だけを提供に切り替える | `nest use`、`nest release` |

**ほかの MCP サーバーで作ると**（ファイルシステムやベクトルデータベースの MCP サーバー）、これを自分でやります。

1. PDF や Office を、エージェントが読めるテキストに変える道具を用意する
2. 資料を分割し、埋め込みモデルを選んで、ベクトルデータベースに入れる
3. 資料が変わるたびに、入れ直す
4. 型番や専門用語で当たらないときに、どこを変えればよいか手探りする

**Knowledge-Nest なら**

```sh
nest init mcp ./kb --source ./manuals
cd kb
nest build
nest serve --print-config   # 出てきた設定を、エージェントに貼るだけ
```

PDF・Office・スキャンした資料も読み、埋め込みモデルなしで日本語の語で引けます。資料を直したら `nest build` で、変わった文書だけが入れ替わります。当たり具合は回収率で測り、候補の設定をまとめて試して最適化できます。 [MCP 入門](docs/start-mcp.md)

### RAG：出典付きで答える API

RAG の良さも、**答えの土台が育ち続ける**ことです。答えの質は、根拠を拾えているかで決まります。RAG の検索は MCP と同じなので、上の育ち方がそのまま答えの質になります。そのうえで、答える側も広げられます。

| 育ち方 | 何が起きるか | 使う仕組み |
|---|---|---|
| 検索が育つ | 資料の更新、当たり具合の測定、ユーザー辞書、構成の最適化。MCP と同じ | MCP と同じ |
| 答えを書くモデルを替える | 手元の Ollama から API のモデルへ、設定を変えて `serve` を起動し直すだけで差し替える。索引の作り直しは要らない | `KnowledgeNestfile.yaml` の `models` |
| 使うアプリを増やす | 同じ API を、社内のほかのアプリやチャットボットにも開く。エージェントは同じポートの `/mcp` で引ける。認証と接続元の制限を付けられる | `nest serve`、`serve.access` |

**ほかのライブラリで作ると**（LangChain、LlamaIndex など）、これを自分でやります。

1. 読み込み、分割、埋め込み、ベクトルデータベース、検索、生成の部品を選び、コードでつなぐ
2. 答えに出典を付ける方法と、根拠がないときに断る方法を作る
3. アプリから呼ぶための API サーバーを立て、認証を付ける
4. 答えの良し悪しを測るために、別の評価ライブラリを組み合わせる

**Knowledge-Nest なら**

```sh
nest config set llm --provider ollama --model qwen3:4b   # 最初の1回だけ
nest init rag ./rag --source ./manuals
cd rag
nest build
nest serve   # OpenAI の SDK でそのまま呼べる API が立つ
```

答えには資料の版と原文の範囲を指す出典が付き、根拠がなければ断ります。認証と接続元の制限は設定に書くだけです。評価用の質問づくりから最適化まで、同じ道具でできます。 [RAG 入門](docs/start-rag.md)

### Wiki：みんなで使う知識のページ

Wiki の良さは、**チームの知識が、だれのものでもない共有の財産として育つ**ことです。一人ひとりが持っている資料や現場の知見が、テーマごとのページに集まり、出典を保ったまま積み上がっていきます。

| 育ち方 | 何が起きるか | 使う仕組み |
|---|---|---|
| だれかが資料を足す | 関係するページに書き足され、新しいテーマはページになる。新しいことのない資料は「得るものなし」と記録され、水増ししない | `nest ingest`、画面の **資料を取り込む** |
| 資料が改訂される | その資料から書いたページだけが、新しい版で書き直される | 資料の版の追跡 |
| 人が知っていることを足す | 資料にない現場の知見を、誰の補足かを付けて出典にし、ページに入れる | `nest instruct <ページ> "…" --supplement "…" --by <名前>` |
| だれかが質問する | 残したい答えは、次の人のためのページになる | `nest query`、`nest save-answer` |
| 抜けや食い違いを見つける | ページ同士の矛盾、ページのない用語、次に調べるとよい問いと資料を挙げる | `nest lint --content` |
| みんなで使う | チームのネットワークに開いたブラウザの画面と、エージェントの MCP で、同じページを使う | `nest serve` |

人はページを直接書き換えず、指示で AI に直させます。だから、だれが手を入れても、ページは出典を持ったままです。いつ何をしたかは作業の記録（`log.html`）に残り、作業ごとに取り消せます。

**ほかの道具で作ると**（LLM-Wiki のスクリプト、ノートアプリの AI など）、これを自分でやります。

1. AI に資料を読ませてページを書かせる仕組みと、書き方の決まりを用意する
2. AI が書いたページに誤りがないか、人が全部読んで資料と見比べる
3. 資料が改訂されるたびに、どのページを直せばよいかを探す
4. 人が読む画面と、エージェントが引く口を別に用意する

**Knowledge-Nest なら**

```sh
nest init wiki ./wiki --purpose "設備保全の手順と部品情報をまとめる"   # モデルの設定は RAG と同じ1行
cd wiki
nest ingest ../manuals
nest serve   # ブラウザで読み、エージェントも MCP で引ける
```

数字・日付・引用が出典の資料にあるかはプログラムが照らし、ページ同士の矛盾やページのない用語も挙げます。資料が改訂されたら、その資料から書いたページだけを書き直します。AI の変更は作業ごとに取り消せます。Karpathy の LLM-Wiki の考え方に、出典との照合を足したものです。 [Wiki 入門](docs/start-wiki.md)

### PARA：自分の仕事を整理するノート

PARA（Tiago Forte の方法）の良さは、**仕事の知識と、自分の知識を分けて育てられる**ことです。

| 置き場所 | 育つ知識 | 例 | 決めるのは |
|---|---|---|---|
| **Projects** | いまの仕事・テーマの知識。期限があり、終われば片付く | 来月のポンプ更新工事 | あなた（`rules.md` に書く） |
| **Areas** | 続けて責任を持つ仕事の知識 | 設備の定期保全 | あなた（`rules.md` に書く） |
| **Resources** | 自分のスキルや関心の知識。仕事が変わっても残り、積み上がる | 振動の診断、部品メーカーの動向 | AI が、資料に合わせて話題を足していく |
| **Archives** | 終わった取り組みと、担当を外れた領域 | 昨年度の更新工事 | `nest archive` で移す |

仕事の資料は、その取り組みのノートとして集まり、取り組みが終われば丸ごと Archives へ片付きます。いまの仕事には使わないけれど自分の糧になる資料は、Resources の話題ごとに溜まり、仕事が入れ替わっても育ち続けます。Knowledge-Nest では、仕事の枠（Projects と Areas）はあなたが決め、関心の枠（Resources）は AI が資料に合わせて広げます。

**ノートアプリで PARA を運用すると**（Notion や Obsidian など）、これを自分でやります。

1. 資料が来るたびに読んで、どの取り組みに使うかを考え、フォルダに入れる
2. 使い道のメモを書き、元の資料をそばに置く
3. 取り組みが終わったら、ノートと資料とリンクを手で Archives へ移す
4. 期限を過ぎた取り組みがないかを、自分で見張る

**Knowledge-Nest なら**

```sh
nest init para ./para --purpose "設備保全の仕事に関わる資料とメモを整理する"
cd para
# rules.md に、いまの取り組みと領域を書く
nest ingest ../inbox                      # AI が使い道をノートに書き、使う取り組みに置く
nest archive Projects/ポンプ更新工事      # 終わったら、ノートも資料もリンクも一度に片付く
```

置き場所は、あなたが書いた取り組みと領域の中からしか選ばないので、フォルダは勝手に増えません。片付けは `nest undo` で戻せ、期限を過ぎた取り組みは `nest lint` が知らせます。 [PARA 入門](docs/start-para.md)

## 組み替えて、足せる（MCP・RAG）

MCP と RAG の処理は、読み込み、チャンク分け、索引、検索、回答の段ごとに、モジュールを並べた設定でできています。

- **組み替える。** ベクトル検索やリランカーを足す、チャンクを見出しに沿わせる、といった変更は設定を数行書き換えるだけです。 [モジュール](docs/modules.md)
- **読めない形式は、手持ちの変換ツールで。** `loader.command` に変換コマンドを書けば、その出力を本文として取り込めます。
- **モデルは差し替えられる。** 埋め込みと回答は手元の Ollama か OpenAI などの API から、リランカーは `/v1/rerank` か `/rerank` を出すサーバーから選べます。
- **新しいモジュールを足したいときは、どうぞ。** `src/registry.rs` の登録表に定義して足します。本体は MIT ライセンスで、手順は [開発と変更の確認](CONTRIBUTING.md) にあります。プルリクエストを歓迎します。

検索を測って最適化する手順は [検索を数字で良くする](docs/guide.md) にあります。

## インストール

npm への公開は準備中です。現在はソースからビルドします。Rust 1.95 以降と、Node.js 22.20 以降の 22 系または 24.12 以降の 24 系が必要です。

```sh
git clone https://github.com/hachiware-labs/knowledge-nest
cd knowledge-nest
npm ci
npm run build
npm link
nest --help
```

## 開発

```sh
npm ci
npm run build
npm test
npm --prefix tools/rag ci
npm --prefix tools/rag test
npm run test:package
npm run bench -- 1000 300
```

`test:package` は `dist/packages/` に tarball を作り、空のプロジェクトへオフラインでインストールして検索と本文取得を試します。ベンチマークは合成データで索引作成、検索レイテンシ、メモリ、Recall@10、nDCG@10 などを計測します。変更前の確認と CI の起動方法は [開発と変更の確認](CONTRIBUTING.md) にあります。

## 現在の状態

- バージョン 0.5.0 の開発版です。コマンドや設定の形は変わる可能性があります。
- `knowledge-nest` は仮のパッケージ名です。npm への公開は準備中です。本体のライセンスは MIT です。
- 動作を確認している環境は、Windows x64、Linux x64（glibc）、macOS arm64 と x64 です。
- 版の保管と、それを使うコマンド（`list`、`results`、`optimize`、`release`）は `data-management` ブランチで実装中です。コマンドは、読む設定ファイルの形で仕組みを選びます。

| | 新しい形（段階ごとの並びで書く設定） | `init` が作る形（`modules:` と `use:`） |
|---|---|---|
| 読める資料 | `.md`、`.markdown`、`.txt` | 左に加え HTML、PDF、Word、Excel、PowerPoint、OCR |
| 検索 | キーワード | キーワード、ベクトル、ハイブリッド、リランク、ユーザー辞書 |
| 版の記録と再利用、`list`、`results`、`optimize`、`release` | ○ | — |
| `serve`（MCP・HTTP）、`ask` | まだ | ○ |

Wiki と PARA は、どちらの形とも別の仕組みで、いつでも使えます。2つの形の詳しい違いは [検索を数字で良くする](docs/guide.md#10-従来の流れで使うもの) の10章 にあります。
