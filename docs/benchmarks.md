# キーワード検索のベンチマーク

`benches/keyword.mjs` は Node.js API で合成 Markdown を登録し、同一プロセスからキーワード検索を順次実行します。検索語には文書ごとに異なる識別子を含め、正解は対応する文書1件とします。

## 再現する

```sh
npm run build
npm run bench -- 1000 300
npm run bench -- 10000 300
```

第1引数は文書数、第2引数は計測する問い合わせ数です。索引付きストアを開き直した後、初回の検索を単独で計測し、後続の上位10件検索で p50・p95・p99 を測ります。`ingestMs` は生成済み資料の読み取りと索引登録にかかった時間です。`rssMiB` は計測終了時のプロセス全体の RSS です。

## 検索品質の基準

`benches/retrieval.mjs` は、決まった文書と評価ケースで MCP・RAG の検索品質を測ります。検索の手法（[retrieval-techniques.md](retrieval-techniques.md)）を足すときは、ここで基準と比べます。

```sh
npm run build
node benches/retrieval.mjs
node benches/retrieval.mjs benches/retrieval/hybrid.yaml candidate.yaml
```

引数を省くと、`benches/retrieval/keyword.yaml` と `benches/retrieval/hybrid.yaml` を順に測ります。設定ファイルごとに一時フォルダに新しいプロジェクトを作り、文書を入れて構築し、ケースを取り込んで `dev` の分割を評価します。最初の設定ファイルが基準で、ほかの設定はケースごとの差と符号検定の p で比べます。`hybrid.yaml` には、Ollama の ruri-v3（`hf.co/Targoyle/ruri-v3-310m-GGUF:Q8_0`）が要ります。

| --- | --- |
| `benches/retrieval/corpus/` | `docs/` の日本語の文書23件の写し（2026年11月23日）。設計仕様の2件（`knowledge-nest-spec.md`、`data-management.md`）は除いた |
| `benches/retrieval/cases.jsonl` | 評価ケース106件。`dev` 78件、`test` 28件（5文書のケースすべて）。`eval-data export` の形 |

**評価ケースの作り方。** 文書ごとに3〜8件、種類がおよそ同じ数になるように作りました。`lexical` 17件、`paraphrase` 35件、`identifier` 28件、`variant` 26件です。`variant` は、同義語や表記ゆれへの対策（[retrieval-techniques.md](retrieval-techniques.md) の9）を測るためのものです。文書は「索引」「文脈」「フォルダ」「埋め込み」「ユーザー」と書き、質問は「インデックス」「コンテキスト」「ディレクトリ」「エンベディング」「ユーザ」のように別の書き方をします。

- `eval-data generate` を `qwen3:4b` で試しましたが、使えませんでした。質問の多くは文書の文の写しか見出しで、種類はほぼすべて `lexical` でした。`variant` と `paraphrase` は作れませんでした。
- そこで、ケースはエージェント（Claude）が文書を読んで書き、別のエージェントが確認しました（`input_by: agent`、`reviewed_by.type: agent`）。
- 引用は文書の中に1度だけ現れる300文字以内の文です。ほかの文書に同じ答えが書かれている事実は避けました。
- 質問と引用の重なりが低いのに `lexical` とされていた7件は `paraphrase` に直しました。重なりの平均は `lexical` 0.50、`identifier` 0.46、`variant` 0.30、`paraphrase` 0.09 です。
- 人による確認はまだです。

**基準の値。** 2026年11月23日、コミット `c3067cd` に、このベンチマークを足す変更を加えた状態で測りました。環境は上と同じ Windows マシンです。`dev` の78件の値です。

| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| `keyword` | 0.513 | 0.513 | 0.628 | 0.859 | 0.597 | 0.658 | 0.007 | 1.9 ms | 0.3秒 |

種類ごとの値（MRR@10 と文脈の回収）:

| 種類 | 件数 | 重なり | `keyword` MRR | `hybrid` MRR | `keyword` 文脈 | `hybrid` 文脈 |
| --- | --- | --- | --- | --- | --- | --- |
| `lexical` | 11 | 0.50 | 0.886 | 0.861 | 0.727 | 0.818 |
| `identifier` | 20 | 0.46 | 0.752 | 0.721 | 0.650 | 0.650 |
| `variant` | 19 | 0.30 | 0.599 | 0.680 | 0.526 | 0.684 |
| `paraphrase` | 28 | 0.09 | 0.371 | 0.400 | 0.321 | 0.393 |

- **ベクトル検索を足すと、文脈の回収が上がる。** 6件で良くなり、悪くなった質問はありません（p = 0.031）。MRR@10 は14件で良くなり16件で悪くなり、差は誤差と区別できません（p = 0.86）。回収@1 は同じです。
- **言い換えと表記ゆれが弱い。** `paraphrase` の MRR は `lexical` の半分以下です。`variant` は、キーワード検索だけでは `lexical` より0.29低くなります。ベクトル検索で0.08上がりますが、差は残ります。同義語と表記ゆれへの対策は、`variant` の行で測れます。
- **見つからなかった根拠のほとんどは、文脈の予算が足りなかったもの。** `keyword` で見つからなかった38件のうち、35件が `over_budget` で、`not_retrieved` は3件です（`hybrid` では32件と0件）。抜粋は行の単位で広がり、これらの文書は段落を1行に書くので、1つの抜粋が1500文字ほどになります。4000文字の文脈には2〜3件しか入りません。根拠の割合が1%に満たないのも、そのためです。チャンクを行の途中で止める、文脈の予算を増やす、の効果は、この行で測れます。
- **Ollama は `127.0.0.1` で指定する。** `http://localhost:11434` と書くと、この Windows マシンでは、検索のたびの埋め込みの要求に約2秒かかりました（検索 p50 は2073 ms）。`127.0.0.1` では20 ms で、値は同じです。

`test` の分割は、手法を選び終えた後の確認に取っておきます。
