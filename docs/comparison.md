# Knowledge-Nest が向いている構成

Knowledge-Nest は、手元の資料フォルダから、エージェントが引く検索、出典付きで答える API、AI が書くナレッジベース、PARA のノートを、プログラムを書かずに作る道具です。ここでは、やりたいことごとに、よくあるほかの方法と比べます。ほかを選ぶほうがよい場合も書いています。 [入門](getting-started.md)

## やりたいことごとに比べる

### Claude などのエージェントに、手元の資料を調べさせる（MCP）

| よくある方法 | Knowledge-Nest を選ぶ理由 | ほかを選ぶほうがよいとき |
|---|---|---|
| エージェントに、フォルダのファイルを直接読ませる | PDF・Word・Excel・スキャンした資料も、日本語の語で引ける。答えのある箇所だけを、資料名と行を付け、決めた文字数に収めて返すので、資料が多くても文脈を埋めない | 資料が数件の Markdown だけで、エージェントが全部読めば済む |
| ベクトル検索の検索サーバー（ベクトルデータベースの MCP など） | 埋め込みモデルなしで、日本語のキーワード検索がすぐ動く。型番や専門用語のように、その語で探したい検索に強い。ベクトルを足したハイブリッドにもできる。当たり方を回収率で測り、候補の設定をまとめて試して最適化できる | すでにベクトルデータベースを運用していて、複数のアプリで同じベクトルを使いたい |

### 自分のアプリやチャットボットに、出典付きで答えさせる（RAG）

| よくある方法 | Knowledge-Nest を選ぶ理由 | ほかを選ぶほうがよいとき |
|---|---|---|
| LangChain などのライブラリで、検索と生成の流れをコードで組む | コードを書かず、設定ファイルとコマンドで立ち上がる。回答 API は OpenAI の Responses API の形で、既存のアプリは接続先を変えるだけ。根拠がなければ答えずに断る。引用は資料の版と原文の範囲まで指す。評価から最適化までが同じ道具に入っていて、評価の仕組みを別に組まなくてよい。モジュールの並びを変えれば構成を組み替えられ、足りないモジュールは足せる | アプリ固有の処理、ツール呼び出し、検索と生成の細かな流れをコードで作り込みたい |
| ノーコードの RAG アプリ（画面で資料を登録してチャットする製品） | 資料も索引も手元のフォルダに置いたまま動く。設定を変えたときに、答えの根拠を拾える割合を測って比べられる。どこで根拠を落としたか（検索、統合、文脈の予算）まで分かる | 利用者ごとの権限、チャット画面、利用状況の管理まで含めた製品がすぐに欲しい |

### 資料から、ナレッジベースを作る（Wiki）

| よくある方法 | Knowledge-Nest を選ぶ理由 | ほかを選ぶほうがよいとき |
|---|---|---|
| ノートアプリの AI 機能や、チャットで資料を要約させる | ページはどの資料から書いたかを持ち、数字・日付・引用が資料にあるかをプログラムが照らす。資料の新しい版が来ると、古い版から書いたページを知らせる。資料を足すたびに、関係するページへ書き足す | 1回きりの要約が欲しいだけで、ページを育てる必要がない |
| LLM-Wiki を自分でスクリプトにする | 取り込み、問い合わせ、点検（矛盾、リンク切れ、ページのない概念）、作業ごとの取り消し、ブラウザの画面、MCP での提供が、最初からそろっている。ページはただの HTML ファイルで、ほかの道具にも持っていける | ページの形や書き方を、プログラムで自由に変えたい |
| 人が Wiki を書く | 書くのは AI で、人は資料を選び、指示し、点検の結果を判断する。ログインの要るページや X の投稿も取り込める | 内容の正しさを、人が一文ずつ書いて保証する必要がある |

### 溜まった資料とメモを、仕事ごとに整理する（PARA）

| よくある方法 | Knowledge-Nest を選ぶ理由 | ほかを選ぶほうがよいとき |
|---|---|---|
| ノートアプリで、手で PARA に振り分ける | 資料を入れるだけで、AI が使い道をノートに書き、使う場所に置く。置き場所は、人が書いた取り組みと領域の中からしか選ばない。終わった取り組みは、ノート、資料、リンクごと一度で Archives へ移し、取り消せる | ノートを書く行為そのものを、自分の考える時間にしたい |
| フォルダの自動振り分け（ルールやタグで分ける） | ファイルの名前や種類ではなく、中身を読んで「どの取り組みに使うか」で分ける。期限を過ぎた取り組みを知らせる | 振り分けの規則が単純で、中身を読む必要がない |

## 組み合わせて使う

LangChain には文書を検索するエージェントや、処理の流れを組み立てる RAG の例があります。Qdrant はベクトル検索に加え、付随データを使った絞り込みの API を提供します。どちらも、Knowledge-Nest と一緒に使えます。Knowledge-Nest の検索は MCP と HTTP で呼べるので、自作のアプリやエージェントから、その1つの道具として使えます。 [LangChain の利用例](https://docs.langchain.com/oss/python/learn) · [Qdrant の概要](https://qdrant.tech/documentation/overview/what-is-qdrant/) · [Node.js API](api.md)

文書単位のアクセス権、複数テナント運用、独自のエージェント制御が要件に入る場合は、その責任を持つアプリケーションの設計が先に必要です。ほかの方法と比べるときは、実際の質問と正解の引用を揃えて、出典の回収と検索時間を測ります。 [評価の手順](evaluation.md)
