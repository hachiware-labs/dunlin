# Knowledge-Nest データ管理システム 設計

2026年11月21日 · 北田成秀

## 1 この文書について

Knowledge-Nest のビルドが作るデータを、Git のコミットのように記録して再利用する仕組みと、設定ファイル・段階との関係を定める。記録の形とIDの計算の決まりを先に固定し、`extract`、`transform`、`index` の3つの段階をその利用者にする。

- **範囲**: 種別 `mcp` と `rag` のビルド。Wiki/PARA の原本と版も、同じ保管を使えるようにするが、この文書では扱わない。
- **前提**: 2026年11月21日から22日の議論と、4回のレビューで決めた内容（末尾の15章に未決事項）。保管の形は、テキストの `extract` を実装しながら決め直した（4章）。実装の現状は、コミット `73ac628` のコードを読んだ内容に基づく。レビューでコードと照合したが、実行しての確認はしていない。
- **位置づけ**: [knowledge-nest-spec.md](knowledge-nest-spec.md) の7章、11章、12章の土台を置き換える。

### 用語

| 用語 | 意味 |
| --- | --- |
| オブジェクト | IDと中身とメタデータ。IDは中身のハッシュで、同じ中身は1つだけ持つ |
| 部品 | 読み取りデータの1単位。オブジェクトと、その種類、形式、元の文書の中での位置を持つ |
| 項目 | 文書1つの、ある段階での中身。部品の並びを持つ。これもオブジェクトとして保存する |
| スナップショット | 段階の終わりにできる版。種別、入っているものの一覧、親、付いている名前を持つ。IDは通し番号である |
| 付箋 | オブジェクトやスナップショットに後から足せるメタデータ。失っても計算し直せるものだけを置く |
| 処理のキー | 実行する前に計算できるID。「もうあるか」を引くために使う |
| 内容のID | 作ったデータから計算するID。オブジェクトID、項目ID、一覧のダイジェストの総称 |
| タグ | スナップショットを指す名前。動く。スナップショットの種類ごとに別の棚を持つ |
| `default` | 手で実行して最後にできたものに、種類ごとに付くタグ |
| 提供用の名前 | `serve` が提供に使う名前。タグとは別に持ち、リリースだけが動かす |
| 最適化の指示 | 基準の設定ファイル、変えるところ、評価の方法、上限を書いたファイル（11章） |
| 候補 | 指示から作った設定ファイルの1つ。または、人が書いた、本体以外の設定ファイル |

## 2 設計の原則

このシステムの価値は、利用者が意識しない階層で、版管理と再利用と枝分かれが自然に起きることにある。

1. **利用者に新しい操作を求めない。** 設定ファイルを書いて `build` を実行するだけで動く。最短の3コマンドに、タグもIDも出さない。
2. **中身の意味を知らない。** テキストか画像か、チャンクがどう切られたか、索引の内部がどうなっているかを、このシステムは知らない。知っているのは、種類の名前、項目の識別子、オブジェクトのハッシュ、処理の識別だけである。
3. **テキストに限定しない。** 読み取りデータは種類つきの部品の並びとして持つ。マルチモーダルの機能は今は作らず、後から足しても作り直しにならない形だけを決める。
4. **同じ入力と同じ処理は、1回しか実行しない。** 変えた所から後ろだけが動く。
5. **確定したものは変えない。** オブジェクトの中身と、スナップショットの種別・一覧・親は書き換えない。後から変わるのは、名前と付箋だけである。
6. **全段階で形をそろえる。** 名前、日時、完了の判定、差の表示、回収を、段階ごとに作らない。
7. **速さを落とさない。** テキストだけの資料では、今と同じ速さと同じ結果になる。
8. **エラーは利用者の言葉で出す。** 「キーが一致しない」ではなく、「チャンクの設定が、出発点を作ったときと違う」と伝える。

新しい決定のたびに、次の2つを確かめる。

- この形は、テキスト以外でも成り立つか。
- この変換だけを変えて、後ろだけをやり直せるか。

## 3 全体像

システムは3つの表でできていて（4章）、考え方の多くは Git と対応づけられる。ただし、全体を1つのツリーにまとめる Git とは違い、データは種別ごとに管理する。

| 表 | 役割 | Git での対応 |
| --- | --- | --- |
| `objects` | 中身をハッシュで保存する。同じ中身は1つだけ持つ | ブロブ |
| `snapshots` | 中身の一覧、親、付いている名前を持つ。種別ごとに系列を作る | コミットとツリー、ブランチに近い。ただしIDは通し番号で、名前は行が持つ |
| `runs` | 起きたことの記録。キーから結果を引き、名前の履歴を辿る | reflog に近い。ビルドのキャッシュも兼ねる |

スナップショットは、入力にしたスナップショットを親として指す。たどると、フォルダを読んだ時点まで戻れる。

```text
extract             transform              index
docs ─────┬─────── chunks-800 ─────────── main          ← release
          └─────── chunks-400 ───┬─────── trial-400
                                 └─────── trial-400-dict
```

- **データは種別ごとに管理する**: ここが Git と違う。Git は1つのツリーが全ファイルを持ち、コミットが1本の履歴になる。このシステムでは、種別（`files`、`extracted`、`chunks`、`index`、辞書など）ごとにスナップショットの系列があり、それぞれが自分の名前と履歴を持つ。種別の間は「入力」でつながる。全体を1つにまとめたツリーは持たない（4.5節）。
- **つながりは2種類ある**: 「入力にした上流のスナップショット」と、「同じタグが前回指していたスナップショット」である。IDの計算に使うのは前者だけとする。後者は差の表示と履歴にだけ使う。
- **段階は区切りとして残る**: 段階は「スナップショットを確定して保存する、名前のついた区切り」である。実行の仕組みはIDで動き、人とエージェントがやり直しの範囲を言う言葉として段階を使う。
- **索引は中身の見えない作成物として扱う**: `index` のスナップショットは論理的な中身だけを持ち、索引のディレクトリは別に記録する（6.4節）。索引の内部には立ち入らない。

### 3.1 設定ファイル、段階、データ管理の位置づけ

Knowledge-Nest のビルドは3つの層でできている。利用者が触るのは一番上の設定ファイルだけで、データ管理は一番下で見えないまま働く。

```text
設定ファイル   KnowledgeNestfile.yaml         何を、どの順に、どんな名前で作るかを書く
     │         区切り・モジュール・引数・タグ
     ▼
段階           extract → transform → index   区切りごとに処理を進め、終わりで確定する
     │         開始・引く・書く・閉じる・まとめて作る・確定（8章）
     ▼
データ管理     オブジェクト・スナップショット・実行の記録   作ったものを記録し、同じものは作り直さない
```

| 層 | 担うこと | 知っていること | 触る人 |
| --- | --- | --- | --- |
| 設定ファイル | 処理の内容と名前の宣言 | 区切り、モジュール、引数、タグ名 | 利用者、エージェント |
| 段階 | 区切りごとの実行と進み具合の表示 | モジュールの中身。1項目をどう変換するか | 実装者 |
| データ管理 | 記録、再利用、名前、系統、回収 | 種類の名前、ハッシュ、処理の識別だけ | 誰も触らない |

### 3.2 設定ファイルの要素がどこへ行くか

設定ファイルに書くものは、すべてデータ管理のどこかに対応する。データ管理を使うための専用の指定はない。

| 設定ファイルの要素 | データ管理での対応 | IDに影響するか |
| --- | --- | --- |
| 区切りの名前（`extract`、`transform`、`index`） | スナップショットを確定する境目と、データの種類（`kind`） | する |
| 区切りの中のモジュール名と引数 | 処理の識別（6.1節）。結果に影響する引数だけが入る | する |
| `models` の定義 | モジュールが参照した分だけ、処理の識別に解決して入る | する |
| 区切りの最後の `tag` | 名前の表。段階が完了するたびに付け替わる | しない |
| 区切りの先頭の `from`（案） | 入力にするスナップショットの解決。作らずに既存のものを使う | する（入力が決まる） |
| `serve.tag` | 提供に使うスナップショットの解決 | しない |
| `serve` のほかの項目（ポート、接続制限） | 対応なし | しない |
| `search`、`ask` の区切り | 対応なし。検索設定IDとして、評価レポートが記録する | しない |
| `eval-data`、`eval` の区切り | 対応なし。評価はスナップショットを読む側 | しない |

- **設定ファイルがそのまま処理の定義になる。** 「キャッシュを使う」という指定は要らない。同じ設定なら同じ結果、という動きとして現れる。
- **構築に関わるのは3つの区切りだけ。** `search` や `serve` を変えても、スナップショットは作り直されない。
- **候補の設定ファイルが枝分かれになる。** 設定ファイルを複製して区切りの中身とタグ名を変えると、変えた区切りから先が別の枝になる。

### 3.3 段階とデータ管理の分担

段階は「何を作るか」を担い、データ管理は「作ったものをどう持つか」を担う。

| ことがら | 段階 | データ管理 |
| --- | --- | --- |
| フォルダの走査、抽出、チャンク化、索引の作成 | 担う | 知らない |
| 設定から処理の識別を作る | 担う（モジュールの宣言を使う） | 受け取るだけ |
| キーの計算と、既存の結果の検索 | 呼び出す | 担う |
| 追加・更新・削除の判定 | ファイルのハッシュを渡す | 一覧の比較で判定する |
| 完了の確定、日時、タグの付け替え | 呼び出す | 担う |
| 進み具合と計画の表示（`--dry-run`） | 段階の名前で表示する | 再利用か実行かを答える |
| やり直しの範囲を言う言葉 | 段階の名前（`--from transform`） | タグとID |
| 系統、差、比較できるかの判定、回収 | 関わらない | 担う |

1回の `nest build` は、次の順で進む。

1. 設定ファイルを読み、検証する。区切りごとに、モジュールの並びから処理の識別を作る。
2. `extract` の区切りを実行する。フォルダを走査し、変わった文書だけを読み取り、スナップショットを確定してタグを付ける。`from` が書いてあれば、作らずにその名前を解決する。
3. `transform` の区切りを実行する。前のスナップショットと処理の識別からキーを計算して引く。あればそれを使い、なければ項目ごとに引いて、足りない分だけを実行する。
4. `index` の区切りを同じように実行する。
5. 本体の設定ファイルでの実行なら、提供用の名前を `index` のスナップショットへ付け替える。候補の設定なら付け替えない。

段階の進め方は3つとも同じで、違うのは「1項目をどう変換するか」だけである。

### 3.4 利用者から見える範囲

| 利用者 | 触るもの | 見えるもの |
| --- | --- | --- |
| 簡単に使う人 | `init`、`build`、`search`、`serve` | 文書数と所要時間。タグもIDも見えない |
| 設定を調整する人 | 設定ファイルのモジュールと引数、`--from <段階>`、`--dry-run` | 段階ごとの「再利用」「実行」 |
| 作り込む人、エージェント | 候補の設定ファイル、タグ名、`eval`、`report compare`、`release` | タグ、系統の木、リリースの記録 |

深く使うほど下の層が見えてくるが、どの深さでも同じ仕組みの上で動いている。

## 4 保管の形

保管は3つの表でできている。中身を持つ `objects`、中身の組を持つ `snapshots`、起きたことを記録する `runs` である。初版からの検討で、表は10個から3個になった。経緯は4.6節に残す。

| 表 | 役割 | 置き場所 |
| --- | --- | --- |
| `objects` | IDから中身を引く | `objects.sqlite` |
| `snapshots` | 中身の組と、その親、付いている名前 | `records.sqlite` |
| `runs` | 起きたことの記録。キーから結果を引き、名前の履歴を辿る | `records.sqlite` |

全体を通す決まりは1つである。**新しく作る行に、その行のことをすべて書く。すでにある行には書き足さない。** スナップショットは、作るときに自分の親と中身の一覧を書く。親の行にも、オブジェクトの行にも、何も書かない。後から変わるのは、名前（タグ）と付箋だけである。

### 4.1 オブジェクト

オブジェクトは、IDと中身とメタデータである。

| 属性 | 内容 | 書くとき |
| --- | --- | --- |
| `id` | 中身のハッシュ。`obj-` に続けて、バイト列の BLAKE3 を書く | 作るとき |
| `data` | 中身。バイト列 | 作るとき |
| `size` | バイト数 | 作るとき |
| `created_at` | 最初に保存した時刻 | 作るとき |
| `results` | 控え。この中身に処理をかけて、できた項目。処理のIDごとに持つ | 処理したとき |
| `meta` | 付箋。後から足せる | 足すとき |

- **IDは中身だけで決まる。** メタデータはIDに入れない。同じバイト列は、必ず1つのオブジェクトになる。
- **種類と形式は、オブジェクトではなく、指す側が持つ。** 同じ内容の `guide.md` と `guide.txt` は、オブジェクトが1つで、形式が2つある。形式をオブジェクトに置くと、後から書いたほうが勝ち、片方の文書の形式が間違う。そのため、種類と形式は部品に置く（5.1節）。
- **テキストの原本と、読み取った本文は、同じオブジェクトである。** テキストは読んだバイト列がそのまま本文になるので、ハッシュが一致する。ファイルリストも、読み取りデータも、同じIDを指す。
- **項目もオブジェクトである。** 項目のIDは `itm-` で始まり、`data` は部品の並びの JSON である。接頭辞と計算の領域を分けるのは、文書として置かれた JSON が、項目の記録と同じIDを持つのを防ぐためである。
- **付箋には、失っても作り直せるものだけを置く。** `results` と `meta` を消しても、次の実行が処理し直すだけで、結果は変わらない。付箋は、内容のIDに影響するものを持たない。作ってある物の場所のように、IDに関わらないことを付箋から読むのは構わない。
- **情報オブジェクトも置ける。** 文書の中身ではなく、「何を、どの設定で作ったか」を表す JSON である。IDは `inf-` で始まる。索引の情報がその例である（6.4節）。
- **`results` が、項目のキーの役割を担う。** 「この中身に、この処理をかけたら、これができた」を、処理をかけられた側のオブジェクトが覚える。途中で止まった実行の続きと、以前の内容に戻したファイルの再利用は、これで働く。

### 4.2 スナップショット

スナップショットは、オブジェクトの一覧に、親と名前を付けたものである。

| 属性 | 内容 | 書くとき |
| --- | --- | --- |
| `id` | 通し番号。作った順に振る。中身を表さない | 作るとき |
| `type` | 種別。`files`、`extracted`、`chunks`、`index`、辞書など | 作るとき |
| `items` | 入っているものの一覧。名前と、オブジェクトID、項目ID、情報オブジェクトIDのどれかの組 | 作るとき |
| `count` | `items` の件数 | 作るとき |
| `parents` | 入力にしたスナップショットのID | 作るとき |
| `tags` | 付いている名前の配列 | 付け外しのとき |
| `created_at` | 作った時刻 | 作るとき |
| `meta` | 付箋。後から足せる | 足すとき |

- **つながりは、子の側に親を書くだけである。** 「このスナップショットから作られたもの」は持たない。知りたいときは、`parents` にそのIDを持つ行を探す。系統を表示するときだけの操作である。
- **オブジェクトは、自分がどのスナップショットに入っているかを持たない。** オブジェクトは多くの版で共有される。持たせると、版を作るたびに、変わっていない全オブジェクトの行を書き換えることになる。
- **名前は、スナップショットの行が持つ。** 名前の解決は、その名前を `tags` に持つ行を探すことである。付け替えは、古い行から外して新しい行に付ける、2行の更新になる。履歴は `runs` が持つ。
- **IDは中身を表さない。** そのため、次の2つを `type` と `items` で行う。
  - 「同じ中身か」は、`type` と `items` を比べて決める。実行の結果が、名前が今指す版と同じなら、行を作らず、その版を結果にする。
  - 下流のキーは、上流のIDではなく、上流の `type` と `items` から計算したダイジェストで作る（6.2節）。同じ中身なら、番号が違っても同じキーになる。
- **省いた文書は載せない。代用した文書は、以前の項目を載せる。** 理由と「代用を含む」という事実は、`runs` が持つ。読めなかった文書に以前の項目を載せた結果は、中身としては以前の版と同じなので、同じ版になる。
- **`files` の付箋に、走査の観測を置く。** ファイルごとの大きさ、更新日時、次回は必ずハッシュを計算し直す印である。ハッシュは `items` が持っているので、重ねて持たない。

### 4.3 実行の記録

`runs` は、段階を1回進めるたびに1行できる。3つの役割を兼ねる。実行の履歴、キーから結果を引く表、名前の付け替えの履歴である。

| 属性 | 内容 |
| --- | --- |
| `id` | 実行ID。開始時に発行する |
| `stage` | 段階の名前 |
| `key` | スナップショットのキー |
| `inputs` | 入力にしたスナップショットのID |
| `state` | `building`、`complete`、`failed` |
| `started_at`、`completed_at` | 開始時刻と完了時刻 |
| `snapshot` | 結果のスナップショットのID |
| `outcome` | `created`（新しい版ができた）、`reused`（キーで引けたので実行しなかった）、`unchanged`（実行したが、今の版と同じ中身だった） |
| `degraded` | 失敗による代用を含むか |
| `tag` | この実行が結果に向けた名前 |
| `added`、`updated`、`deleted`、`unchanged` | 件数 |
| `config` | 実行したときの設定ファイル。オブジェクトIDで持つ |
| `info` | 結果の作り方。作る種別、入力の一覧のダイジェスト、モジュールの並び（名前、出力互換性バージョン、引数）を持つ情報オブジェクトのID |
| `cause` | この実行を起こした実行のID。最適化が起こした build と評価が持つ（11.4節）。人が実行したものは空 |
| `stats` | 一覧や所要時間など。JSON |

- **作り方は、実行の記録が持つ。** `info` は、キーがハッシュにしているものを、読める形で持つ。キーからは中身を読めないが、`info` からは「どのモジュールが、どの引数で作ったか」が読める。スナップショットの一覧には入れない。入れると、設定を変えただけで結果が同じ場合にも別の版になり、下流の再利用が減るためである。
- **当時の設定ファイルも、実行の記録が持つ。** 検証を通った設定ファイルの全体を、原文のままオブジェクトとして保存する。秘密は、モジュールの宣言と検証で弾く（6.1節）。同じファイルは1つのオブジェクトなので、実行のたびに増えない。`nest show <タグ>` は、その名前を動かした実行の `config` と `info` から、作り方を表示する。
- **スナップショットを作らない実行もある。** 最適化の行は、`snapshot` と `outcome` が空である。キーの検索と名前の履歴には現れない。
- **走査には `info` がない。** `files` は処理の結果ではなく、フォルダを見た結果である。走査の設定（パス、除外）は `stats` に置く。
- **キーの検索**: そのキーを持つ、完了していて代用を含まない、最新の行の `snapshot` が結果である。代用を含む実行はここで外れるので、次の実行が失敗した文書を読み直す（6.3節）。
- **名前の履歴**: その名前を `tag` に持つ完了した行を、順に並べたものである。
- **前回のファイルリスト**: その名前を `tag` に持つ最新の完了した行の `inputs` である。追加・更新・削除は、これと今回のファイルリストの差である。
- **スナップショットの「完了時刻」**は、それを最初に結果にした行の完了時刻とする。**「最後に確認した時刻」**は、それを結果にした最新の行の完了時刻とする。変更なしの build では、`files` が `unchanged`、その先が `reused` になり、行だけが増える。

### 4.4 ファイルリスト

ファイルリストは、`type` が `files` のスナップショットである。`items` は、情報源IDと文書IDから、ファイルの中身のオブジェクトIDへの対応である。

- **中身だけで決まる。** 「どの文書が、どの内容であったか」が同じなら、フォルダの場所や走査の設定、日時が違っても、同じ一覧になる。
- **`extract` の段階は、内部で2つのスナップショットを作る。** 走査して `files` を作り、それを親に `extracted` を作る。利用者に見える段階は3つのままで、設定ファイルの `tag` は `extracted` に付く。
- **`files` はキーで引かず、毎回走査して作る。** 前回と同じ一覧なら、前回の版を結果にする。
- **パーサが受け持つファイルは、走査のときにオブジェクトとして保存する。** ハッシュを計算するために読んだバイト列を、そのまま保存する。読み取りは保管から行うので、ファイルを2度読まない。原本を読む口は、オブジェクトを読むことである。
- **どのパーサも受け持たないファイルは、IDだけを載せる。** 中身は保存しない。誰も読まないためである。

取り込む変更は、`source.filesystem` の引数 `apply` で選べる。

```yaml
extract:
  - source.filesystem: { path: ./docs, apply: [add, update] }   # 削除は取り込まない
```

- **`apply` には、`add`、`update`、`delete` を並べる。** 省くと3つすべてで、フォルダの今の状態に合わせる。
- **選ばなかった変更は、ファイルリストに入れない。** 追加を選ばなければ、新しいファイルを載せない。更新を選ばなければ、書き換えたファイルを前の内容のIDのまま載せる。削除を選ばなければ、消えたファイルを前の内容のIDのまま残す。ファイルリストは「フォルダにあるもの」ではなく、「情報源が持つとみなすもの」である。
- **この選択は、`files` より先に伝わらない。** `extracted` の処理の識別にもキーにも入れない。結果が `files` の中身にすでに表れているためである（6.2節の「走査だけに関わる引数」）。同じ一覧からは、選択が違っても同じ文書ができる。
- **比べる相手は、前回のファイルリストである。** 取り込まなかった変更は、前回の一覧に入っていないので、次の実行でもう一度「変更」として見つかる。`apply` を広げた実行が、その分を取り込む。
- **取り込まなかった文書は、実行の記録の `stats` に残す。** 追加、更新、削除ごとの文書の名前である。実行の記録の件数（`added` など）は、取り込んだ分だけを数える。
- **新しいファイルで、追加を選んでいないものは、開かない。** 更新を取り込まなかったファイルは、付箋に読み直しの印を付ける（5.3節）。付箋の大きさと更新日時が、一覧に載せた内容のものではないためである。

### 4.5 種別ごとの管理と、文書をまたぐデータ

スナップショットは種別（`type`）ごとに系列を作る。全体を1つにまとめたツリーは持たない。文書をまたいで作るデータは、文書の一覧に押し込まず、別の種別のスナップショットとして持つ。辞書がその最初の例である。

| 種別 | `items` の名前 | 親 | 作り方 |
| --- | --- | --- | --- |
| `files` | 情報源IDと文書ID | なし | 毎回走査して作る |
| `extracted`、`chunks` | 情報源IDと文書ID | 上流のスナップショット | キーで引き、なければ項目ごとに作る |
| `index` | 索引の種類。`keyword`、`vector` | `chunks` | キーで引き、なければ索引を作って、索引の情報を載せる |
| 辞書（例） | 用語。または辞書全体で1件 | 手で書いた辞書はなし。チャンクから抽出する辞書は `chunks` | 手で書いた辞書は毎回読んで作る。抽出する辞書はキーで引く |

- **仕組みは共通で、系列は別である。** 3つの表は、どの種別でも同じものを使う。種別ごとに違うのは、`items` の名前と、指す中身だけである。辞書にも名前と履歴が付き、版の差として「どの用語を足したか」が出る。
- **使う側は、親を複数持つ。** 辞書を使う `index` のスナップショットは、`chunks` と辞書の2つを親にする。
- **文書をまたぐ入力を変えると、使う段階の全項目が対象になる。** 辞書は全項目の入力なので、どの項目も処理し直す。キーワード索引は作り直しが要るので、これは正しい動きである。
- **循環を禁じる。** ある段階の結果から作ったデータを、同じ段階かそれより上流で使う構成は、設定エラーにする。
- **当面、ユーザー辞書は処理の識別に入れる。** 今は外部ファイルの内容のハッシュとして扱う（6.1節）。辞書を独立の種別にする時期は15章で決める。
- **一覧は、文書以外のものも持てる。** `index` の一覧は、文書ごとの項目ではなく、索引ごとの情報オブジェクトを持つ。文書の一覧は親の `chunks` が持っているので、重ねて持たない（6.4節）。

### 4.6 この形になった経緯

| 決めたこと | 理由 |
| --- | --- |
| 保存体系を新規に作る | 今の表との互換を考えずに、形を決められる |
| ブロブ、実体、項目、スナップショットの表を1つにする | どれも「IDから、変わらない中身を引く」だけの表である |
| オブジェクトは、IDと中身とメタデータだけにする | ハッシュ関数が1つになり、ブロブと実体を分ける理由がなくなった |
| メタデータをIDに入れない | 後から足せるようにする。そのかわり、種類と形式は指す側が持つ |
| スナップショットを独立の表にし、親、名前、一覧を持たせる | 版として扱うものを、1行で表す |
| スナップショットのIDを通し番号にする | 名前や付箋を後から変える行なので、中身から計算する理由が薄い |
| つながりは、子に親を書くだけにする | 子を作るときに書くのは容易だが、親の側を後から書き換えるのは大変である |
| キーの表と名前の表をなくす | 実行の記録が、同じ情報をすでに持っている |
| 名前に「動かない」という種類を設けない | Git と同じく、名前はどれも動かせる。動かさなければ、動かないだけである |
| 項目のキーと走査の観測を、付箋に移す | どちらも、失っても計算し直せる控えである |
| 付箋のうち共通で使うものを、属性に括り出す | `size`、`created_at`、`results`、`count`、`inputs`、`tag`、件数 |
| 作り方と当時の設定ファイルを、実行の記録に持たせる | どの版も、自分がどう作られたかを説明できる。一覧に入れないので、再利用は減らない |
| 索引だけは、作り方を一覧にも載せる | 索引は、一覧が結果のすべてを表さない。設定が違えば別の索引なので、別の版にする（6.4節） |

## 5 項目と部品

文書を扱う種別（`extracted`、`chunks`、`index`）の項目を定める。1つの項目は、1つの文書に対する種類つきの部品の並びである。テキストだけの文書は、部品が1つの項目になる。

### 5.1 部品

| 項目 | 内容 |
| --- | --- |
| `object` | オブジェクトID（4.1節） |
| `kind` | 種類。`text`、`table`、`image`、`chunks`、`embedding` など。知らない種類も保存できる |
| `media_type` | 形式。`text/plain`、`image/png` など |
| `location` | 元の文書の中での位置（5.2節） |
| `derived_from` | 派生した部品の場合、元の部品とその位置。OCRの結果、図の説明文、書き起こし |
| `attrs` | 文書の中での役割を表す付加情報。見出しの階層など |

部品は「どの中身が、何として、文書のどこにあるか」を表す。同じ図が2つの文書にあれば、オブジェクトは1つで、部品が2つになる。

- **派生したテキストは元への対応を持つ。** キーワード検索はテキストの部品に対して今のまま動き、出典は元の画像の領域まで辿れる。
- **段階は扱える種類を宣言する。** 扱わない種類の部品は、エラーにせず、そのまま次へ渡して警告する。
- **項目の内容のIDは、全部の部品から計算する。** 本文だけで計算すると、図だけを差し替えた更新を見逃す。

### 5.2 位置

位置は種類つきで表す。出典、評価の根拠、Wikiの引用は、すべてこの形の位置を指す。

| 種類 | 表し方 | 今使うか |
| --- | --- | --- |
| `text_range` | 行の範囲とバイトの範囲 | 使う |
| `page_region` | ページ番号と領域 | 形だけ決める |
| `cell_range` | シートや表と、セルの範囲 | 形だけ決める |
| `time_range` | 開始と終了の時刻 | 形だけ決める |

**評価の根拠の正本は変えない。** 今の実装は「文書と引用」を正本とし、位置は照合で求めた派生物として持っている（仕様 9.4、9.5）。`text_range` は抽出後の本文の上の位置なので、読み方を変えるとずれる。読み方やチャンクの切り方を変えても同じ評価データで比べられるのは、今の形のほうである。初版の「根拠を位置への参照として持つ」という記述は誤りだったので、次のように改める。

- **根拠は「文書と、種類つきの手がかり」として持つ。** 今ある手がかりの種類は「引用」だけである。評価データの形式に種類の欄を用意しておく。
- **位置対応表は派生物のままとし、形だけを種類つきにする。** 対応表のキーは、根拠と、`extract` の項目の内容のIDと、照合の規則の版とする。読み方を変えると項目の内容のIDが変わり、その文書の位置だけが求め直される。
- **テキスト以外の根拠は、元の文書の座標で指す。** 「このページのこの領域」「この時間帯」は、抽出の仕方によらない座標である。手がかりの種類として後から足す。

### 5.3 変わっていないファイルの判定

変わっていないファイルは、開かず、読み取りもしない。前回と同じオブジェクトIDを、そのまま一覧に載せる。判定は次の順で行う。

1. 大きさと更新日時が前回の観測と同じなら、ファイルを開かずに「変更なし」とする。
2. どちらかが違う場合だけ、ファイルを読んでハッシュを計算する。ハッシュが前回と同じなら「変更なし」とし、読み取りはしない。
3. 前回の観測で、更新日時が走査の開始時刻以降（同じ時刻を含む）だったファイルは、1の近道を使わず、必ず2を行う。日時の刻みが粗いファイルシステムでは、ハッシュを計算した直後の書き換えが同じ更新日時になり、見逃すためである。

観測は、`files` のスナップショットの付箋に置く（4.2節）。更新日時はこの近道にだけ使い、どのIDにも入れない。

## 6 IDの計算

IDは2種類に分ける。実行前に分かる「処理のキー」で既存の結果を引き、実行後に分かる「内容のID」で中身を共有する。

| ID | 何から計算するか | いつ分かるか | 用途 |
| --- | --- | --- | --- |
| 処理のキー | 入力の内容のIDと、処理の識別 | 実行する前 | 「もうあるか」を引く |
| 内容のID | 作ったデータ | 実行した後 | 同じ中身を共有する。下流のキーの材料になる。オブジェクトID、項目ID、一覧のダイジェストがこれに当たる |

### 6.1 処理の識別

処理の識別は、段階の中のモジュールの並びから作る。モジュールごとに次を含める。

| 入れるもの | 入れないもの |
| --- | --- |
| モジュールの名前 | タグ名、スナップショットの名前 |
| 結果に影響する引数（標準値を補った後の値） | 結果に影響しない引数（並行数、制限時間、進捗の表示） |
| 出力互換性バージョン | 依存ライブラリの版そのもの（由来として記録する） |
| モデルの識別（提供元、モデル名、要求パラメーター、秘密でない接続先） | APIキー、環境変数名 |
| 外部ファイルの内容のハッシュ（ユーザー辞書、プロンプト） | そのファイルのパス |
| | 日時、実行ID、ファイルの更新日時 |

引数がどれに当たるかは、モジュールが宣言する。引数の意味を知っているのは、モジュールだけだからである。

| 引数の区分 | 意味 | 使う場面 |
| --- | --- | --- |
| 結果に影響する | 処理の識別に入れる | キーの計算 |
| 結果に影響しない | 処理の識別に入れない。並行数、制限時間、進捗の表示など | キーの計算 |
| 走査だけに関わる | 処理の識別に入れない。結果は `files` の中身に表れる（6.2節） | キーの計算 |
| 秘密 | 値を直接書けない。環境変数の名前だけを受け付ける | 設定の検証 |

- **秘密と宣言した引数に値を直接書いたら、検証で弾く。** 実行の前に弾くので、build は始まらず、その設定ファイルは保管に残らない。
- **保管は、秘密を知らない。** 検証を通った設定ファイルを、原文のまま保存する（4.3節）。伏せる処理は持たない。
- **宣言していない場所に書かれた秘密は、検査しない。** 外部コマンドの引数の文字列や、コメントに書かれた秘密である。Git、Docker、Terraform、CI の設定も同じで、秘密を置く正しい場所を用意し、そこに宣言された値だけを守る。それ以外は利用者の責任とする。
- **今の実装との差。** `models` の `api_key_env` は、設定の検証が決め打ちで調べている（`config_check.rs`）。これを、モジュールとモデルの宣言から調べる形に移す。

### 6.2 スナップショットのキーと項目のキー

キーは、スナップショット単位と項目単位の両方で引けるようにする。2つは、処理の識別の範囲が違う。

| キー | 入力 | 処理の識別の範囲 | 一致したとき |
| --- | --- | --- | --- |
| スナップショットのキー | 入力のスナップショットの、一覧のダイジェスト | 区切りの全モジュール | 段階をまるごと飛ばす。`runs` から引く |
| 項目のキー | 入力のオブジェクト | その項目に実際に適用されるモジュールだけ | その文書は本文を読まずに前の結果を使う。入力のオブジェクトの `results` から、処理のIDで引く |

- **項目のキーは、振り分け先のモジュール単位で作る。** 各モジュールは、どの項目に適用されるか（形式、部品の種類、`match`）を宣言する。OCR のモジュールを足すと、スナップショットのキーは変わるが、Markdown の項目のキーは変わらない。今の実装（受け持つパーサ単位）と仕様 7.2 に合わせる。これは `extract` に限らず、全段階の決まりとする。
- **下流のキーには、上流の中身を使う。** スナップショットのIDは通し番号なので、キーには使わない。一覧のダイジェストを使う。上流の設定を変えても、結果が同じなら、下流は段階ごと飛ばせる。抽出の設定を変えたが本文が変わらなかった文書は、チャンクと埋め込みをそのまま使う。
- **項目のIDは、場所を含めない。** 部品の並び（オブジェクトID、種類、形式、位置、派生元、属性）だけから計算する。同じファイルが別の場所にあっても、同じ項目として共有される。
- **走査だけに関わる引数は、`extracted` の処理の識別に入れない。** `source.filesystem` のパスや除外は、結果が `files` の中身にすでに表れている。入れたままだと、フォルダを移しただけでスナップショットのキーが変わる。モジュールの宣言に「走査だけに関わる」という区分を足す。

**`extract` の段階は、走査してから引く。** 入力を空にすると、フォルダが変わってもキーが同じになり、走査せずに古い結果を返してしまう。そこで、ファイルリストを `files` のスナップショットとして先に作り、それを入力にする（4.4節）。

1. フォルダを走査して、`files` のスナップショットを作る。これはキーで引かず、毎回実行する。中身が前回と同じなら、同じスナップショットが結果になる。
2. `extracted` のスナップショットのキーを、`files` のスナップショットIDと処理の識別から作って引く。一致すれば「変更なし」で終わる。
3. 一致しなければ、ファイルごとに、そのオブジェクトの `results` を、受け持つパーサの処理のIDで引く。足りない分だけを読み取る。

走査を軽くする近道は、5.3節に定める。

### 6.3 同じキーで結果が変わる処理

OCRやモデルを使う処理は、同じキーでも結果が変わり得る。

- 1つのキーに、複数の成功した結果を記録できる。
- 新しい実行は、最新の成功した結果を使う。`--force` を付けたときだけ作り直す。
- 過去のスナップショットは、自分が使った結果の内容のIDを指し続ける。
- 失敗した結果と未完了の結果は、キーで引けないようにする。
- **失敗による代用を含む結果は、キーで引けないようにする。** 実行の記録に `degraded` の印を付け、キーの検索から外す。抽出に失敗した文書に以前の項目を載せた結果は、完了して名前も付くが、キーでは引けない。引けてしまうと、次の `build` が「変更なし」で終わり、ファイルを直すまで失敗した文書を読み直さなくなる。引けなければ、次の `build` は段階を実行し、成功済みの文書はオブジェクトの `results` から引いて、失敗した文書だけを読み直す。OCR やモデルの接続エラーのような一時的な失敗が、次の実行で自然に解消する。
- **代用した文書は、オブジェクトの `results` にも書かない。** 「新しいファイルの中身から、以前の項目へ」という対応は記録しない。記録すると、次の実行が引けてしまい、やはり読み直されない。
- **結果が決まっている除外は、代用に含めない。** 未対応の形式で飛ばした文書は、何度実行しても同じ結果なので、`degraded` にしない。

### 6.4 索引のスナップショット

`index` のスナップショットは、索引ごとの情報オブジェクトを一覧に持つ。文書ごとの項目は持たない。

| | `extracted`、`chunks` | `index` |
| --- | --- | --- |
| 一覧の名前 | 情報源IDと文書ID | 索引の種類。`keyword`、`vector` |
| 一覧が指すもの | 文書の項目 | 索引の情報オブジェクト |

索引の情報オブジェクトは、「何を、どう索引したか」を表す。

```json
{
  "index": "keyword",
  "input": "lst-455195…",
  "modules": [
    { "name": "index.keyword", "compatibility": 1, "args": { "tokenizer": "lindera" } }
  ]
}
```

- **`input`** は、入力にした `chunks` のスナップショットの、一覧のダイジェストである。
- **`modules`** は、索引を作ったモジュールの並びである。モジュールの名前、出力互換性バージョン、結果に影響する引数を持つ。処理の識別（6.1節）と同じ形で、モデルの識別や、辞書の内容のハッシュもここに入る。
- **ほかの段階では、同じ形の情報を実行の記録が持つ（4.3節）。** 索引だけは、一覧にも載せる。索引は、設定が違えば別の物だからである。
- **IDに関わらないことは、付箋に置く。** 依存ライブラリの版、文書数、大きさ、所要時間は、由来として付箋に書く。
- **モジュールや引数を変えると、別の版になる。** 情報オブジェクトのIDが変わり、一覧が変わるためである。文書ごとの項目を載せる形では、トークナイザを変えても一覧が同じになり、設定の違う2つの索引を区別できなかった。
- **文書の一覧は、親が持つ。** どの文書が索引に入っているかは、親の `chunks` のスナップショットで分かる。

差分で更新した索引と、最初から作った索引は、ファイルとしては別物になる。そこで、論理的な中身と物理的な作成物を分ける。

- **索引のディレクトリは、情報オブジェクトの付箋に書く。** この物理的な作成物を、以下「実体化」と呼ぶ。付箋は場所、世代、作った時刻を持つ。失っても作り直せるので、付箋の条件に合う。

  ```json
  { "built": { "location": "indexes/7f3a…", "generation": 2, "built_at": 1795300000000 } }
  ```

- **作り直しても、スナップショットは変わらない。** `--force` で索引を作り直すと、付箋の世代が進む。情報オブジェクトのIDも、スナップショットも変わらない。「確定したものは変えない」という原則と両立する。
- **`serve` は、名前から順に辿る。** 名前、スナップショット、情報オブジェクト、付箋の順に辿って、開くディレクトリを決める。
- **`index` の段階には2つの作業がある。** 項目ごとの変換（埋め込みの計算）と、全項目をまとめた作成（索引の構築）である。埋め込みは、チャンクのオブジェクトの `results` に、埋め込みのモデルごとの結果として覚えさせる案を第一候補とする。段階4で決める。

**キーで引けたが、有効な実体化がない場合がある。** 完全な削除や回収の後に起きる。このときは付箋を消してある。`index` では「引けた」だけで終わらず、付箋があり、その場所にディレクトリがあるかを確かめる。なければ、項目の変換は飛ばして索引だけを作り、付箋を書く。スナップショットは変わらない。

実装は、情報オブジェクトの保存と、オブジェクトの付箋の読み書きまでが済んでいる（`tests/store.rs`）。索引を作る処理そのものは、まだ新しい保管に載せていない。

### 6.5 計算の手順

オブジェクトIDは、バイト列の BLAKE3 そのものである。ほかのツールで計算した値と照合できる。

それ以外のIDは、次の手順で計算する。

1. 値を正規化したJSONにする。キーは文字コード順、整数値は小数点なし、文字列はNFCとする。指数表記の数値は `1.5e+300` の形にする。
2. 形式の版番号と値を並べた `[形式の版番号, 値]` を、ハッシュの対象にする。
3. BLAKE3 を、IDの種類ごとの領域（derive key）で計算する。別の種類の値が同じIDにならないようにするためである。結果の16進表記に、種類の接頭辞を付ける。

固定の入力に対するIDを、テストの値として持つ。出力が変わったのに出力互換性バージョンが同じなら、テストを失敗させる。実装は `src/records.rs` にある。

- **一覧の名前は、文字列の並びにする。** 文書では `[情報源ID, 文書ID]` である。区切り文字でつなぐと、区切り文字を含む名前で取り違えが起きる。一覧は、NFC にした名前の順に並べる。
- **スナップショットのキーには、作る種別も入れる。** 同じ入力と処理から別の種別を作る場合に、キーが重ならないようにする。

### 6.6 IDの一覧

| ID | 接頭辞 | 何を識別するか | 何から決まるか |
| --- | --- | --- | --- |
| オブジェクトID | `obj-` | 中身（バイト列） | バイト列 |
| 項目ID | `itm-` | 1つの文書の、ある段階での中身 | 部品の並び（オブジェクトID、種類、形式、位置、派生元、属性） |
| 情報オブジェクトID | `inf-` | 文書をまたいで作った物の説明 | その JSON。キーの順序によらない |
| 処理のID | `prc-` | 項目に適用するモジュールの並び | モジュールの名前、出力互換性バージョン、結果に影響する引数 |
| 一覧のダイジェスト | `lst-` | スナップショットが持つ中身 | 種別と、名前とIDの組の並び |
| スナップショットのキー | `sky-` | 「この入力にこの処理」という組 | 作る種別、入力の一覧のダイジェスト、区切りの全モジュールの識別 |
| スナップショットID | なし | スナップショットの行 | 通し番号。中身からは決まらない |
| 実行ID | `run-` | 1回の実行 | 開始時に発行する。中身からは決まらない |

一覧のダイジェストまでが「内容のID」で、下から積み上がる。バイト列が変わるとオブジェクトIDが変わり、項目ID、一覧のダイジェストへと伝わる。日時、名前、パス、置き場所、付箋は、どの内容のIDにも入らない。

## 7 完了と日時

スナップショットは、それを作った実行の記録が完了して初めて使える。日時は実行の記録が持ち、未完了の実行の結果は、下流からも名前からも使えない。

### 7.1 extract のファイルリスト

`extract` の段階は、更新情報つきのファイルリストと、それを読み取ったデータを作る。ファイルリストは `files` のスナップショット（4.4節）で、IDを決める部分と、観測として記録する部分に分けて持つ。

| 項目 | 内容 | 置き場所 |
| --- | --- | --- |
| 情報源IDと文書ID | どのフォルダの、どのファイルか | ファイルリスト（IDに入る） |
| 内容のハッシュ | ファイルのバイト列のハッシュ | ファイルリスト（IDに入る） |
| 大きさ、更新日時 | 走査したときの値 | `files` のスナップショットの付箋（4.2節） |
| 追加、更新、削除の件数と検出時刻 | 前回のファイルリストとの差 | 実行の記録 |

- **ファイルリストのIDは、情報源ID、文書ID、内容のハッシュの並びから計算する。** 「ある時点の原文の集合」を表し、`extract` の入力になる（6.2節）。読み方を変えても変わらないので、評価を比べてよいかの基準にも使う（10.4節）。
- **更新日時をIDに入れない。** 中身が同じで日時だけが変わる場面があるためである。フォルダをコピーし直した、`git clone` し直した、バックアップから戻した、という場合に、下流の再利用と評価の比較が崩れないようにする。今の実装は `modifiedAtMs` が段階のIDに入っており、日時だけの変化がビルドのキーまで伝わる（13.1節）。
- **更新日時は利用者に見せる。** 検索結果の出典や `status` には、付箋の更新日時を出す。

### 7.2 完了の決まり

- **すべてそろって初めて完了。** 全部の情報源の走査が成功し、対象の全項目を書き終えたときだけ、実行の記録に完了時刻を入れて `complete` にする。
- **確定は1回のトランザクションで行う。** スナップショットの行、実行の記録、タグの付け替えを同時に書く。この3つは同じデータベース（`records.sqlite`）にある。オブジェクトは別のデータベースに先に書いておく（12.3節）。
- **変更がなかったとき。** `files` の走査は毎回実行し、中身が同じなら `unchanged` になる。その先の段階はキーで引けるので `reused` になる。どちらもスナップショットは増えず、実行の記録だけが残る。「最後に確認した時刻」は、`reused` と `unchanged` の両方を含めた最新の実行の完了時刻である。
- **途中で止まったとき。** 実行の記録が `failed` になる。スナップショットはできない。成功した項目の結果は、入力のオブジェクトの `results` に残っているので、次の実行は続きから進む。利用者が何かを消す必要はない。
- **削除の確定は完了時だけ。** 走査が途中で失敗したら、`files` のスナップショットを作らず、削除を確定しない。
- **走査中に変わったファイル。** 読み終えたときの更新日時が走査の開始時刻以降（同じ時刻を含む）であれば、次回に読み直す印を付箋に付ける（5.3節）。

### 7.3 追加・更新・削除

| 変化 | 一覧での扱い | オブジェクト |
| --- | --- | --- |
| 追加 | 新しい項目を足す | 新しく作る |
| 更新 | 載せるIDが変わる | 新しく作る。古いものは残る |
| 変更なし | 前回と同じIDを載せる | 共有する。本文は読まない |
| 削除 | 一覧に載せない | 残る。過去のスナップショットから参照される |
| 以前の内容に戻す | 以前と同じIDを載せる | 共有する。読み直さない |
| 名前や場所の変更 | 削除と追加として扱う | 内容が同じなら共有する |

2つのスナップショットの差は、一覧を比べれば出る。この比較はどの段階でも同じ処理で済む。

フォルダを以前の内容に戻すと、キーで引ける段階は、以前の版を結果にする。入力の一覧が以前と同じなので、以前の実行のキーが見つかるためである。名前は以前の版へ戻り、履歴には「版1、版2、版1」と残る。`files` はキーで引かないので、同じ中身の新しい行ができる。

### 7.4 安全弁

- **大幅に減ったときは止める。** 前回から文書数が大きく減った場合は、確定せずに止めて確認を求める。空のフォルダが正常に読めた場合は、走査の失敗と区別できないためである。しきい値は15章で決める。
- **更新された文書の抽出に失敗したときは、以前の版を載せて完了する。** 提供を止めないためである。以前の版がない新しい文書は、除外して完了する。どちらも実行の記録に理由を残し、`degraded` にして、`status` に必ず表示する。
- **代用した文書は、次の `build` で必ず読み直す。** `degraded` の結果はキーで引けないようにするので、次の実行は失敗した文書だけを読み直す（6.3節）。壊れたファイルのように何度読んでも失敗する場合の抑制は、15章で決める。

## 8 段階から見た操作

各段階は、6つの操作だけでこのシステムを使う。段階のコードは、表やファイルの置き場所を知らない。

1. **開始する**: 入力のスナップショットIDと、処理の識別を渡す。実行IDが発行され、スナップショットのキーが返る。
2. **引く**: そのキーのスナップショットがあるかを尋ねる。あれば、それを結果として終わる。
3. **書く**: 項目ごとに、まず項目のキーで引く。あれば参照だけを載せる。なければ処理を実行し、部品とオブジェクトを渡す。
4. **閉じる**: 一覧を閉じる。ここで、今の版と同じ中身かどうかが分かる。
5. **まとめて作る**（必要な段階だけ）: 全項目にまたがる作成物を作り、そのスナップショットの実体化として登録する。`index` の索引の構築がこれに当たる。
6. **確定する**: 実行の記録を完了にする。同じIDのスナップショットがすでにあれば、それを結果とする。設定にタグ名があれば、同時に付け替える。

```rust
impl Store {
    pub fn open(directory: &Path) -> StoreResult<Store>;
    pub fn begin(&self, stage: &str, kind: &str, inputs: &[SnapshotId], process: &Process) -> StoreResult<Draft>;
    pub fn begin_scan(&self, stage: &str, kind: &str) -> StoreResult<Draft>;
    pub fn find(&self, key: &SnapshotKey) -> StoreResult<Option<SnapshotId>>;
    pub fn resolve(&self, tag_or_id: &str) -> StoreResult<Option<SnapshotId>>;
    pub fn snapshot(&self, id: SnapshotId) -> StoreResult<Snapshot>;
    pub fn item(&self, id: &ItemId) -> StoreResult<Vec<Part>>;
    pub fn bytes(&self, id: &ObjectId) -> StoreResult<Vec<u8>>;
    pub fn diff(&self, from: SnapshotId, to: SnapshotId) -> StoreResult<Diff>;
    pub fn history(&self, tag: &str) -> StoreResult<Vec<SnapshotId>>;
    pub fn note(&self, id: SnapshotId, name: &str, value: &Value) -> StoreResult<()>;
}

impl Draft {
    pub fn key(&self) -> &SnapshotKey;
    pub fn existing(&self) -> StoreResult<Option<SnapshotId>>;
    pub fn save(&mut self, bytes: &[u8]) -> StoreResult<ObjectId>;
    pub fn list(&mut self, name: ItemName, id: String);
    pub fn result(&self, input: &ObjectId, process: &ProcessId) -> StoreResult<Option<ItemId>>;
    pub fn put(&mut self, name: ItemName, input: &ObjectId, process: &ProcessId, parts: &[Part]) -> StoreResult<ItemId>;
    pub fn substitute(&mut self, name: ItemName, earlier: Option<String>);
    pub fn finish_reused(self, snapshot: SnapshotId, tag: Option<&str>) -> StoreResult<Committed>;
    pub fn commit(self, tag: Option<&str>, previous: Option<SnapshotId>) -> StoreResult<Committed>;
}
```

これは `src/store.rs` の今の形である。「閉じる」と「まとめて作る」は、索引を載せる段階4で足す。

- **途中で捨てると失敗扱いになる。** `commit` を呼ばずに終わった場合、実行の記録が `failed` になる。書き終えたオブジェクトと、その `results` は残る。
- **段階のコードが書くのは2つまで。** 「1項目をどう変換するか」と、必要なら「全項目から何をまとめて作るか」である。`extract` と `transform` は前者だけ、`index` は両方を持つ。キーの計算、引く、閉じる、確定は共通の処理が担う。
- **まとめの作成は、差分を受け取れる。** `base` は、元にできる実体化と、そこからの項目の差（追加、更新、削除）を返す。段階は、差分で更新するか最初から作るかを選び、できたものを `materialize` で登録する。
- **`extract` の段階は、この流れを2回使う。** 1回目で `files` を作り、そのIDを入力にして2回目で `extracted` を作る。`files` のときだけ、「引く」を飛ばして必ず走査する。
- **失敗した文書は `substitute` で載せる。** 以前の項目があればそれを載せ、なければ何も載せない。1件でもあると、実行の記録が `degraded` になり、キーで引けなくなる。
- **文書をまたぐデータは、別の種別のスナップショットにする。** 項目の変換は、その項目と、入力のスナップショットだけを見る。ほかの文書の項目は見ない。全文書から作るデータ（辞書、統計）は、別の種別として作り、入力として受け取る（4.5節）。
- **項目の処理は並行に実行できる。** 項目どうしは独立しているので、rayon で並べられる。一覧の並びは、閉じるときに文書IDの順にそろえる。
- **実行の計画を先に出せる。** `--dry-run` はキーを計算して引くところまでを行い、段階ごとに「再利用」「実行」、文書ごとに「追加」「更新」「削除」を表示する。

## 9 名前と設定ファイル

設定ファイルの区切りごとにタグ名を書き、その名前でデータを指す。段階の区切りは設定ファイルの機能として維持する。

```yaml
extract:
  - source.filesystem: { path: ./docs }
  - loader.auto: { unsupported: error }
  - tag: docs

transform:
  - text.normalize: { unicode: nfkc }
  - chunk.length: { unit: characters, size: 800, overlap: 100 }
  - tag: chunks-800

index:
  - index.keyword: { tokenizer: lindera }    # user_dictionary も指定できる
  - tag: main

serve:
  tag: release
```

区切りは処理の並びである。上から順に実行し、最後の `tag` で結果に名前を付ける。`modules`、`use`、`with` という構造のための語は使わない（9.6節）。

### 9.1 名前

名前（タグ）はスナップショットに付き、どれも動かせる。Git のブランチやタグと同じで、「動く名前」と「動かない名前」の区別は持たない。動かす操作をしなければ、動かないだけである。1つのスナップショットに、名前はいくつでも付く。

名前は、スナップショットの種類ごとに別の棚に置く。種類は、文書（`extracted`）、チャンク（`chunks`）、索引（`index`）、評価データ（`eval-data`）、評価の結果（`eval-report`）である。指すときは「索引の `default`」のように、種類と名前の組で指す。

| 誰が動かすか | 動かす名前 |
| --- | --- |
| 設定ファイルの実行 | 区切りの `tag` に書いた名前。段階が完了するたびに、結果へ付け替える |
| 手での実行 | 各種類の `default`。その実行でできたものへ付け替える |
| 評価データの保存 | 指定した名前と、評価データの `default` |
| 最適化の試行 | 試行の名前（11.2節）だけ。`default` も、基準の名前も動かさない |
| リリース | 提供用の名前（標準は `release`）。索引を指す（10章） |
| `nest tag <名前> <参照>` | 指定した名前。人が明示して付ける |

- **手で実行して最後にできたものに、種類ごとの `default` が付く。** 区切りに `tag` を書いていれば、その名前と `default` の両方が付く。書いていなければ、`default` だけが付く。名前を1つも決めなくても、「最後に作った索引」「最後の評価の結果」を `default` で指せる。
- **何も動かなかった実行でも、`default` は動く。** 結果がキーで見つかって再利用されたときも、その実行が指した結果へ `default` を付け替える。試行の設定ファイルを手で実行すると、その試行の成果物が `default` になる。
- **最適化は `default` を動かさない。** 試行は、最適化が順に実行するもので、人が選んだ結果ではない。最適化の後も、`default` は最適化の前に手で作ったものを指す。
- **同じ名前を、違う種類に付けられる。** 文書、チャンク、索引のどれもが `default` を持ち、試行のチャンク、索引、評価の結果のどれもが同じ試行の名前を持つ。同じ種類の中では、1つの名前は1つのスナップショットを指す。
- **提供用の名前は、タグとは別に持つ。** 索引のタグと同じ名前でも混ざらない。リリースだけが動かし、設定ファイルの実行も `default` の付け替えも動かさない。今どの索引を提供しているかは、リリースの記録の最後の1つである。
- **設定ファイルに書いていない名前は、実行が動かさない（`default` を除く）。** `nest tag` で付けた名前は、もう一度 `nest tag` を実行するまで、同じスナップショットを指し続ける。出発点を固定したいとき、提供する内容を固定したいときは、こうして付けた名前を使う。
- **付け替えの履歴をすべて残す。** いつ、どのスナップショットを指していたかを辿れる。`default` の付け替えも、提供用の名前の付け替えも、実行の記録に残る。
- **記録はIDで持つ。** 評価やリリースの記録は、名前ではなく、実行時に解決したIDを持つ。
- **`eval` の区切りにも `tag` を書ける。** 評価の結果に名前が付く。

### 9.2 設定を変えたのにタグ名が同じとき

文書の更新でタグが動くのは、通常の動作である。処理の設定が変わってタグが動くときは扱いを分ける。判定の決まりは9.5節で定める。

| 場面 | 動き |
| --- | --- |
| 本体の設定ファイルで `build` | 進める。「`chunks-800` の設定が変わった」と表示する |
| `--config` で渡した候補の設定で `build` | 止める。本体のタグを上書きしないよう、別のタグ名を求める |

### 9.3 出発点を固定する書き方（案）

候補の設定は、本体の `extract` のタグが今指すスナップショットにつながる（9.5節）。本体の `build` を実行すると、そのタグは新しい文書へ進むので、試行の出発点も動く。出発点を動かしたくないときは、`nest tag` で名前を付け、モジュールの代わりに参照を書く。設定ファイルの `tag` に書いていない名前なので、`build` は動かさない。

```yaml
extract:
  - from: 2026-11-基準      # 作らずに、この名前のスナップショットを使う
```

これが今の `--input` の役割を引き継ぐ。本体の設定に書けば、フォルダを走査せずに、固定した原文の集合から作り直せる。

### 9.4 開始点の指定

開始点は、段階でもタグでも指定できる。中の仕組みは同じで、入口が2つある。

```sh
nest build --from transform        # 段階で指定。本体の設定の、その段階の手前から
nest build --config candidate.yaml # 候補の設定。変えた区切りから後ろだけが動く
```

開始点より前の処理が設定と食い違うときの扱いは、9.5節の表で決まる。`nest show <タグ>` は、そのスナップショットを最初から再現できる設定の全体を出す。

### 9.5 本体の設定と候補の設定

候補の設定での `build` は、本体のタグを動かさない。判断を2つに分ける。

- **作るか、再利用するか**は、常にキーだけで決める（6章）。タグは関わらない。
- **タグをどう扱うか**は、「タグが今指すスナップショットのキー」と「今回のキー」を比べて決める。スナップショットは入力と処理を持つので、キーはスナップショットから求められる。設定ファイルどうしは比べない。

| タグの状態 | 本体の `build` | 候補の `build` |
| --- | --- | --- |
| タグがない | キーで引き、なければ作る。結果にタグを付ける | 同じ |
| タグがあり、キーが同じ | キーで引く。引ければそのまま。引けなければ（代用を含む結果だった場合）実行し直し、タグを付け替える | 参照として扱う。タグが指すスナップショットをそのまま使い、実行しない。代用を含む場合は警告する |
| タグがあり、キーが違う | 作って、タグを付け替える。処理が違う場合はその旨を表示する | 実行する前に止めて、別のタグ名を求める |

- **本体の `build` では、タグの比較が要らない。** キーで引くか作るかして、結果にタグを付けるだけである。代用を含むスナップショットはキーで引けないので、必ず実行し直され、6.3節のとおり失敗した文書が読み直される。
- **候補の「キーが同じ」は、名前による参照である。** `from` を書いたのと同じ扱いで、キーで引かず、そのスナップショットをそのまま入力にする。失敗した文書の読み直しは本体の `build` の仕事で、候補は行わない。ここで実行し直すと、結果が変わって本体のタグを動かすことになり、読めないファイルが1つあるだけですべての試行が止まる。
- **候補自身のタグが代用を含む場合。** 本体の設定にないタグ名（候補が作ったタグ）は、`--retag` を付けると実行し直して付け替える（案）。付けなければ、参照として扱い、警告だけを出す。

本体と候補の違いは、次の3点である。

| | 本体の設定 | 候補の設定 |
| --- | --- | --- |
| 見分け方 | プロジェクトの `KnowledgeNestfile.yaml` | `--config` で渡した、それ以外のファイル |
| フォルダの走査 | する。新しい `files` を作る | しない。本体の `extract` のタグが今指すスナップショットの `files` を使う |
| 提供用の名前 | `--release` を付けたときだけ動く | 動かない |

この決まりで、次の5つの場面が扱える。

- **下流だけを変えた試行。** `transform` を変えて `chunks-400` とした候補では、`extract` は `docs` が参照として使われ、`transform` から先が新しく作られる。
- **上流を変えた試行。** `extract` だけを変えて `docs-ocr` とした候補では、`transform` の `chunks-800` は入力が違うので「キーが違う」に当たり、止まる。変えた区切りから下は、すべて新しいタグ名が要る。エラーは、名前を変えるべき区切りをすべて挙げる。判定は実行の前に、全区切りについて行う。
- **別の候補が作ったタグを出発点にする試行。** `chunks-400` がすでにあり、キーが同じなら、参照として使う。ここから `index` だけを変えた試行を重ねられる。
- **本体の設定を編集したまま、`build` していない場合。** タグは編集前の処理で作ったスナップショットを指している。それを複製した候補は「キーが違う」で止まり、「先に本体を `build` するか、別のタグ名にする」と案内する。
- **本体に代用した文書がある場合。** 候補は `docs` をそのまま参照して進む。試行どうしは同じ出発点なので比較できる。代用を含むことは、評価レポートにも記録する。

あわせて次が成り立つ。

- **本体のタグは3つそろって動く。** 本体の `build` だけが本体のタグを動かすので、`docs`、`chunks-800`、`main` は常に同じ出発点にそろう。
- **試行は、実行した時点の本体につながる。** 試行の間に文書が更新されても、本体の `build` を実行するまでは出発点が変わらない。本体の `build` の後は、試行のタグが「キーが違う」になる。新しい文書で作り直すには、`--retag` を付けて候補のタグを付け替える（案）。付け替えられるのは、本体の設定にないタグ名だけである。
- **読み方を変える試行は、原本を読む口を使う。** `files` の各ファイルを、フォルダの現物、保存済みの原本、読み取りデータからの復元の順に探して読む（4.4節）。

### 9.6 書き方の決まり

設定ファイルには、構造を示すだけの語を置かない。モジュール名をそのままキーにし、値を引数にする。

| 以前の形 | 新しい形 |
| --- | --- |
| `modules:` の下に並べる | 区切りそのものを並びにする |
| `- use: chunk.length` と `with: { size: 800 }` | `- chunk.length: { size: 800 }` |
| 区切りの `tag: docs` | 並びの最後に `- tag: docs` |
| `user_dictionary: null`、`exclude: []` | 書かない。コメントで存在を示す |

- **並びの1項目は、キーが1つの対応とする。** キーはモジュール名か、`tag` か、`from` である。モジュール名は必ずドットを含むので、取り違えは起きない。
- **順序は並びで表す。** キーを直接並べる形にはしない。YAML ではキーの並びに意味がなく、設定を書き換える道具がキーを並べ替えることがある。ローダーの優先順位が黙って変わるのを防ぐ。
- **同じモジュールを何度でも書ける。** `loader.command` を対象ごとに並べる、複数のフォルダを `source.filesystem` で並べる、という使い方がそのままできる。
- **`tag` は最後に1つ、`from` は先頭に1つ。** それ以外の位置や複数の指定は設定エラーにする。`from` を書いた区切りにはモジュールを書かない。
- **使わないものは書かない。** 「使うものはすべて書き出す」方針は変えない。未設定を表す値（`null`、空の一覧、`none`）は使っていないので、`init` は書き出さず、指定できることをコメントで示す。省いた引数は「使わない」という意味に限り、標準値が黙って補われる引数は引き続き書き出す。
- **字下げの間違いを検出する。** 引数を複数行で書くとき、字下げが浅いと、引数がモジュール名と同じ階層のキーになる。「1つの項目にキーが2つある」場合は、字下げの直し方を示すエラーにする。
- **`search`、`ask`、`eval` の区切りも同じ形にする。** これらはスナップショットを作らないので、`tag` は書かない。`serve` は処理の並びではないので、今の形のままとする。
- **評価の方法は、`eval` の区切りに書く。** `- eval.evidence: { data: default, split: dev }` の形で、評価データの名前と分割を書く。評価だけのための別のファイルは作らない。評価の同じさは、書く場所ではなく、評価の処理の識別で保証する（11.3節）。1つの RAG を複数の評価で測る必要が出たら、定義を別ファイルに出すことを考える。
- **以前の形は受け付けない。** npm への公開前なので、新しい形だけを読む。`use` や `modules` を見つけたら、新しい形での書き方を示すエラーにする。

引数が多いモジュールは、複数行で書ける。

```yaml
search:
  - query.normalize: { unicode: nfkc }
  - retrieval.keyword: { top_k: 10 }
  - context.assemble:
      budget_chars: 4000
      retrieval: fill_budget
      max_candidates: 100
      merge_overlaps: true
      truncate_last: true
      include_headings: true
```

### 9.7 チャンクの文脈

チャンクは、文書から切り出すと、どの文書のどの節にあったかを失う。「2年ごとに交換する」というチャンクは、何の部品の話かを本文に持たないことがある。チャンキングのモジュールの引数 `context` で、この情報をチャンクに持たせ、索引が検索する本文の先頭に付けられる。

```yaml
transform:
  - chunk.structure:
      max_chars: 800
      context: { document: true, headings: true, prepend: true }
```

| 引数 | 意味 |
| --- | --- |
| `headings` | チャンクの最初の行より上にある見出しを、外側から順に、チャンクのメタデータ（`context.headings`）に記録する |
| `document` | 文書の名前を、文脈に含める。`prepend` と一緒にだけ使える |
| `prepend` | 索引が検索する本文の先頭に、文脈を付ける。`manuals/pump.md > ポンプの保守 > 部品` の形の1行である |

- **もとになった手法は、Anthropic の Contextual Retrieval である。** その手法は、文書の全体とチャンクをモデルに渡し、チャンクを文書の中に位置づける短い文を書かせて、埋め込みと BM25 の索引を作る前にチャンクの先頭に付ける。ここにあるのは、モデルを使わず、文書の構造から作る形である。モデルに書かせる形は、モデルを使うモジュールを載せるときに、`context` の種類として足す。
- **検索が返す本文は、文書にあるとおりのチャンクである。** 文脈を付けるのは、索引が検索する本文だけである。位置（行とバイトの範囲）も変わらない。
- **`context` は、チャンキングの処理の識別に入る。** 指定を変えると、チャンクを作り直し、索引も作り直す。指定しないときの識別は、`context` がなかったときと同じである。
- **見出しは `transform` が記録し、先頭に付けるのは `index` が行う。** 見出しは文書の中身だけで決まるが、文書の名前は中身ではない。項目は場所を含めずに共有するので（6.2節）、名前を項目に書き込むと、同じ中身で名前が違う文書が、他方の名前を持ってしまう。`chunks` の部品の属性が「付ける」という指定を持ち、索引は一覧の名前から文書の名前を得る。
- **見出しを読むのは、Markdown の文書だけである。** `#` で始まる見出しを読み、コードブロックの中は読まない。ほかの形式では、見出しの並びは空になる。
- **最適化の軸にできる。** 文脈のありなしで候補を作ると、チャンクと索引は別になり、文書は読み直さない。

## 10 試行、リリース、記録

提供を切り替えるのは、明示したときだけである。作る、評価する、最適化するは、どれも提供を動かさない。文書を足して作り直しても、確かめるまでは前の索引を提供し続ける。

| 操作 | 提供用の名前 | 想定する利用者 |
| --- | --- | --- |
| `nest build` | 動かさない | すべての人 |
| `nest build --release` | 作り終えた索引へ動かす | 作るたびに提供したい人 |
| `nest release <索引>` | 指した索引へ動かす。名前でも版の番号でも指せるので、前の版に戻すのにも使う | 確かめてから提供したい人 |
| 最適化の試行 | 動かさない。試行の設定ファイルには `serve` を書かない | |

- **初めは自動にしていた。** 単なる `build` で提供が切り替わる形を考えていたが、やめた。文書の削除や設定の誤りが、そのまま利用者に届いてしまうからである。作ったものを `list` と `search` と `eval` で確かめてから切り替える流れを、標準にする。
- **一度で済ませたい人は `--release` を付ける。** 簡単に使う人の手間は、オプション1つで済む。

### 10.1 提供に使うもの

- `serve` は、`serve.tag` に書いた提供用の名前が指す `index` のスナップショットの、最新の有効な実体化を提供する。
- 提供用の名前は、索引のタグとは別に持つ（9.1節）。動かすのはリリースだけである。索引を作り直しても、`default` が動いても、提供する内容は変わらない。
- `serve.tag` が書かれていない場合の扱いは、`serve` を新しい保管に載せるときに決める。
- 稼働中の `serve` は、提供に使う実体化が変わると、要求の合間に切り替える。変わるのは2つの場合である。提供用の名前が新しいスナップショットを指したときと、同じスナップショットに新しい世代の実体化ができたとき（`--force`、完全な削除の後）である。`serve.tag` 自体の変更は再起動で反映する。
- 手動でしかリリースしない設定（`release: manual`）は、最初の版では用意しない。

### 10.2 試行

設定ファイルを複製し、変えたい区切りの中身とタグ名を変えると、試行になる。1つの出発点から、複数の結果タグが枝分かれする。

```sh
nest build --config a.yaml      # trial-400
nest build --config b.yaml      # trial-400-dict
nest eval main trial-400 trial-400-dict
nest report compare main trial-400 trial-400-dict
```

試行の後の行き先は、採用だけではない。

| 行き先 | システムの動き |
| --- | --- |
| リリースする | 提供を切り替え、記録を残す |
| さらに最適化する | 試行のタグを出発点にして、次の試行を重ねる。系統は何段でも辿れる |
| データを見直す | 見直す前の結果は残す。新しいデータでの結果とは「比較できない」と区別する |
| 見送る、保留する | 何もしなくてよい。急かす表示は出さない。名前がある限り消さない |

### 10.3 リリースの記録と覚え書き

`release` を明示したときは、次を記録する。自動で取れるものは自動で入れ、人が書くのは理由だけにする。

| 項目 | 取り方 |
| --- | --- |
| 選んだタグとスナップショットのID、置き換えたもの | 自動 |
| 比べた候補（同じ出発点から枝分かれした結果タグ） | 自動。系統から分かる |
| 各候補の評価レポートのIDと主な指標、評価の鮮度 | 自動。評価がなければ「評価なし」 |
| 設定の差 | 自動 |
| 理由 | `--reason`。省略したら「理由なし」と記録する |
| 選んだ人と日時 | `--by` またはOSの利用者名。日時は自動 |

- **`--release` による切り替えも、同じ記録を残す。** `release` と同じく、どの版からどの版へ切り替えたかが残る。
- **覚え書きを残せる。** `nest note <タグ> "..."` で、採用しなかった場合の判断も残せる。系統の表示に出す。
- **記録は消さない。** 元に戻す場合も、「以前のタグを選び直した」という新しい記録を足す。
- **選ぶのは人。** エージェントは候補と結果と推奨を報告するところまでを担う。

### 10.4 系統と比較

```text
docs (11/21 完了, 1,204文書)
├─ chunks-800 ─ main             回収 0.82   ← release（11/15）
└─ chunks-400 ┬ trial-400        回収 0.88   「型番が弱い。辞書を足す」
              └ trial-400-dict   回収 0.93
```

- **比べてよいかは、ファイルリストのIDで判定する。** 系統をたどって同じファイルリストのIDに行き着き、同じ評価データと評価方法で測った結果どうしを、比較できるものとする。初版は「同じ `extract` のスナップショット」としていたが、それでは OCR やローダーの設定を比べる試行が比較できなくなる。原文の集合が同じであることを基準にする。
- **入力が複数あっても、判定は変わらない。** 辞書のような別の種別の入力が違う結果どうしは、原文の集合が同じなら比較できる。辞書の違いは、設定の差として表示する。
- **読み方が違うと、根拠の位置は文書ごとに求め直される。** 位置が決まらなかった根拠は、今の仕様どおり「取りこぼし」として数える。読み方の差がスコアに表れる。
- **文書を更新した後。** `nest build` は、新しいファイルリストに本体の設定の処理を適用し直す。試行のタグは古い出発点に残り、候補の設定で `--retag` を付けて `build` し直せば、新しい文書で作り直せる。変わらない文書の処理は再利用される。
- **試行をリリースしたら、設定を本体へ取り込む（案）。** 取り込まないと、次の `nest build` が古い設定で索引を作る。提供は動かないが、`default` と本体のタグが古い設定の索引を指し、次に `--release` を付けた build で、試行の前の設定に黙って戻る。

## 11 最適化

最適化は、指示に応じた設定ファイルを試行ごとに作り、その設定ファイルを実行する。実行とは、ビルドして、評価することである。10.2節の試行を、人が1つずつ行う代わりに、まとめて行う仕組みである。

保管には、新しい仕組みを足さない。試行の1つ1つは、設定ファイルを指定した実行であり、3つの表と、キーによる再利用をそのまま使う。足すのは、指示から試行の設定ファイルを作る部分と、評価を同じ保管に載せる部分である。テキストの文書、キーワード索引、根拠の回収に限って、実装してある（`src/optimize.rs`、`src/pipeline.rs`、`src/assess.rs`、`src/settings.rs`。14章）。CLI からは `nest store` で使う（11.8節）。この章では、試行と候補を同じ意味で使う。

```text
最適化の指示 ──→ 試行の設定ファイル ──→ build ──→ 評価 ──→ 結果の一覧 ──→ 人が選ぶ
（変えるところ）   （軸の組み合わせ）     （変えた区切り    （同じ評価データ、                （release）
                   連番のファイルに書く    から後ろだけ）     同じ評価方法）
```

### 11.1 最適化の指示

指示は、基準にする設定ファイルと、変えるところと、評価の方法と、上限を書いたファイルである。

```yaml
optimize:
  base: KnowledgeNestfile.yaml
  vary:
    - name: chunking                 # 軸1: チャンクの切り方
      options:
        length:
          transform:
            - text.normalize: { unicode: nfkc }
            - chunk.length: { size: [400, 800], overlap: 100 }
        structure:
          transform:
            - text.normalize: { unicode: nfkc }
            - chunk.structure: { max_chars: [1200, 1600] }
    - name: retrieval                # 軸2: 検索の方式
      options:
        keyword: {}                  # 基準のまま
        hybrid:                      # 2つの区切りを、組で変える
          index:
            - index.keyword: { tokenizer: lindera }
            - index.vector: { model: local-embed }
          search:
            - retrieval.keyword: { top_k: 10 }
            - retrieval.vector: { top_k: 10 }
            - fusion.rrf: {}
            - context.assemble: { budget_chars: 4000 }
  eval:
    data: default                    # 評価データの名前
    metric: recall                   # 並べる基準にする指標
  limit:
    candidates: 20
    minutes: 60
```

- **変えるところの1つ1つを「軸」とする。** 軸は名前と、選択肢の並びを持つ。Knowledge-Nest は、軸ごとに選択肢を1つずつ選んで組み合わせ、候補を作る。上の例では、チャンクが4通り、検索が2通りで、候補は8つになる。
- **選択肢は、区切りをまるごと書き換える。** 中身は設定ファイルの区切りそのもので、書き方は9.6節と同じである。「何番目に足す」「これを消す」といった編集の言葉は作らない。モジュールの入れ替えも、並びの順序も、同じ書き方で表せる。
- **連動する変更は、1つの選択肢にまとめる。** `hybrid` は、索引と検索を組で変える。片方だけを変えた候補は作られない。
- **基準の設定は、必ず評価する。** 候補の0番として、最初に評価する。比べる相手が、同じ評価データと同じ評価方法で測られていることを保証するためである。
- **空の選択肢は「基準のまま」を表す。** どの軸も基準のままの組み合わせは、0番と同じ処理になる。特別には扱わない。結果がすべてキーで引けるので、何も動かずに同じ値が出る。
- **引数の値を配列で書くと、その場で展開する。** `size: [400, 800]` は、選択肢を2つ書いたのと同じである。1つの選択肢に配列が複数あれば、その組み合わせになる。引数だけを変える最適化は、この省略形で書ける。
- **配列を受け取る引数は、配列の配列で書く。** 引数が値を1つ受け取るのか、配列を受け取るのかは、モジュールが宣言する引数の型で決まる。展開するかどうかを、Knowledge-Nest が推測することはない。
- **1つの区切りを、2つの軸が書き換えることはできない。** 設定エラーにする。組み合わせたときに、どちらを使うかが決まらないためである。
- **`tag` と `from` は書かない。** 試行の名前は Knowledge-Nest が付ける（11.2節）。
- **評価の方法は、すべての試行で同じにする。** 基準の設定ファイルの `eval` の区切り（9.6節）を使う。指示の `eval` に評価データや分割を書くと、すべての試行について、まとめて差し替える。選択肢が `eval` を書き換えることはできない。

冗長に見えるが、何を試したかが、指示を読めば分かる。指示は保管に残るので、後から読める形であることに価値がある。

### 11.2 試行の設定ファイル

試行は、基準の設定ファイルに、選んだ選択肢の区切りを差し替えた、1つの完全な設定ファイルである。Knowledge-Nest はそれをファイルに書き、人が書いた設定ファイルと同じように実行する。

```yaml
# .knowledge-nest/trials/chunk-and-search/010.yaml
extract:
  - from: docs
transform:
  - chunk.structure: {"max_chars":200}
  - tag: chunk-and-search/010
index:
  - index.keyword: {"tokenizer":"lindera"}
  - tag: chunk-and-search/010
search:
  - retrieval.keyword: {"top_k":10}
eval:
  - eval.evidence: {"data":"default","split":"dev"}
  - tag: chunk-and-search/010
```

- **ファイルは、連番で作る。** 置き場所は `.knowledge-nest/trials/<最適化の名前>/<番号>.yaml` で、番号は3桁である。0番は基準で、その後は指示の順である。実行しない試行（検証を通らないもの、上限で見送ったもの）のファイルも書く。
- **ファイルを指定して実行すると、その試行をやり直せる。** `nest eval <ファイル>` である。最適化の中の実行と、手での実行は、同じものである。うまくいかない試行を、1つだけ調べられる。
- **同じ内容を、保管にも残す。** ファイルは後で書き換えたり消したりできる。「この結果はこの設定で作った」は、実行の記録の `config` が指すオブジェクトが示す（11.4節）。
- **試行の名前は、軸と選択肢から決まる。** 例: `chunking=length(size=400),retrieval=hybrid`。展開した引数は、括弧の中に書く。
- **`extract` は、基準の文書の名前から始める。** `from` に、基準の `extract` のタグを書く（9.4節）。基準がタグを書いていなければ、`default` を書く。フォルダを走査しないので、すべての試行が同じ文書から出発する。
- **試行の名前は1つである。** `<最適化の名前>/<番号>` で、チャンクにも、索引にも、評価の結果にも、同じ名前を付ける。名前は種類ごとに別の棚にあるので、混ざらない（9.1節）。
- **書き換えた区切りと、その後ろの区切りに、試行の名前を付ける。** `transform` を書き換えた試行はチャンクと索引に、`index` だけを書き換えた試行は索引にだけ付く。どの成果物がどの試行のものかを、名前で辿れる。
- **評価の結果には、どの試行でも名前を付ける。** 試行は必ず評価をするので、結果は必ず `<最適化の名前>/<番号>` で指せる。
- **書き換えていない区切りは、モジュールを残して、タグを外す。** 基準と同じ処理なので、キーで引けて、実行しない。タグがないので、基準の名前は動かない。
- **`search` だけを変えた試行は、評価の結果にだけ名前を持つ。** 基準の索引をそのまま使い、評価だけが動く。
- **試行は `default` を動かさない。** 最適化の後も、各種類の `default` は、手で最後に作ったものを指す（9.1節）。
- **同じ成果物を使う試行が複数あると、その成果物に名前が複数付く。** チャンクの切り方が同じで検索だけが違う2つの試行は、同じチャンクと同じ索引を、それぞれの番号の名前で指す。
- **`serve` は書かない。** 試行は、提供中の名前を動かさない。
- **実行の前に、すべての試行を検証する。** 組み合わせの中には、動かないものが出る。たとえば、ベクトル索引を作らないのに、ベクトル検索を使う設定である。`validate` と同じ検査である。
- **通らない試行は、実行せずに理由を記録する。** 最適化は止めずに、次の試行へ進む。指示そのものの誤り（知らないモジュール、同じ区切りを書き換える2つの軸）は、最初に止める。
- **同じ設定になった試行を、特別には扱わない。** 書き方が違っても、処理が同じならキーが同じなので、後の試行は何も動かずに同じ結果になる。

モジュールを変えることは、保管から見ると、処理の識別が変わることである。引数を変えるのと区別がない。

| 変えたところ | 動くもの |
| --- | --- |
| `search` だけ | 評価だけ。build は要らない |
| `index` | 索引の作成と、評価 |
| `transform` | チャンク化、索引の作成、評価。読み取りは再利用する |
| `extract` | すべて。ただし項目の再利用は、適用されるモジュールごとに効く（6.2節）。PDF 用のローダーを足しても、Markdown の文書は読み直さない |

試行どうしも、途中までが同じなら、そこまでを共有する。上の例で、`length(size=400)` のチャンクは1回だけ作られ、`keyword` と `hybrid` の2つの候補が使う。

### 11.3 評価を同じ保管に載せる

候補を比べるには、評価も「同じ入力と同じ処理は、1回しか実行しない」に従う必要がある。評価データと評価の結果を、種別の1つとして載せる（4.5節）。

| 種別 | `items` の名前 | 親 | 作り方 |
| --- | --- | --- | --- |
| `eval-data` | 評価ケースのID | なし | 毎回読んで作る。同じ中身なら、前の版を結果にする |
| `eval-report` | 評価ケースのID | `index` と `eval-data` | キーで引き、なければ評価を実行する |

- **評価ケースは、オブジェクトである。** 質問、正解の文書と引用、調整用か最終確認用かの分割を持つ。ケースを足すと、評価データの新しい版ができ、差として「どのケースを足したか」が出る。
- **評価のキーは、今のキーの計算で作れる。** 入力は、索引と評価データの一覧のダイジェストである。処理は、`search` の区切りのモジュールの並びと、採点の方法と、使った分割である。採点は、モジュールと同じ形の識別（`eval.evidence`）として、並びの最後に入れる。検索設定はビルドに含めず、評価が「スナップショットと検索設定の組」を記録する（未決事項12）という決まりと、同じ形になる。
- **ケースごとの結果を、項目として持つ。** 返った根拠、回収できたか、順位を持つ。2つのレポートの差は、一覧の比較で出る。「どの質問が良くなり、どの質問が悪くなったか」が、文書の追加・更新と同じ仕組みで分かる。
- **所要時間は、項目に入れない。** 実行のたびに変わるので、入れると同じ結果が別の版になる。`runs` の `stats` に置く。集計した指標も、項目から計算できるので、`stats` に置く。
- **同じ候補を2度評価しない。** 索引も、評価データも、検索設定も同じなら、キーで引ける。最適化をやり直したときも、指示に選択肢を足したときも、済んだ候補は実行されない。
- **根拠の位置は、今の決まりのままである。** 正本は「文書と引用」で、位置は照合で求める（13.1節）。チャンクの切り方を変えた候補でも、同じ評価データで測れる。

### 11.4 記録

最適化そのものも、`runs` の1行にする。新しい表は作らない。

| 記録するもの | 置き場所 |
| --- | --- |
| 最適化の指示 | オブジェクト。最適化の行の `config` が指す |
| 基準の設定ファイル | オブジェクト。指示とともに、最適化の行の `stats` が指す |
| 候補の設定ファイル | オブジェクト。候補の build と評価の行の `config` が指す |
| 候補の作り方 | 候補の各行の `info`（4.3節）。今と同じである |
| 試行の一覧（番号、名前、軸の選択、ファイルの場所、状態と理由、動いた段階、タグ、索引とレポート、回収、所要時間） | 最適化の行の `stats` |
| どの最適化が起こした実行か | 候補の各行の `cause`。最適化の行の実行IDを書く |

- **`runs` に `cause` を足す。** 候補の build と評価の行が、自分を起こした最適化の実行IDを持つ。子の行にだけ書く。最適化の行に、後から子の一覧を書き足すことはしない（スナップショットが親を子の側にだけ書く、4.2節の決まりと同じである）。人が実行した `build` では、空である。
- **最適化の行は、キーで引かない。** `stage` は `optimize` で、スナップショットを作らない。`snapshot` と `outcome` は空である。再利用は、候補の build と評価の1つ1つで効く。
- **失敗した試行は飛ばす。** 試行の実行が失敗したら、理由を一覧に記録して、次の試行へ進む。失敗した段階の実行は、`failed` の行として残る。この行も、`cause` と `config` を持つ。
- **続けて3回失敗したら、残りを実行しない。** どの試行でも失敗するのは、試行のせいではなく、環境のせいである（ディスクの空き、鍵、保管の破損）。残りは「実行していない」と記録する。成功が1回入れば、数え直す。
- **失敗は、悪い結果として扱わない。** 回収の値を持たない。値の選び方に「この設定は悪い」と伝わるのを防ぐ。
- **途中で止まっても、続きから進む。** 同じ指示でもう一度実行すると、済んだ候補はキーで引け、残りだけが動く。新しい行ができ、前の行は `failed` のまま残る。
- **見送った候補も残る。** 検証を通らなかった候補、上限で実行しなかった候補は、理由とともに一覧に残る。「試していない」と「試して悪かった」を区別できる。

### 11.5 進み具合と上限

実行の前の見積もりは出さない。次に試す値を前の結果から決める探索（11.7節）では、見積もる相手が先に決まらないためである。代わりに、進み具合を見えるようにする。

- **進み具合は、3つの出来事で伝える。** 試行の開始（何番目か、全部でいくつか、名前）、段階の開始と終わり（作った、再利用した、変わらなかった）、試行の終わり（回収と MRR の値、または失敗の理由）である。CLI は、これを標準エラーに1行ずつ出す。
- **最適化の行にも、途中経過を書く。** 試行が1つ終わるたびに、試行の一覧を `stats` に書く。別の端末から `nest results <最適化の名前>` で、実行中の最適化を見られる。実行が終わると、最後の一覧が残る。
- **上限は、試行の数だけである。** 指示の `limit.candidates` で、基準のほかに実行する試行の数を決める。基準の0番は、数に入れない。時間と、モデルへの要求の数の上限は、まだない。
- **総当たりでは、上限を超える分は実行しない。** 指示の順に実行し、残りは一覧に残す。上限を上げてもう一度実行すると、済んだ試行はキーで引け、残りだけが動く。
- **選ぶ探し方（11.7節）では、上限が試行の数そのものになる。** 上限は必ず書く。続けて3回失敗したら、そこで止め、止めた理由を表に出す。

### 11.6 結果と選択

```text
最適化 chunk-and-retrieval（11/22、8候補、評価データ default 調整用 120件）

  候補                                              回収    基準との差   動いた区切り
  chunking=length(size=400),retrieval=hybrid        0.93   +0.11        transform, index
  chunking=structure(max_chars=1200),retrieval=...  0.91   +0.09        transform, index
  chunking=length(size=400),retrieval=keyword       0.88   +0.06        transform, index
  chunking=length(size=800),retrieval=keyword       0.82    基準         なし
  chunking=structure(max_chars=1600),retrieval=...  ―      検証で不可: local-embed がない
```

- **結果は、表で出す。** 評価できた試行を回収の高い順に並べ、回収が同じなら MRR の高い順にする。基準との差、動いた段階、所要時間を出す。評価できなかった試行は、その後に、状態と理由を付けて並べる。実装した表は、番号、回収、MRR、基準との差、動いた段階、所要時間、名前の列を持つ。
- **候補どうしは、必ず比較できる。** 同じ文書、同じ評価データ、同じ採点の方法で測るので、10.4節の条件を満たす。
- **並べる基準は、回収、次に MRR とする。** MRR（平均逆順位）は、根拠が1位なら1、2位なら0.5、3位なら0.33、外れなら0として、ケースの平均を取ったものである。評価の結果に保存してある順位から求めるので、保管の形は変わらない。質問が少ないと回収はすぐに同点になり、同点ばかりでは、次の試行を結果から選ぶ探し方（11.7節）が何も学べない。MRR は、同じ回収の中で「根拠を上に出せる設定」を見分ける。重みを付けて1つの値にまとめることはしない。重みの決め方という別の問題を持ち込むからである。速さ、索引の大きさ、モデルへの要求の数は、並べて表示するだけで、順位には使わない。
- **調整用の分割だけを使う。** 最終確認用は、選んだ候補を確かめるときに、人が明示して使う。今の決まりのままである。
- **選ぶのは人である。** 最適化は、提供中の名前を動かさない。結果の一覧と、ケースごとの差を示すところまでを担う。採用は `nest release <候補のタグ>` で行い、10.3節の記録が残る。比べた候補と評価は、`cause` から自動で入る。
- **`search` だけを変えた候補を採用するとき。** 索引は基準と同じなので、動かすタグがない。採用は、候補の設定を本体へ取り込むことである（未決事項3）。
- **次の最適化へ続けられる。** 選んだ候補の設定ファイルを `base` にして、別の軸を変える。前の最適化で作ったチャンクと索引は、キーで引ける。

### 11.7 指示を誰が書くか

指示は、人が書いても、エージェントが書いてもよい。Knowledge-Nest が受け取るのは、11.1節の形だけとする（案）。

- **言葉での依頼は、指示を書く層が受ける。** 「型番の質問に弱いので直したい」という依頼から、エージェントが評価レポートと辞書の提案を読み、指示を書く。Knowledge-Nest は、その指示を検証して実行する。
- **こうすると、試したことが必ず読める形で残る。** 言葉の依頼だけが残ると、何を試したかを後から確かめられない。
- **探し方は3つある。** 指示の `search` で選ぶ。

| `search` | 試行の決め方 | 向く場面 |
| --- | --- | --- |
| `grid`（既定） | すべての組み合わせを、指示の順に作る | 組み合わせが十数個まで。漏れがなく、読みやすい |
| `random` | 上限の数だけ、ランダムに1つずつ選ぶ | 組み合わせが多すぎるとき。TPE と比べる基準 |
| `tpe` | 初めの数回はランダム、その後は、それまでの結果から1つずつ選ぶ | 範囲で探す値があり、試行が20回以上のとき |

- **範囲は `{ int: [下限, 上限] }` と書く。** 上限と下限を含む整数である。`log: true` を付けると、対数の目盛りで均等に試す。チャンクの大きさのように、100と200の差が800と1600の差と同じくらい効く値に向く。範囲は `random` と `tpe` だけで使え、`grid` では断る。
- **選ぶ探し方では、値の並びと選択肢も「どれかを選ぶ」値になる。** 軸の選択肢が1つの値、選択肢の中の並びや範囲がそれぞれ1つの値である。選択肢の中の値は、その選択肢を選んだ試行でだけ使う（条件つきの値）。
- **TPE は、Knowledge-Nest の中に持つ。** 試行を良い組（上位4分の1）とそれ以外に分け、値ごとに、良い組での出やすさと、それ以外での出やすさを作る。良い組から候補を24個引き、「良い組で出やすく、それ以外で出にくい」ものを次の値にする。条件つきの値は、その値を使った試行だけで数える。初めの試行（上限の3分の1、3以上10以下）はランダムに選ぶ。失敗した試行と、検証で不可だった試行は、いちばん悪い結果として数える。
- **ライブラリを使わずに書いた。** 要るのは、整数、選択肢、条件つき、数十回までの範囲だけで、数百行で済む。そして、同じ指示と同じ種（`seed`）なら、どの版でも同じ試行の並びになってほしい。そうすれば、作った成果物がキーで引け、もう一度実行しても何も動かない。ライブラリや乱数の部品の版が上がると、提案が黙って変わりうる。乱数も中に持つ（SplitMix64）。
- **同じ試行は、引き直す。** 選んだ値が、前の試行と同じ設定になったら、20回まで引き直す。キーで引けるので結果は同じだが、上限の数を無駄に使うからである。
- **確かめ方。** 答えの分かっている作り物の問題で、TPE がランダムより良い値に近づくこと、良い選択肢を多く選ぶことを、種を変えて40回ずつ確かめる。整数では最良の値までの距離が約6分の1、選択肢では良いものを選ぶ回数が約5倍だった。
- **もっと難しい探し方は、外から動かす。** 複数の指標を同時に最適化する、ガウス過程やCMA-ESを使う、などである。試行は「設定ファイルを `nest eval` で実行して結果を返す」ものなので、Optuna などから1つずつ呼べる。中には持たない。

### 11.8 コマンド

新しい保管のコマンドは、ほかのコマンドと同じ最上位に置く。`nest store` という入れ物は持たない。プロジェクトの保管は `.knowledge-nest/store`、索引は `.knowledge-nest/indexes` である。

| コマンド | すること |
| --- | --- |
| `nest build [<設定ファイル>] [--release]` | 設定ファイルのとおりに、extract、transform、index を実行する。`eval` の区切りがあっても、評価はしない。できたものに、種類ごとの `default` を付ける。`--release` を付けると、`serve` の名前で索引を提供用にする |
| `nest eval [<設定ファイル>]` | `eval` の区切りのとおりに評価する。索引がまだなければ、先に build と同じことをする。`eval` の区切りがない設定は断る |
| `nest list [documents\|chunks\|indexes\|eval-data\|results]` | 名前の付いた版を、種類ごとに並べる。版の番号、作った日時、件数、元にした版を出す。索引には、提供用の名前を添える。評価の結果は、回収の高い順に並べる |
| `nest search <質問> [--index <索引>] [--limit <件数>]` | 索引を検索して、見つかったチャンクの場所と最初の行を出す。索引は名前か版の番号で指す。省くと `default`、件数は5 |
| `nest release <索引> [--name <提供用の名前>]` | 既にある索引を提供用にする。索引は名前か版の番号で指すので、前の版に戻すのにも使う。提供用の名前を省くと `release` |
| `nest eval-data import <ファイル> [--tag <名前>]` | 評価ケースの JSON を、評価データとして保存する。指定した名前と `default` を付ける。名前を省くと `default` だけになる |
| `nest optimize <指示> [--name <名前>]` | 最適化を実行する。名前の既定は、指示のファイル名（拡張子を除く） |
| `nest results [<名前>]` | 評価の結果を見る。名前を省くと、名前の付いた結果を回収の高い順に並べ、最適化の名前を添える。結果の名前を渡すと、その評価のケースごとに、根拠が何番目に返ったかを出す。外したケースを先に並べる。最適化の名前を渡すと、その最適化の試行の表を出す。実行中のものは、途中までを出す |

`build`、`eval`、`search`、`eval-data` は、今までの保管にも同じ名前のコマンドがある。どちらで動くかは、設定ファイルの書き方で決める。

- **区切りが処理の並びなら、新しい保管で動く。** `extract`、`transform`、`index` のどれかが、モジュールの並び（9.6節の書き方）になっている設定ファイルである。
- **それ以外は、今までどおりに動く。** 今までの `KnowledgeNestfile.yaml` のプロジェクトは、何も変わらない。
- **読む設定ファイルは、今までと同じ順で決める。** `build` と `eval` は引数、`--config`、プロジェクトの `KnowledgeNestfile.yaml` の順である。`search` と `eval-data` は `--config`、`KnowledgeNestfile.yaml` の順である。引数なしの `nest build` や `nest search "質問"` が、そのまま使える。
- **`list`、`release`、`optimize`、`results` は、新しい保管だけのコマンドである。** 設定ファイルを見ない。
- **今までの保管だけが持つオプションは、新しい保管では断る。** `build` の `--from`、`--until`、`--force`、`--input`、`--dry-run`、`--skip-unsupported`、`--tag`、`eval` の `--build`、`--split`、`--tag`、`search` の `--budget-chars`、`--source-id` である。黙って無視はしない。
- **引数に渡した設定ファイルが今までの書き方なら、断る。** 今までの `build` は、設定ファイルを引数に取らないからである。
- **今までの保管をやめるときは、この分岐を消す。**
- **`validate` と `status` も、設定ファイルの書き方で分かれる。** 新しい書き方なら、`validate` は build と同じ検査だけをして何も作らず、`status` は `list` と同じものを出す。
- **`search` の `--index` は、提供用の名前も受ける。** 索引の名前、版の番号、提供用の名前の順に探す。`--index release` で、今提供しているものを検索できる。
- **評価の結果は、名前がなくても一覧に出す。** 評価し直すと `default` は新しい結果へ移るが、前の結果は版の番号で残り、`nest results <番号>` で読める。前と比べるためである。
- **新しい書き方は、ヘルプで説明する。** `nest init` はこの書き方を作らないので、`build`、`eval`、`eval-data`、`optimize` などの `--help` に、設定ファイルと指示の例、使えるモジュールを載せる。
- **Windows で索引のパスが長すぎるときは、作る前に断る。** 索引の中のデータベースは、260文字以上のパスを開けない。作り始めてから失敗すると原因が分からないので、先に長さを数えて、プロジェクトを短いパスへ移すよう伝える。失敗した試みが残したフォルダは、次の実行の前に消す。

- **`build` と `eval` は、文書の増減を出す。** 走査で見つけた追加、更新、削除、変わらなかった文書の件数と、その文書の名前（多いときは最初の10件）である。`apply` で取り込まなかった変更と、ローダーが扱えなかったファイルも、分けて出す。チャンクを作り直した文書の数も出す。
- **評価に要るものは、build の前に確かめる。** `eval` の区切りが指す評価データがなければ、何も作らずに止める。
- **最適化の表は、どの文書で測ったかを出す。** 試行はフォルダを走査せず、同じ版の文書から始める（11.2節）。コーパスを固定するのは、試行の差を設定の差だけにするためである。文書を増やした後で測り直すには、先に基準を作り直す。
- **進み具合は標準エラーに、結果は標準出力に出す。** `--json` を付けると、結果を1つの JSON にする。
- **設定ファイルの中の相対パスは、プロジェクトのフォルダから数える。** 試行のファイルが `.knowledge-nest/trials` の下にあっても、`./docs` はプロジェクトの `docs` を指す。

## 12 回収、完全な削除、同時実行

消すかどうかは、「名前から辿れるか」という1つの規則で決める。

### 12.1 回収

- **残すもの**: 名前が付いているスナップショット。そこから親をたどって届くスナップショット（`files` まで）。評価レポートとリリースの記録が参照するスナップショット。それらの一覧が指すオブジェクトと、項目の部品が指すオブジェクト。最新の有効な実体化。
- **消せるもの**: 上のどれからも辿れないスナップショットとオブジェクト。古い世代の実体化。失敗した実行が残した、参照されないオブジェクト。
- **最初の版では自動で回収しない。** `status` で容量を示し、「名前が指す分」「辿れない分」を分けて表示する。回収は `nest gc` で明示して実行する。
- **直近の分は猶予を置く。** タグが動いた直後の古いスナップショットと実体化は、一定の期間は消さない。稼働中の `serve` がまだ開いている可能性があるためである。
- **回収の範囲はプロジェクトの中である。** オブジェクト、記録、名前はすべてプロジェクトの `.knowledge-nest/` の下にあり、ほかのプロジェクトとは共用しない（13.1節で確認済み）。Wiki/PARA と共有する原本は、Wiki/PARA 側の参照も数える。

### 12.2 完全な削除

誤って置いた資料や、公開してはいけない資料を消す操作である。フォルダから削除しただけでは、過去のスナップショットと索引に残る。

- `nest purge <文書ID>` は、その文書の項目を「完全に削除した」状態にし、ほかから参照されなくなったオブジェクトを消す。
- **原本も、同じ操作で消える。** テキストの原本は本文と同じオブジェクトで、PDF などの原本もオブジェクトである。走査の観測は `files` の付箋にあり、文書の中身を含まない。
- **同じ中身を別の文書が共有している場合。** オブジェクトは内容で共有されるので、同じ内容のファイルが別の文書IDでも載っていると、オブジェクトは残る。実行前に「同じ内容を持つ文書」を一覧で示し、それらも対象にするかを選ばせる。対象にしなかった場合は、オブジェクトが残ることを結果に表示する。
- **ファイルがフォルダに残っている場合は、実行前に警告する。** 残したままだと、次の `build` がその文書を読み直して、元に戻る。
- **その文書を含む索引の実体化を無効にする。** 情報オブジェクトの付箋を消し、ディレクトリを消す。 タグが指しているスナップショットの分は、その文書を除いて作り直す。
- **スナップショットの記録とIDは変えない。** 「完全に削除した項目」の表を別に持ち、読む側がその項目を飛ばす。
- 実行前に、影響するスナップショット、タグ、評価ケースの件数を表示して確認を求める。

### 12.3 同時実行と障害

- **書き込みはプロジェクトに1つ。** `build` はプロジェクト単位のロックを取る。取れないときは、待たずに「別のビルドが実行中」と伝えて終わる。
- **読み取りはロックしない。** `search`、`serve`、`eval` は完了済みのスナップショットだけを読むので、ビルドの途中でも動く。
- **オブジェクトを先に書き、記録を後に書く。** 記録が指すオブジェクトは必ず存在する。途中で止まると、参照されないオブジェクトが残るだけで、回収の対象になる。
- **起動時に片付ける。** ロックを持ったまま異常終了した実行の `building` は、次の `build` が `failed` に変える。
- **索引は別の場所に作り、完成してから指す。** 今の実装と同じである。変わらないセグメントはハードリンクで共有する。

## 13 現在の実装との対応と移行

考え方はすでに実装に入っていて、作業の中心は「段階ごとに違う記録の形を、1つにそろえること」になる。以下はコミット `73ac628` のコードを読んだ内容で、実行しての確認はしていない。

| この設計 | 今の実装 | 差 |
| --- | --- | --- |
| 項目のキー（抽出） | `state.sqlite` の `extractions`。入力のハッシュと抽出設定から、コーパスの版を引く | 近い |
| 項目のキー（チャンク） | `corpus.sqlite` の `version_chunkings` と `chunkings` | 近い |
| オブジェクト（チャンク、埋め込み） | `chunk_sets`（IDはチャンクのJSONの SHA-256）、`embeddings` | 近い |
| オブジェクト（読み取りデータ） | `corpus.sqlite` の `revisions`。1版につき本文1本（`content`）と形式と位置 | 部品の並びになっていない |
| 位置 | 行の範囲とバイトの範囲。抽出時の位置には、ページと領域（`page`、`bbox`）を持てる | 種類つきの形にはなっていない。土台はある |
| スナップショットの記録 | `stage_outputs`（段階、ID、内容）。内容の形は段階ごとに違う | 形がそろっていない |
| スナップショットのキー | `transform_outputs`、`index_outputs`（キーから出力を引く） | 段階ごとに別の表 |
| 完了時刻 | `source_checks` の確認時刻、`build_runs` の作成時刻 | スナップショットごとの開始・完了時刻は見当たらない |
| タグ | `build_tags`、`tag_history`。ビルドにだけ付く | `extract` と `transform` には付けられない |
| リリース | `project.build_id`、`adoption_history`、`serving_generations` | タグとしては表されていない。理由や候補の記録はない |

### 13.1 確かめたこと

レビューでコードと照合した結果は、次のとおりだった。段階0は済んだものとする。

| 点 | 結果 | この設計での扱い |
| --- | --- | --- |
| 更新日時がIDに入っているか | 入っている。`source_entry` が `modifiedAtMs` を一覧に入れ（`stage_store.rs`）、その一覧から `src-` のIDを作る（`source_stage.rs`）。`transform` のIDとビルドのキーまで伝わる | ファイルリストの中身から外し、付箋に移す（5.3節） |
| 評価の根拠が何を指すか | 「文書と引用」が正本。位置は照合で求め、`evidence_positions` と `evidence_maps` に派生物として持つ | 正本は変えない。手がかりと位置の形だけを種類つきにする（5.2節） |
| 版の識別子にURLが入っているか | 入っている。ただし手前で、場所を含まない `parsed_version` を計算している（`source.rs`） | `parsed_version` を項目の内容のIDの土台にする（6.2節） |
| 置き場所の共用の範囲 | プロジェクトに閉じている。`state.sqlite`、コーパス、原本はすべてプロジェクトの `.knowledge-nest/` の下にある（`cli_project.rs`）。「共有」は、ビルドの間と、Wiki/PARA との間の共有である | 12.1節の前提がそのまま成り立つ |
| テキストの原本を読み直せるか | 読み直せる。テキストは読んだバイト列を UTF-8 として検証し、そのまま本文にしている（`source_load.rs`）。仕様 28.14 も、復元したバイト列の SHA-256 が記録と一致するとしている | 原本を読む口を新しく作る（4.4節）。今はその口がない |

### 13.2 移行の選択

| 案 | 内容 | 向き |
| --- | --- | --- |
| 一度だけ作り直す | 形式が古いプロジェクトは、次の `build` で最初から作る。評価データと設定は残す | 軽い。npm に公開する前なら選べる |
| 記録を変換する | 今の表から新しい記録を組み立てる。ビルドIDは変わるが、処理はやり直さない | 中くらい |
| IDを保って変換する | 今のビルドIDと評価レポートの対応を保つ | 重い。IDの計算を変える以上、完全には保てない |

公開前なので、「一度だけ作り直す」に決める。保存体系を新規に作る（13.3節）ので、今の表を変換する案は取らない。古い評価レポートは読めるまま残し、新しいビルドとは「比較できない」と表示する。

### 13.3 保存体系は新規に作る

データの保存体系は、今の表を引き継がず、完全に新しく作る。今の `corpus.sqlite` の `revisions`、`chunk_sets`、`chunkings`、`version_chunkings` と、`state.sqlite` の `extractions`、`stage_outputs`、`transform_outputs`、`index_outputs`、`embeddings`、ビルドとタグの表は、新しい保管に置き換える。

| 置くもの | 置き場所 | 理由 |
| --- | --- | --- |
| `objects` | `.knowledge-nest/store/objects.sqlite` | 構築中に大きな書き込みが続く。記録の短い更新を待たせない（仕様 28.14 と同じ理由） |
| `snapshots`、`runs` | `.knowledge-nest/store/records.sqlite` | 確定を1回のトランザクションで行うため、1つのデータベースにまとめる（7.2節） |
| 評価データ、評価レポート | 今の `state.sqlite` のまま。段階8で、種別 `eval-data` と `eval-report` として新しい保管に載せる（11.3節） | 最適化が、評価の再利用と、ケースごとの差を必要とする |
| 根拠の位置対応、Wiki/PARA の状態 | 今の `state.sqlite` のまま | この設計の範囲外。スナップショットのIDを参照するだけである |

表の形は4章に定める。

- **今の形に縛られない。** 記録の形とIDの計算を、既存の表との互換を考えずに決められる。段階1と2を、Knowledge-Nest のほかの部分に触れずに作れる。
- **移行の間は、新旧が並ぶ。** 段階3と4で、段階を1つずつ新しい保管へ載せ替える。載せ替えが済んだ表から消す。Wiki/PARA は、未決事項13で載せるまで、今のコーパスと原本を使い続ける。
- **読む側も載せ替える。** 検索、文脈の組み立て、評価は、今はコーパスの版から本文と位置を読んでいる。これらをオブジェクトから読む口に替える。Node.js API の `KnowledgeNest.open` が単独の索引に作るコーパス（`.knowledge-nest-corpus-v1`）の扱いも、段階4で決める。
- **速さを最初に測る。** 新しい保管だけで、Markdown 1万件ぶんの書き込みと、変更なしの確認にかかる時間を測る。段階2の受け入れ条件にする（14章）。
- **古い保管は、利用者が消さなくてよい。** 新しい形式で最初に `build` したとき、古い表とファイルが残っていれば、作り直した後に消す。評価データと設定は残す。

段階2から4は、テキストの文書とキーワード索引に限って、先に通してある。CLI にはつないでいない。`tests/rag.rs` が、次の流れを確かめる。

3. 何も変えずに実行する。ファイルを開かず、チャンク化も索引の作成もしない。
4. チャンクの大きさだけを変えた試行を実行する。文書は読み直さず、チャンク化と索引だけが動く。提供中の名前は動かない。

`tests/optimize.rs` は、最適化（段階8）を確かめる。プロジェクトの最初の build も、設定ファイルの実行で行う。

1. 最適化を実行する。チャンクの切り方（基準のまま、`chunk.length` の2つの大きさ、`chunk.structure`）と、検索（10件、1件、ベクトルとの併用）の組み合わせで、基準と合わせて試行が13できる。
2. 進み具合が、試行、段階、結果の順に伝わる。
3. 基準と、検索だけを変えた試行は、build が動かず、評価だけが動く。切り方が同じ2つの試行は、チャンクと索引を1回だけ作り、同じ成果物にそれぞれの試行の名前が付く。試行の名前は、チャンク、索引、評価の結果で同じである。モジュールを替えた試行も、文書は読み直さない。
4. 試行の設定ファイルが、連番で `.knowledge-nest/trials` の下にできる。そのファイルを手で実行すると、同じ結果が、何も動かずに出る。その試行の索引と評価の結果が、`default` になる。
5. ベクトル索引を使う4つの試行は、build の前に、理由とともに外れる。ファイルは書かれる。
6. 最初の build の後、文書、チャンク、索引、評価データのそれぞれに `default` が付いている。最適化の後も、提供中の名前、基準のタグ、各種類の `default` は動かない。最適化の行が指示と試行の一覧を持ち、試行の実行が `cause` でそれを指す。
7. 結果の表が、回収の高い順に出る。評価できなかった試行は、理由とともに後ろに並ぶ。
8. 同じ指示をもう一度実行すると、何も実行されない。上限で残した試行は、次の実行でその分だけが動く。
9. 2つの軸が同じ区切りを書き換える指示、評価データがない指示、タグや `eval` を書いた選択肢は、何も実行せずに断る。評価データは、基準の設定ファイルの `eval` からも取れる。
10. 文書の本文を保管から1つ消すと、チャンクを作り直す試行だけが失敗する。失敗した試行は理由とともに記録され、後の試行は実行される。続けて3回失敗すると、残りは実行されない。
11. 文書を1つ足して実行すると、走査の結果が追加1件、変わらず6件と返り、チャンクを作り直した文書は1つである。提供中の索引は、リリースするまで動かない。リリースの履歴は、前の版を残す。索引でないものは、リリースできない。ない評価データを指す設定は、何も作らずに止まる。

最適化を足すときに、保管の側に必要だった変更は3つだった。`runs` の `cause`、スナップショットを作らない実行の終わり方、実行せずにキーを引く操作である。評価データと評価の結果は、種別を足すだけで載った。

段階を足すときに、保管の側に必要だった変更は2つだった。項目にも `results` を覚えさせること（チャンク化の入力は、オブジェクトではなく項目である）と、名前を付ける操作である。3つの段階は、どれも同じ操作（開始する、引く、書く、確定する）だけで書けた。

全段階に共通する条件は次のとおり。

- **速さ**: Markdown 1万件の構築時間が、移行前（変更履歴によると3.7秒）から悪化しない。変更なしの `build` は、文書の本文を読まずに終わる。
- **見せ方**: `init` → `build` → `search` の表示に、IDもタグも出ない。
- **続きから進む**: どの段階で止めても、次の `build` が何も指定せずに続きから動く。
