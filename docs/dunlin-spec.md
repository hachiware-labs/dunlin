# Dunlin 設計仕様 統合版

Nov 14, 2026 · @北田成秀

Dunlin は、ひとつ入れるだけで手元の資料からすぐに立ち上げられるナレッジ基盤である。本書は、RAG/MCP側とLLM Wiki/PARA側の2系統について、これまでの検討で決めたコマンド体系と動作をひとつにまとめる。

## 1 この文書について

本書は実装済み機能の一覧ではなく、これから実装するコマンド体系と動作契約の案である。これまでの検討（CLI仕様案、整理版、設計方針、その後の議論）を統合し、後から決めた内容を優先している。

| 項目 | 内容 |
| --- | --- |
| 範囲 | RAG/MCP側とLLM Wiki/PARA側のサブコマンド、設定、評価、画面、運用 |
| 状態 | コマンドの粒度と役割分担は決定。オプション名、設定キー、数値は案 |
| 優先順位 | 本書の内容が、以前の文書と食い違う場合は本書を優先する。23章に変更した決定をまとめる |
| 未決事項 | 21章にまとめる。本文中では「未決」と明記する |

### 用語

| 用語 | 意味 |
| --- | --- |
| 系統 | RAG/MCP側、またはLLM Wiki/PARA側。取り込みの入り口から分かれる |

## 2 位置づけと3つの軸

次の3点は、今後の検討でも動かさない軸とする。機能や設計を足すか迷ったときは、「3つの軸のどれかに必要か」で判断し、どれにも当たらないものは非目標か後続に回す。

| 軸 | 内容 | 設計に課される条件 |
| --- | --- | --- |
| 最速で構築できる | Dunlin は最速で構築できるナレッジ基盤である | 設定を書かなくても、資料を指定するだけで検索まで届く。3コマンドで到達できる |
| 入れれば解決 | 他の道具をいくつも入れさせない。MCPとRAGを提供し、LLM WikiとPARAも支える | 1つのパッケージで完結する。別のデータベースや検索サーバーを立てさせない |
| 評価・改善・文書更新まで | RAG/MCPは、評価、改善、文書更新までを設定ファイルで支える | 検索の品質を測り、設定を変えて比べ、文書の変更に追従できる。これらを宣言的な設定で扱う |

### 軸から導かれる方針

- **速さは測れる形で約束する**: 「インストールから検索まで数分、3コマンド」を受け入れ条件にする。
- **本体は軽く、重い機能は後付け**: キーワード検索は標準構成だけで動く。OCR、埋め込み、再ランク付けは設定したときだけ使う。
- **違いは3つ目の軸が担う**: 1コマンドで検索を立てる道具は多い。立ち上げた後も測って良くし続けられることが、Dunlin の特徴である。
- **対象は手元の資料**: 個人、小さなチーム、エージェントが手元で使う道具であり、大規模な分散検索サービスではない。

### 前提とする実装方針

設計方針で採用済みの次の点を前提とする。

- 標準構成を1つの npm パッケージで提供する。中核は Rust の単一 crate で実装し、Node.js との接続は NAPI-RS を第一候補とする。
- 設定ファイルは `Dunlinfile.yaml` とする。
- 共通機能はライブラリAPIに置き、CLI、MCP、画面は薄い層とする。
- 人とコーディングエージェントの両方を操作者とし、すべての操作に非対話の経路を用意する。

## 3 全体構成

Dunlin は、取り込みの入り口から分かれた2つの系統で構成する。系統は `init` で選び、作業ディレクトリも系統ごとに分ける。

&#91;embedded content: 全体構成 · 2系統と共有する内部部品\]

両側は同じ段階をたどるが、コマンドも対象も別である。共有するのは下段の内部部品だけで、利用者が直接操作することはない。

|  | RAG/MCP側 | LLM Wiki/PARA側 |
| --- | --- | --- |
| 目的 | 既にある資料を検索して引く | 資料を読み、知識をページやノートに蓄積・整理する |
| 入り口 | `build`（`source` → `transform` → `index`） | `ingress` |
| 入れ方 | フォルダを指定し、全体を走査する | 資料を選んで1件ずつ、または数件ずつ渡す |
| 引く | `search`（mcp）、`ask`（rag） | `query` |
| 確かめる | `eval-data` → `eval` | `verify` |
| 整理する | なし | `archive` |
| 提供する | `serve`（MCPサーバー） | `serve`（ブラウザ向けの画面） |
| 書き手 | Dunlin（決定的な処理） | AI（設定したモデル） |
| 調整するもの | チャンク、索引、検索方式 | 目的と範囲、運用の決まり |
| 評価 | あり | なし |

両側とも「入れる → 引く → 確かめる → 提供する」の並びになる。`search` と `query` で名前を変えるのは、前者が原文の断片、後者が書かれたページやノートを対象にするためである。

### 利用者には見せずに共有する部品

入り口は分けるが、内部の部品は二重に作らない。次のものは実装として共有し、コマンドとしては見せない。

| 部品 | 役割 |
| --- | --- |
| 原本の保存と版の管理 | 内容が同じ資料は1つだけ持つ。過去の版を引用から辿れる |
| テキスト抽出 | 文書形式ごとの読み取り。両側が同じ抽出結果を使える |
| 引用の表現と検証 | 「版と範囲」で原文を指し、実在を確かめる。評価データの根拠とページの引用で同じ仕組みを使う |
| キーワード検索 | Wiki/PARA側では、取り込んだ資料から根拠を探すために固定の構成で使う。調整も評価もしない |

部品のうち、どれを Rust で作り、どれを JavaScript で作るかと、データの正本の置き場所は28章で決める。

### 「同じ資料を共用できる」の意味

1回の構築が4つの用途すべてに効くのではない。同じ保存領域と抽出結果を使い回せる、という意味である。同じ資料を両方の系統で使う場合は、`build` と `ingress` の両方に渡す。Wiki/PARA側の作業中にRAG/MCP側の索引も引けるようにするかは未決である（21章）。

## 4 共通事項

### 4.1 初期化と作業ディレクトリ

```bash
dunlin init mcp ./kb --source ~/manuals
dunlin init rag ./qa --source ~/manuals
dunlin init wiki ./wiki
dunlin init para ./notes
```

種別は4つあり、それぞれ「引く」ためのコマンドが決まっている。

| 種別 | 系統 | 引くコマンド | 返すもの | モデル | 生成される初期設定 |
| --- | --- | --- | --- | --- | --- |
| `mcp` | RAG/MCP側 | `search` | 根拠となる文脈と出典 | 不要 | [MCP の YAML](#mcp-の-dunlinfileyaml) |
| `rag` | RAG/MCP側 | `ask` | 回答の文章と出典 | 回答用のモデルが必要 | [RAG の YAML](#rag-の-dunlinfileyaml) |
| `wiki` | LLM Wiki/PARA側 | `query` | ページに基づく回答と出典 | 執筆用のモデルが必要 | [Wiki の YAML](#wiki-の-dunlinfileyaml) |
| `para` | LLM Wiki/PARA側 | `query` | ノートに基づく回答と出典 | 執筆用のモデルが必要 | [PARA の YAML](#para-の-dunlinfileyaml) |

`mcp` と `rag` は、構築から評価までの仕組みを共有する。違いは、回答を作るのが誰かである。`mcp` では根拠を受け取ったエージェントが回答を作り、`rag` では Dunlin が回答を作る。`rag` は `mcp` の設定に回答生成の区切りを足したものなので、`mcp` で始めて後から `rag` に広げられる。

- `init` で系統を選ぶ。選んだ種別は設定ファイルに記録され、そのディレクトリで使えるサブコマンドが決まる。
- 作業ディレクトリは系統ごとに分ける。同じディレクトリで両方の系統のコマンドを使うことはない。
- `serve` は両側にあるが、意味は種別で変わる。RAG/MCP側はMCPサーバー、Wiki/PARA側はブラウザ向けの画面である。異なる系統のコマンドを実行した場合は、種別が違うことを表示して終了する。
- 初期化は、モデルのダウンロード、外部APIの呼び出し、構築を行わない。既存のプロジェクトや同名ファイルを上書きしない。
- コマンドは、現在のディレクトリから親方向に `Dunlinfile.yaml` を探してプロジェクトを特定する。別の場所からは `--project <dir>` で指定する。

#### 初期化時のモデル指定

`init` にモデル名とプロバイダーを渡して、初期設定に書き出せる。

| 用途 | 指定 | 対応する種別 | プロバイダー |
| --- | --- | --- | --- |
| 埋め込み | `--embedding-model <name>`、`--embedding-provider <provider>` | `mcp`、`rag` | `ollama`、`openai` |
| 回答・執筆 | `--llm-model <name>`、`--llm-provider <provider>` | `rag`、`wiki`、`para` | `ollama`、`openai`、`strata` |

頻繁に使う組み合わせは `dunlin config set <embedding|llm> --provider <provider> --model <name>` でユーザーごとに保存する。`dunlin config list` で確認し、`dunlin config unset <embedding|llm>` で解除する。保存先は `~/.dunlin/config.yaml` とし、`DUNLIN_GLOBAL_CONFIG` で変更できる。

- `init mcp` は埋め込みを明示した場合にモデルを設定する。RAG は `init` の指定、ユーザー設定、標準値の順に優先する。プロバイダーを変えた場合、以前のプロバイダーのモデル名は引き継がない。
- `--no-embedding`、`--no-llm` で、それぞれのユーザー設定をその初期化だけ適用しない。同じ用途のモデル・プロバイダー指定との併用はエラーにする。
- プロバイダーの標準値は Ollama。OpenAI を選ぶと、認証用の環境変数名 `OPENAI_API_KEY` を生成する設定に書く。キー本体は保存しない。
- モデルの設定と、必要なモジュール・引数を `Dunlinfile.yaml` に書く。以後の実行は、そのプロジェクトの設定を使う。ユーザー設定の変更は次回以降の初期化に適用する。

#### 初期化時の OCR 指定

OCR の実行方式は次の2つから選ぶ。

| ツール | 内容 | 向く環境 |
| --- | --- | --- |
| `oar-ocr`（標準） | PaddleOCR のモデルを ONNX Runtime で動かす。Rust から直接呼ぶ | GPU のない環境を含む、すべての環境 |
| `lightonocr` | LightOnOCR の視覚言語モデルを、管理された Python の実行環境で動かす。Rust から別プロセスとして起動する | GPU があり、精度を優先する環境 |

`dunlin config set ocr` で OCR をユーザー設定に登録する。`--tool oar-ocr` または `--tool lightonocr` で方式を選ぶ。`--tool` を省いた場合は `oar-ocr` を登録する。以前に登録した `tool: lightonocr` はそのまま有効である。`dunlin config list` で確認し、`dunlin config unset ocr` で解除する。登録内容はモデルの既定値と同じ `~/.dunlin/config.yaml` に保存する。

`init mcp` は `--ocr` を明示すると OCR を有効にする。ほかの種別は `init` のオプション、ユーザー設定、組み込みの既定値（無効）の順で優先する。`init --ocr-tool <oar-ocr|lightonocr>` で、その初期化に限って方式を選べる。方式は `--ocr-tool`、ユーザー設定、`oar-ocr` の順で決める。

OCR を有効にした `init` は、MCP/RAG では `source`、Wiki/PARA では `ingress` の `loader.auto` で `with.ocr` に `loader.ocr` を設定し、`tools` に選んだ方式の名前と版を記録する。`config set` と `init` は設定を書き出す。実行環境とモデルは必要に応じてプロジェクト内で `dunlin add ocr` を実行して準備する。`dunlin add ocr` は、`tools` に記録された方式を準備し、記録がなければ `oar-ocr` を準備して記録する。

- PDF のテキスト層は先に読み、テキスト層のないページと画像だけを OCR にかける。テキスト層は `pdf_oxide` で読み、テキスト層のないページも `pdf_oxide` で長辺 1540 ピクセルの画像にしてから OCR にかける。
- 1つのプロジェクトで使う OCR は1つとする。`tools` に2つの方式を書いた場合は検証エラーにする。
- 方式を切り替えるには、`dunlin remove` で今の方式を外し、`dunlin add` で別の方式を足してから `dunlin build` を実行する。抽出結果の再利用のキーには方式と版を含めるので、OCR にかけた文書だけが読み直される。
- 以前のプロジェクトの `tools` にある `name: ocr` は、`lightonocr` の旧名として読む。

#### 初期化で作成する項目

| 作成物 | 内容 |
| --- | --- |
| `Dunlinfile.yaml` | 編集可能な設定の正本 |
| `.dunlin/state.sqlite` | データ、設定の記録、派生成果物、実行履歴、タグ |

### 4.2 設定ファイルの方針

標準構成でも、使うものはすべて設定ファイルに書き出す。中が見えない箱にしない。分からない利用者は開かなければよく、分かる利用者は開けばすべて書いてある、という形にする。

**基本**

- **設定ファイルが正本**: ファイルの編集とコマンドによる変更は、同じ設定を変更する。
- **標準構成をすべて書き出す**: `init` が、標準構成で使うモジュールと引数をすべて書き出す。省略された既定に頼らない。
- **触らなくても動く**: 書き出された設定のまま、構築と提供ができる。編集は必須ではない。
- **秘密値を書かない**: APIキー本体ではなく、環境変数名を書く。
- **相対パスの基準**: 設定ファイル内の相対パスは、そのファイルの位置を基準に解決する。

**書式**

- **区切りごとにモジュールと引数を書く**: 最上位の区切りはサブコマンドに対応する。各区切りに、使うモジュール（`use`）とその引数（`with`）を順に並べる。
- **区切りは固定し、深さは区切りの中に持たせる**: 利用者が増やせるのはモジュールであって、区切りではない。各区切りの入力と出力の型が決まっているから、再利用と途中からの実行が成り立つ。自由に配線できる形にはしない。
- **区切りごとに独立させる**: ある区切りを書き換えても、他の区切りには影響しない。
- **結果に影響する引数は書き出す**: モジュール名だけを書いて引数を省くと、既定値が見えない部分として残る。省略された引数がある場合も、その既定値はモジュールの同じ版の中では変えない。
- **モジュールは名前で指す**: 並びの何番目かではなく名前で特定する。評価の一覧に「何を変えたか」を出すときや、エージェントが差分を取るときに、位置がずれても追える。同じモジュールを2回使う場合だけ別名を付ける。

**検証と欠落**

- **知らない名前や引数はエラーにする**: 黙って無視すると、書いたつもりの設定が効いていない状態になる。
- **必須の区切りが欠けていたらエラーにする**: 欠けていることに2つの意味を持たせない。標準構成を再出力する方法を案内する。
- **任意の区切りは、書かれていなければ未設定とする**: 評価の区切りなどがこれに当たる。
- **モデルの種別を検証する**: モデルには種別（対話用、埋め込み用）を持たせ、各モジュールは種別が合うモデルだけを参照できる。

**踏み込むための手がかり**

- **使っていない機能は書かない**: 書き出すのは使うものだけとする。埋め込みや再ランク付けは、初期のファイルには現れない。
- **追加例をコメントで添える**: 区切りごとに1行の説明と、追加できるモジュールの例をコメントで付ける。設定ファイル自体が説明書の役割を果たす。
- **使えるモジュールを一覧できる**: モジュール名、入出力の型、引数、依存条件を返すコマンドを用意する。
- **読める長さに保つ**: 標準構成が1画面に収まる程度を目安とする。

**標準構成が新しくなったとき**

設定にすべて書いてあるので、Dunlin を更新しても挙動は黙って変わらない。その代わり、標準構成の改善は既存のプロジェクトに届かない。自分の設定と現在の標準構成の差分を表示し、選んで取り込める操作を用意する。変えるかどうかは利用者が選ぶ。

設定の例は、RAG/MCP側を5.5節、Wiki/PARA側を13.5節に示す。

### 4.3 共通の指定

| 指定 | 意味 |
| --- | --- |
| `--project <dir>` | 操作するプロジェクト |
| `--json` | スキーマ版付きの構造化出力。進捗は標準エラーに出す |
| `--help` | コマンドとオプションの説明。未提供の機能は表示しない |
| `--dry-run` | 変更操作の予定、理由、影響を表示する。永続状態を変更せず、生成・埋め込みAPIを呼ばない |
| `--config <file>` | その実行に使う設定ファイル。試行用の候補設定を指定する |

`--dry-run` でも、変更検出のためのファイル読み取りはあり得る。未実行の工程に依存する件数、容量、費用は、推定または未確定と表示する。

### 4.4 終了コードと構造化出力

| コード | 意味 |
| --- | --- |
| 0 | 正常完了 |
| 1 | 実行中の失敗 |
| 2 | 引数、設定、スキーマ、互換性の検証エラー |
| 3 | 前提不足。前段の出力、索引、評価データなどがない |
| 4 | ロックや同時更新の競合。再試行できるかを構造化出力のエラーコードで示す |

`--json` は標準出力に1つのJSONオブジェクトを返す。基本形は次のとおりで、コマンド固有の内容は `data` に入れる。IDは説明用である。

```json
{
  "schema_version": 1,
  "command": "build",
  "status": "succeeded",
  "run_id": "run-example",
  "data": {
    "build_id": "bld-example",
    "config_id": "cfg-example",
    "serving_changed": false
  },
  "warnings": [],
  "errors": []
}
```

- 読み取り操作や dry-run では `run_id` を null とする。
- `errors` の各項目は、コード、メッセージ、必要なら設定キーや工程などの対象情報を持つ。
- 秘密値を含めない。
- MCPの標準入出力はMCPプロトコル専用とし、独自の出力を混ぜない。

## 5 RAG/MCP側の概要

RAG/MCP側は「作る」「測る」「採用する」の3つのフェーズに分かれる。基本は作るところまでで切り、評価データの作成と評価はその次のフェーズとする。

### 5.1 最短経路

```bash
npm install -g dunlin
dunlin init mcp ./kb --source ~/manuals
cd kb
dunlin build
dunlin search "手順"
dunlin serve
```

`init`、`build`、`search` の3コマンドで検索に到達する。評価データやLLMの設定がなくても、キーワード検索とMCPでの提供まで動く。

### 5.2 フェーズとコマンド

| フェーズ | コマンド | 役割 |
| --- | --- | --- |
| 作る | `source` | 情報源を走査し、ローダーで原文テキストを抽出する |
| 作る | `transform` | テキストの前処理と変換、チャンク化 |
| 作る | `index` | 埋め込み（設定時）と索引の作成 |
| 作る | `build` | 上の3つを順に実行する省略コマンド |
| 使う | `search` | 検索の試行 |
| 使う | `serve` | MCPサーバーとして提供 |
| 測る | `eval-data` | 評価データの作成、取り込み、分割 |
| 測る | `eval` | 評価の実行 |
| 測る | `report` | 評価結果の表示、一覧、比較 |
| 採用する | `use` | 試行したビルドと設定を、提供に使うものとして採用する |
| 確認する | `status`、`validate` | 現在の状態、設定の検証 |
| 使う | ask | 種別 rag のみ。検索した文脈を使って回答を作り、出典を添えて返す |

### 5.3 フェーズの境界

| フェーズ | 含む処理 | 起動のしかた |
| --- | --- | --- |
| 作る | 走査、変更検出、抽出、前処理、チャンク化、索引更新。変更のあった文書だけ | `build` または各段階のコマンド |
| 測る | 評価データの作成、評価、結果の比較 | それぞれ明示的なコマンド |
| 採用する | 提供に使う構成の変更、切り戻し | `use` |

- 「作る」は評価データに触れず、評価も走らせない。評価用のLLMも呼ばない。
- 「測る」は構築を暗黙に実行しない。索引が現在の設定や文書より古い場合は、その旨を表示する。
- 評価は関門ではなく、鮮度を示す情報である。評価を通さなくても構築と提供はできる。

### 5.4 RAGの回答生成

取得した根拠を使って回答を生成する `ask` は、種別 rag で使うコマンドである。検索で得た文脈を設定したモデルに渡して回答を作り、出典を添えて返す。種別 mcp では使わない。エージェントが自分で回答を作るので、検索が返す文脈と出典で足りる。評価の対象はどちらの種別でも検索の根拠だけであり、回答の文章の品質は測らない。種別 rag でも、検索の部分だけを確かめるために search を使える。

### 5.5 設定ファイルの例

次の2例は、グローバル設定にモデルと OCR の登録がなく、`init` に追加のオプションを渡さない場合に生成する `Dunlinfile.yaml` の全文である。入力ディレクトリの既定は `./docs`。`--source` を指定すると、`source.filesystem` の `with.path` にプロジェクトから見た指定先のパスが入る。

標準の `search` は、Lindera + IPADIC で分かち書きし、Tantivy の BM25 でキーワード検索する。MCP は `serve` で stdio を使う。RAG は `ask` と HTTP の `serve` を備え、回答を生成するには `models.answerer.model` にモデル名を設定する。検索はモデル名が `null` のまま使える。 [HTTP の提供設定](#273-種別-rag-の-serve)

`--embedding-model` または RAG のグローバル設定で埋め込みモデルを指定すると、`models.embedder` と `index.vector` が加わる。`search` には `retrieval.vector`（`top_k: 10`）と `fusion.rrf`（`k: 60`）が加わり、キーワードとベクトルを組み合わせて検索する。 [初期化時のモデル指定](#初期化時のモデル指定)

#### MCP の Dunlinfile.yaml

`dunlin init mcp ./mcp`

```yaml

  type: mcp

    - use: source.filesystem
      with:
        path: ./docs
        exclude: []
    - use: loader.auto
      with:
        unsupported: error
        ocr: none

  modules:
    - use: text.normalize
      with:
        unicode: nfkc
    - use: chunk.length
      with:
        unit: characters
        size: 800
        overlap: 100
# Additional index: use: index.vector, with: { model: local-embed }.
# Build the keyword index. An optional vector index uses index.vector.
index:
  modules:
    - use: index.keyword
      with:
        tokenizer: lindera
        user_dictionary: null
# For hybrid search, add retrieval.vector and fusion.rrf before context.assemble.

search:
  modules:
    - use: query.normalize
      with:
        unicode: nfkc
    - use: retrieval.keyword
      with:
        top_k: 10
    - use: context.assemble
```

## 6 作る: source、transform、index、build

構築は3つの段階に分かれ、`build` がそれらをまとめて実行する。利用者に見せる段階は3つ、内部の再利用はそれより細かい単位で行う。

### 6.1 各段階の内容

| 段階 | 処理 | 入力 | 出力 |
| --- | --- | --- | --- |
| `source` | 情報源の走査、変更検出、ローダーによるテキスト抽出（OCRを含む） | 設定された情報源 | 原文集合、コーパス |
| `transform` | 正規化などの前処理、チャンク化 | コーパス | チャンク集合 |
| `index` | 埋め込み（設定時）、キーワード索引とベクトル索引の作成 | チャンク集合 | 埋め込み集合、索引 |

- MCP/RAG の `source` と Wiki/PARA の `ingress` は、ファイルの読み込み、ハッシュ計算、本文抽出を最大4件まで同時に進める。文書と警告は入力順に記録する。OCR を有効にした取り込みは、認識要求の順序を保つためファイルを1件ずつ処理する。
- チャンク化は `transform` に入れる。チャンク設定を変えても、抽出はやり直さない。
- 埋め込みは `index` に入れる。ただし内部ではチャンク単位で再利用し、トークナイザだけを変えたときに埋め込みを再計算しない。
- 各段階の出力は、その段階が成功した時点で自動的に保存する。利用者が保存操作をする必要はない。

### 6.2 build

```bash
dunlin build
dunlin build --dry-run
dunlin build --from transform
dunlin build --until transform
dunlin build --force
dunlin build --skip-unsupported
dunlin build --from transform --config candidates/trial-3.yaml --tag trial-3
```

| 指定 | 動作 |
| --- | --- |
| なし | `source` → `transform` → `index` を順に実行する。変更のあった文書と、設定変更の影響を受ける段階だけを処理する |
| `--from <段階>` | 指定した段階から実行する。それより前は実行も変更確認もせず、既にある出力を使う |
| `--until <段階>` | 指定した段階まで実行して止める |
| `--force` | 対象の段階を、再利用せずにすべてやり直す |
| `--dry-run` | どの文書のどの段階が実行されるかを表示する |
| `--skip-unsupported` | 未対応形式のファイルを、理由を記録したうえで飛ばす |
| `--config <file>` | 候補の設定ファイルを使う。本体の設定ファイルは変更しない |
| `--tag <name>` | 結果に名前を付ける。タグ付きのビルドは試行として扱い、提供内容を切り替えない（11章） |

日常の操作は `build` だけで足りる。初回の構築、文書の更新、設定の変更のどれでも、1回実行すれば必要な分だけが処理される。

### 6.3 途中からの実行

| 指定 | 実行する段階 | 入力 |
| --- | --- | --- |
| `build` | `source` → `transform` → `index` | 現在の情報源を走査 |
| `build --from transform` | `transform` → `index` | 既にある `source` の出力 |
| `build --from index` | `index` | 既にある `transform` の出力 |

- 指定した段階より前は情報源を走査し直さないので、原文が固定されたまま試行できる。試行の間に文書が更新されても結果に混ざらず、設定の違いだけを比べられる。
- 指定した段階以降でも、入力と設定が同じ部分は再利用する。すべてやり直すときは `--force` を併用する。
- 前段の出力がなければ、その旨を表示してコード3で終了する。

### 6.4 段階の個別実行

`source`、`transform`、`index` は、その段階だけを実行する。前段の最新の出力を入力に使う。

- 前段を暗黙に実行しない。個別実行は「この段階だけを試したい」ときの手段なので、他の段階が勝手に走らないほうが予測しやすい。
- 前段の出力がなければ、コード3で終了する。
- 前段が古い場合（文書が更新されている、設定が変わっている）は、警告を出したうえで今ある出力を使う。

### 6.5 未対応ファイルの扱い

- どのパーサも受け持たないファイルを未対応とする（6.7）。
- 既定では、未対応形式や利用できないローダーがあると停止する。黙って文書を欠落させない。
- 停止時に、対象ファイルと理由の一覧、除外設定の例、`--skip-unsupported` を使う実行例を表示する。
- 飛ばしたファイルは、理由付きで記録と `status` に残す。全文書を検索できるかのように扱わない。
- 処理中の破損、読み取りエラー、抽出エラーは、この指定では飛ばさない。
- 検索可能な文書がゼロなら、件数を示してコード3で終了する。

### 6.6 完了時の表示

`build` の完了時に次を表示する。

- ビルドIDと使用した設定ID
- 原文の総数、処理に成功した数、飛ばした数と理由
- 再利用した段階と新たに実行した段階
- 所要時間
- `build --json` の `data.stages` に、各段階の処理開始から保存完了までの `elapsed_ms` を記録する。全体の `elapsed_ms` は実行ロック待ちも含む。
- 提供内容が切り替わったかどうか
- 次に打つコマンド（`search` など）

### 6.7 パーサの振り分けと外部コマンド

`source` のパーサはすべてモジュールとして書き、受け持つファイルと処理の内容を引数で決める。利用者が持つ変換ツールも、同じ枠組みの `loader.command` として組み込む。任意のコードを読み込む拡張の口（プラグイン）は設けない。

```yaml
source:
  modules:
    - use: source.filesystem
      with: { path: ./manuals }
    - use: loader.command
      with:
        match: ["drawings/**/*.vsdx"]
        command: ["vsdx2md", "--stdout", "{input}"]
        output: markdown
        version: "2.1"
    - use: loader.ocr
      with: { match: ["scans/**/*.pdf"] }
    - use: loader.auto
      with: { unsupported: error }
```

#### 振り分けの規則

- 1つのファイルは1つのパーサだけが読む。`source` に書いたパーサを上から順に照合し、最初に受け持つと判定したモジュールが処理する。
- `loader.auto` は書いた位置によらず最後に照合する。前のパーサが受け持たなかったファイルの形式を判定し、標準のパーサに振り分ける。
- `match` は、情報源のルートからの相対パス（`/` 区切り）に対する glob の配列である。大文字と小文字の扱いは `source.filesystem` の `exclude` と同じにする。
- 標準のパーサ（`loader.text`、`loader.office`、`loader.pdf`、`loader.ocr`）は、扱える形式（拡張子、MIME、先頭のバイト）のファイルを受け持つ。`match` を指定すると、そのうち glob に一致するものだけに絞る。形式が合わないファイルは、`match` に一致しても次のパーサへ回す。
- `loader.command` は形式を判定せず、`match` に一致したファイルを受け持つ。`match` は必須とする。
- どのパーサも受け持たないファイルを未対応ファイルとする（6.5）。
- 走査、未対応の判定、`build --dry-run`、抽出は同じ振り分けの処理を使う。`build --dry-run --json` は、ファイルごとに受け持つモジュールを `parser` に返す。
- 抽出した文書の由来には、受け持ったモジュール名と、外部ツールの名前と版を記録する。

#### loader.command の引数

| 引数 | 型と既定値 | 影響 | 内容 |
| --- | --- | --- | --- |
| `match` | glob の配列。必須 | 結果 | 受け持つファイル |
| `command` | 文字列の配列。必須 | 結果 | 実行ファイルと引数。シェルを通さずに起動する |
| `input` | `file` / `stdin`。既定は `file` | 結果 | 原本の渡し方 |
| `output` | `markdown` / `text` / `json`。既定は `markdown` | 結果 | 標準出力の解釈 |
| `version` | 文字列。省略可 | 結果 | 再利用キーに含める版。外部ツールを更新したら変える |
| `version_command` | 文字列の配列。省略可 | 結果 | 構築の開始時に1回実行し、標準出力を版として使う。`version` とは同時に指定できない |
| `env` | 名前から値への対応。既定は空 | 結果 | 追加する環境変数。値には `${ENV_NAME}` を使える |
| `timeout_ms` | 整数。既定は 120000 | 速度 | 1ファイルあたりの時間の上限 |
| `concurrency` | 1〜4 の整数。既定は 2 | 速度 | 同時に起動するプロセスの数。取り込み全体の同時数（6.1）の内側で数える |

`command` の各要素には、次の置き換え記号を書ける。これ以外の `{…}` は検証でエラーにする。波括弧そのものは `{{` と `}}` で書く。

| 記号 | 置き換える値 |
| --- | --- |
| `{input}` | 原本の写しの一時ファイルのパス。`input: file` のときは必須、`input: stdin` のときは使えない |
| `{name}` | 原本のファイル名（ディレクトリを含まない） |
| `{ext}` | 原本の拡張子。先頭の `.` を含み、小文字にそろえる |

#### 実行の規則

- `command` の先頭が `/` や `./` などのパスなら、設定ファイルの場所を基準に解決する。名前だけなら `PATH` から探す。作業ディレクトリはプロジェクトのルートとする。
- 原本そのものは渡さない。`input: file` では元の拡張子を保った一時ファイルに写して渡し、終了後に消す。`input: stdin` では原本のバイト列を標準入力に流す。
- 環境変数は親プロセスのものを引き継ぎ、`env` の値で上書きする。
- 次の場合は、そのファイルの抽出エラーとする。`--skip-unsupported` を指定しても飛ばさない（6.5）。
  - 終了コードが0以外だった
  - `timeout_ms` を超えた
  - 標準出力が UTF-8 として読めない
  - 本文が空だった、または 1 MiB を超えた
  - `output: json` で形式が正しくない
- エラーの表示には、終了コードと標準エラーの末尾（最大 2 KiB）を含める。秘密値の扱いは 17.3 に従う。
- 構築の中断（利用者の中断、試行の上限）では、起動中のプロセスを終了させる。

#### 出力の形式

| `output` | 扱い |
| --- | --- |
| `markdown` | 標準出力の全体を Markdown の本文とする。位置は `loader.text` と同じく見出しと行から付ける |
| `text` | 標準出力の全体をテキストの本文とする。位置は行から付ける |
| `json` | 標準出力を次の形の JSON として読む。位置を外部ツールが返すので、ページなど原本上の位置を出典に残せる |

```json
{
  "content": "抽出した本文",
  "format": "markdown",
  "locations": [
    { "page": 1, "range": { "startLine": 1, "endLine": 12 } },
    { "symbol": "PumpSpec", "range": { "startLine": 14, "endLine": 30 } }
  ]
}
```

- `format` は `markdown` か `text`。`locations` は省略でき、省略時は `format` に応じて行から付ける。
- `locations` の要素は、本文の行範囲 `range`（1始まり、両端を含む）を必ず持つ。`page`（1始まり）、`symbol`、`bbox`（ページ上の位置）は任意で付けられる。内部のパーサが返す位置と同じ形である。
- 知らない欄は無視せず、検証エラーとする。

#### 再利用と検証

- 工程キー（7.1）には、モジュール名と出力互換性バージョン、影響が「結果」の引数、`version` か `version_command` の出力、原本の内容ハッシュを入れる。`timeout_ms` と `concurrency` を変えても抽出はやり直さない。
- `version` も `version_command` もない場合は、外部ツールを更新しても検出できない。`dunlin validate` で警告し、更新したときは `build --force` で作り直すよう案内する。
- `dunlin validate` は次を検査する。
  - `command` の実行ファイルが見つかること
  - 置き換え記号が正しく、`input` の指定と矛盾しないこと
  - `version` と `version_command` を同時に指定していないこと
- `loader.command` を使えるのは、MCP/RAG の `source` だけとする。Wiki/PARA の `ingress` に書いた場合は検証エラーにする（17.5）。

## 7 再利用の仕組みと識別子

同じ入力と同じ設定の処理は、結果を再利用する。そのために「工程キーから出力を引く表」と「内容で共有する実体」を分けて持つ。

### 7.1 再利用の規則

| 要素 | 内容 |
| --- | --- |
| 工程キー | 入力の内容ハッシュ、その工程が参照する実効設定、出力互換性バージョン、必要なモデル識別情報 |
| キーから出力への対応 | 同じキーに複数の成功出力を記録できる |
| 内容による保存 | 同じ内容の本文や埋め込みは、1つの実体を共有する |
| 通常の再利用先 | 適合する最新の成功出力 |
| 過去のビルド | 記録済みの出力IDを固定し、最新の出力に付け替えない |

- **粒度**: 抽出は文書単位で再利用する。埋め込みは、チャンク本文とモデル、前処理、要求パラメーターなどの実効条件の単位で再利用する。「本文 × モデル名」だけに省略しない。
- **出力互換性バージョン**: 工程ごとに持つ番号で、出力に影響する実装変更や依存更新で上げる。依存ライブラリの版そのものはキーに入れず、由来として記録する。
- **上げ忘れの検出**: 固定の入力に対する出力ハッシュをテストに持ち、出力が変わったのにバージョンが同じなら失敗させる。これは決定的な工程に適用する。LLMや数値処理を含む工程は、固定応答による処理テストと、実モデルでの確認を分ける。
- **出力が変わる工程**: 同じキーで結果が変わり得る工程は、複数の成功出力を記録する。新しい実行は最新の成功出力を使い、過去のビルドは固定した出力を使い続ける。
- **失敗と未完了**: 失敗または未完了の出力は再利用しない。ただし、その中で確定した文書単位の成功出力は次の実行で使える。

### 7.2 変更と再実行の範囲

| 変更 | 再実行する範囲 |
| --- | --- |
| 原文の追加・更新 | 対象文書の抽出以降と、必要な索引更新 |
| 原文の削除 | 新しい索引から除外。過去の記録は保持 |
| ローダー、OCRの設定 | 影響する文書の `source` 以降 |
| パーサの並び、`match`、外部コマンドの引数と版 | 受け持つパーサか、その結果に影響する設定が変わった文書の `source` 以降 |
| 前処理、チャンクの設定 | `transform` 以降 |
| 埋め込みモデル | 埋め込みとベクトル索引 |
| キーワードのトークナイザ | キーワード索引のみ |
| 検索設定 | 構築不要。ビルドIDも変わらない |
| 評価データ、評価方法 | 構築不要。必要な位置対応と評価だけ更新 |

### 7.3 識別子

データや設定を表すIDと、処理を実行した事実を表すIDを分ける。同じ成果物を複数の実行が参照できる。

| 識別子 | 決まり方と対象 |
| --- | --- |
| 設定ID | 秘密値を除いて正規化した設定の内容ハッシュ。同じ内容なら同じID |
| ビルドID | 原文集合、コーパス、チャンク、埋め込み、索引の組。検索設定は含めない |
| 検索設定ID | 参照先を解決した実効検索設定と、関連処理の互換性バージョンのハッシュ。文脈の組み立てを含む |
| 評価データID | 質問、根拠、確認状態、分割を持つ不変の記録 |
| 評価方法ID | 指標、採点ルール、対象選択方針、評価器、プロンプト、関連実装版のハッシュ |
| 根拠対応表ID | コーパス上の確定位置、未解決状態、確認履歴を持つ不変の派生成果物 |
| 実行ID | `build`、`eval` などを実行するたびに発行 |

- **検索設定だけの変更ではビルドIDを変えない**: 件数や重み、文脈の組み立てを変えても、構築処理は走らず、同じビルドを使う。
- **モデルの参照名だけをハッシュしない**: 参照先のプロバイダー、モデル、要求パラメーター、非秘密の接続先まで解決する。外部プロンプトはパスではなく内容を含める。
- **名前と識別を分ける**: 人はタグで指定でき、実行記録は開始時に解決したIDを持つ。タグを付け替えても、過去の記録の参照先は変わらない。
- **タグの付け替えは明示する**: 既存のタグを別の対象へ黙って移さない。付け替えは明示的な指定で行い、履歴を残す。

## 8 検索、文脈の組み立て、MCPでの提供

`search`、`serve`、`eval` は、1つの検索実装と文脈の組み立て処理を共有する。評価で測る文脈と、MCPで実際に返す文脈が同じになるようにするためである。

### 8.1 対象と設定

| コマンド | 対象のビルド | 検索設定 |
| --- | --- | --- |
| `search <query>` | 採用中のビルド | 採用中の設定 |
| `search <query> --build <tag>` | 指定した試行のビルド | その試行の設定、または `--config` |
| `serve` | 採用中のビルド | 起動時の採用中の設定を固定 |

- `search` と `serve` の既定の対象をそろえる。手元で確かめた結果と、提供される結果がずれないようにするためである。
- どちらも構築を暗黙に実行しない。利用できるビルドがなければ、`build` を案内してコード3で終了する。
- ビルドにない索引や、互換性のない埋め込みを要求する設定はエラーにする。黙って別の方式に切り替えない。
- `search` は、使用したビルドIDと検索設定IDを結果とともに表示する。

### 8.2 キーワード検索

- RAG/MCP の標準構成は、同梱する Lindera と IPADIC で本文、見出し、問い合わせを分かち書きする。文書と問い合わせには同じ辞書を適用し、活用語は辞書形を使い、助詞と助動詞を検索語から外す。
- 分かち書きした語のいずれかに一致するチャンクを候補に取り、BM25 で順位付けする。問い合わせの隣り合う検索語が文書でも連続する場合は加点する。
- `index.keyword` の `with.user_dictionary` に UTF-8 の CSV を指定できる。CSV は見出し行なしで `表層形,品詞,読み` の3列とし、表層形は空白を含まない語とする。相対パスは設定ファイルの位置から解決する。索引作成時に CSV の内容を保存し、各ビルドは検索時にもその版を使う。
- 「手順」のような2文字の語も、分かち書きした語として検索する。空白のない自然文で問い合わせ、本文の語順や助詞が異なっても該当する根拠を検索上位に返すことを確認する。
- 1文字の問い合わせの扱いは未決である（21章）。
- トークナイザとユーザー辞書の内容は索引の工程キーに含める。既存の3文字索引は `tokenizer: trigram` で利用でき、`lindera` に切り替えるときはキーワード索引を作り直す。

#### ユーザー辞書の候補を提案する

`dictionary suggest [--report <タグまたはID>]` は、Lindera を使う RAG/MCP ビルドの調整用評価で回収できなかった根拠を調べる。レポートの指定を省略すると、選択中の評価データに対する最新の調整用レポートを使う。問い合わせと根拠の語は、レポートが参照するビルドの辞書と検索時の分かち書きで照合する。

| 分類 | 判断の手がかり | 出力 |
| --- | --- | --- |
| 辞書で改善できる候補 | 問い合わせと根拠に同じ語が現れ、分割や検索語の除外によって対象の語が一致していない。辞書に加えると両方で同じ検索語として扱える | 候補語、現在の分かち書き、該当する質問、根拠の引用と出典 |
| 部分一致が必要 | 問い合わせの検索語が、根拠側の長い検索語の一部になっている（「シール」と「メカニカルシール」など） | 辞書候補から外し、該当する質問数を集計する |
| 語の分割以外の問題 | 対象の検索語は一致しているが、根拠が検索上位に入らない、または文脈の組み立てで落ちる | 辞書候補の対象外と表示し、分かる範囲で理由を示す |

- 根拠ごとに判定し、分類ごとの質問数は同じ質問を重複して数えない。根拠の位置が未解決の場合や、分割の違いを原因と判断できない場合は、判定できた件数と区別して表示する。候補は質問と引用の両方に現れる16文字以内の語とし、引用の分かち書きには保存済みの前後の行内テキストを含める。
- 候補ごとに、語全体を使う問い合わせと、語の一部に置き換えた問い合わせを自動で作る。元の質問から対象語以外の文言を共通にする。「メカニカルシールの交換周期は」と「シールの交換周期は」のように並べ、同じ根拠を探す確認に使う。
- 調整用の評価データがなければ、`eval-data add --question <text> --doc <path> --quote <text>` を案内する。評価データがあり、レポートがなければ `eval` を案内する。旧レポートでどの根拠が未回収かを特定できない質問には、`eval` の再実行を案内する。
- `suggest` は候補と確認用の問い合わせを表示する。採用する行を利用者が CSV にまとめ、`dictionary add <file> --config <候補設定>` で追加する。`add` は既存の辞書と選んだ行を候補設定用の UTF-8 CSV にまとめ、そのファイルを `index.keyword.with.user_dictionary` に設定する。元の辞書と提供中の構成は維持する。
- 部分一致に該当した質問数は、文字単位の索引を併用するか判断するために使う。文書の出現頻度だけで候補を出す機能は後続とする。

### 8.3 文脈の組み立て

検索結果の一覧とは別に、利用者やエージェントへ渡す文脈を次の手順で作る。

1. 同じビルドと問い合わせに対して、安定した順位の候補列を取得する。同点の順序も固定する。
2. 同じ文書内で範囲が重なるチャンクを1つに統合する。統合した群の順位は構成チャンクの最上位、本文は文書内の順とする。
3. 見出しと出典の表示を付ける。これらも出力の文字数に数える。
4. 文脈予算（文字数）に達するまで加える。超える最後の項目は、設定に従って残りの範囲で切るか、加えずに終了する。

| 設定項目 | 意味 | 初期値の案 |
| --- | --- | --- |
| 検索結果の件数 | 検索結果の一覧に出す件数。件数指定の指標にも使う | 10 |
| 文脈予算 | 渡す文脈の上限 | 4000文字 |
| 候補の取得方式 | 予算を満たすまで候補を追加で取るか、検索結果の件数内で作るか | 予算を満たすまで取る |
| 候補の上限 | 文脈用に取りに行く候補の最大数 | 100 |
| 重複の統合 | 重なるチャンクを統合するか | する |
| 最後の項目の切断 | 予算を超える項目を途中で切るか | 切る |

- **件数と文脈用の候補を分ける理由**: 小さいチャンクの設定では、件数の上限で文脈が予算に届かず、不利になる。候補を予算まで取りに行くことで、チャンク設定の違うビルドを同じ文脈量で比べられる。
- **文字の数え方**: 組み立てた文脈文字列のUnicodeスカラー値の数とする。出典の構造化データや通信全体のバイト数とは区別する。
- **停止理由の記録**: 予算を満たした、候補の上限に達した、候補が尽きた、切断しない設定で止まった、のどれかを記録する。
- **位置の追跡**: 各出力部分に、文書、元の範囲、出力側の範囲を対応づける。統合や切断の後も、残った元の範囲を追跡する。
- **装飾は加点しない**: 追加した見出しや出典の表示は、根拠の回収として数えない。
- **生成的な書き換えを含めない**: 本文に位置を戻せない要約や書き換えは、初期の文脈の組み立てに含めない。

文脈の組み立ての設定は検索設定の一部であり、検索設定IDに含める。正確な手順は互換性バージョンで管理する。

### 8.4 serve（MCP）

- 既定の接続方式は標準入出力とする。開始時の説明は標準エラーに出す。
- 設定は起動時に固定する。索引の中身は、文書の更新に追従する（12章）。
- 応答には、組み立てた文脈、出典と位置、使用したビルドID、実効検索設定IDを含める。検索結果の生のチャンクを返す場合は、文脈と区別する。
- 呼び出し側が件数や予算を上書きした場合は、その要求の実効検索設定IDを計算し直し、評価済みの条件と違うことを返す。上書きは次の要求に持ち越さない。
- エージェントへの登録に使う接続設定を、そのまま出力するコマンドを用意する。初回の利用者がここで止まらないようにするためである。

## 9 評価データと根拠の位置対応

評価データは、質問と、正解となる原文中の根拠を対にしたものである。上書きせず、変更のたびに新しい記録を作る。

### 9.1 コマンド

| コマンド | 動作 |
| --- | --- |
| `eval-data add --question <text> --doc <path> --quote <text>` | 質問と根拠を1件追加する |
| `eval-data import <file>` | 最小形式または完全形式のJSONLを取り込む |
| `eval-data export <ref> --output <file>` | 編集・持ち運び用のJSONLを書き出す |
| `eval-data list` / `show <ref>` | 一覧と、ケース・根拠・確認状態・分割の表示。一覧は既定で最新とタグ付きだけを出す |
| `eval-data split --test-ratio <r> --seed <n>` | グループ単位で調整用と最終確認用に分ける |
| `eval-data generate [--model <name>] [--doc <path>] [--count <n>] [--kind <kind>]` | LLMで質問と根拠の候補を生成する。対話用モデルが1つだけなら `--model` を省ける。`--kind` は、作る質問の種類を1つに絞る |
| `eval-data review <ref>` | 候補を確認・修正・採用する。`--case` を繰り返すと複数件をまとめて採用・不採用にできる |
| `eval-data sync <ref>` | 原文の変化を反映した新しい評価データを作る |
| `eval-data diff <ref-a> <ref-b>` | ケース、根拠、分割の差分 |
| `eval-data use <ref>` | 評価に使う評価データを選ぶ |

すべての操作に非対話の経路を持たせる。`review` の代わりに、`export` で書き出して編集し、`import` で戻せる。

### 9.2 最小形式

最初の評価データを手で作れるよう、次の3項目だけの形式を受け付ける。

```json
{"question":"作業前に何を確認しますか","doc":"manuals:guide.md","quote":"作業開始前に電源が切れていることを確認する。"}
```

- 内容ハッシュ、前後の文脈、ケースID、グループ、入力者の種別と日時は、道具が補う。利用者に内容ハッシュを手入力させない。
- 引用が対象文書内で正規化後に一意に一致すれば、位置の対応も保存する。
- 一致しない、または複数箇所に一致する場合は、その場で対象と候補箇所を表示し、コード2で止める。ページや前後の文脈を補助項目として指定できる。
- 一括取り込みは全件を検証してから確定し、失敗した行を黙って落とさない。
- 検索結果の中から正しい箇所を選んでケースにする操作を用意する。引用を手で写す負担と写し間違いを減らすためである。

### 9.3 ケースの状態

| 状態 | 意味 | 評価での扱い |
| --- | --- | --- |
| `generated` | LLMが生成した候補 | 既定で除外。設定で明示的に含められる |
| `provided` | 人またはエージェントが入力し、参照先と引用を道具が検証した | 対象。内容の妥当性を確認済みとは表示しない |
| `reviewed` | 確認して採用した | 対象 |
| `needs_review` | 文書の変更などで再確認が必要 | 対象外。理由を表示 |
| `inactive` | 原文側で有効な根拠がなくなった | 対象外。理由を表示 |
| `rejected` | 不採用 | 対象外 |

確認者には、人かエージェントかの種別と識別情報を記録する。生成しただけで確認済みにしない。

ケースは、質問の種類（`kind`）を持てる。`generate` が作るケースは必ず持ち、手で足すケースでは省ける。種類はケースIDに入らない。

| 種類 | 質問の作り |
| --- | --- |
| `lexical` | 引用にある語を使う |
| `paraphrase` | 引用にある語を避けて言い換える |
| `identifier` | 文書に書かれた型番、数値、名前で尋ねる |

`generate` が作る候補には、次の決まりがある。指示か、モデルに返させる形を変えたら、ケースの `generation.prompt_version` を上げる。今の版は3である。

- **根拠は1つから3つ。** 1つの引用で答えられないときだけ、複数の引用を持つ。引用は別々の文書にあってよい。同じ引用を2度返した場合は、1つとして扱う。
- **引用は300文字（UTF-16 の符号単位）まで。** 根拠の回収は引用がどれだけ返ったかで決まるので、長い引用は小さいチャンクに不利になる。超える候補は `quote_too_long` として除く。
- **1つでも検証できない引用があれば、候補ごと除く。**
- **`--kind` を付けたときは、その種類の候補だけを残す。** ほかの種類は `kind_not_requested` として除く。
- **文書の読ませ方。** 文書は4000文字ごとの部分に分けて読ませる。評価ケースのない文書を先にし、文書の中では、既存のケースの引用が少ない部分を先にする。同じ数の部分は、文書の中に散らばる順に並べ、最初の部分は文書の名前から決める。同じ資料と同じ評価データからは、同じ順になる。

### 9.4 根拠の持ち方

根拠はチャンクIDへの参照ではなく、文書と引用で持つ。1つのケースに複数の根拠を指定できる。

| 項目 | 内容 |
| --- | --- |
| 文書 | 文書の論理ID（情報源名と相対パス）と、確認時の内容ハッシュ |
| 引用 | 根拠のテキストと、その前後の短い文脈 |
| 手がかり | ページや見出しなど。任意 |

チャンク設定や抽出方法を変えても、同じ評価データを使い続けられる。

### 9.5 位置対応表

採点は、固定したコーパス上の位置と範囲で正確に行う。そのため、評価データの引用をコーパス上の範囲に対応づけた表を、派生成果物として持つ。

| 要素 | 内容 |
| --- | --- |
| 項目の再利用キー | 根拠の内容ハッシュ、対象文書の抽出内容のハッシュ、照合ルールの版 |
| 根拠の内容ハッシュ | 文書の論理ID、引用、前後の文脈、手がかり。ケースID、質問、分割、確認日時は含めない |
| 対応表 | 評価データIDとコーパスIDの組に対して、項目を集めたもの |
| 記録 | 評価の実行記録に、使った対応表のIDを残す |

- **自動で確定する条件**: 正規化後の引用が、対象文書内（または手がかりで限定した範囲内）で完全一致し、かつ一意であること。
- **あいまい一致は候補探しにだけ使う**: 抽出方法や原文が変わったときに、引用と前後の文脈から新しい位置の候補を探す。人の確認なしに採点へ使わない。
- **項目単位で再利用する**: ケースの追加、分割の変更、無関係な文書の追加では、変わっていない根拠と文書の項目をそのまま使う。人の確認を要求し直さない。
- **人の確認を優先する**: 同じ項目について、最新の自動照合が人の修正を上書きしない。
- **評価データを変えない**: 位置が未解決であることを理由に、評価データのケース状態を変更しない。

対応表の確認と修正は、評価データとは別のコマンド群（`evidence-map` の作成、表示、書き出し、取り込み、確認）で行う。通常は `eval` が必要に応じて自動で作るので、利用者が直接扱うのは未解決を確認するときだけである。

### 9.6 分割

- 各ケースは、調整用（dev）か最終確認用（test）のどちらかに属する。分割は評価データの一部として固定する。
- 分割はグループ単位で行う。同じ文書や近い内容の質問が両側に混ざらないようにする。
- 最小形式で追加したケースは調整用に入る。件数が増えた時点で、分割を促す表示を出す。
- 後から追加したケースは、同じグループの既存ケースと同じ側に入れる。

### 9.7 生成と同期

- 生成時は、言い換えを含む質問を作る。原文の表現をそのまま写す質問だけに偏ると、キーワード検索が不当に有利になる。業務で実際に使う用語までは避けない。
- 生成元の文書範囲、モデル、プロンプトの版を記録する。
- 評価ケースがまだない文書から先に読ませる。長い文書は先頭だけでなく続きの範囲も渡す。`--count` で作る件数（1〜200、既定10）を指定し、モデルへの要求回数は件数に比例した上限で打ち切る。
- 候補は1件ずつ検証する。引用が渡した範囲にない、文書内で一意に決まらない、既存の質問と重複する候補は採らず、理由ごとの件数を結果に表示する。使える候補が1件もなければ失敗として終了する。

| 原文の変化 | `sync` の処理 |
| --- | --- |
| 追加 | カバレッジ不足を表示。指定時に候補を追加 |
| 根拠箇所の更新 | 関連ケースを `needs_review` にする |
| 根拠文書の削除 | 他に有効な根拠がなければ `inactive` |
| 根拠以外の更新 | 根拠が有効と確認できれば維持。不確かなら `needs_review` |

原文の削除や改訂による無効化と、原文は同じなのに抽出が根拠を失った場合を区別する。後者は評価データの問題ではなく、そのコーパスでの位置が未解決であるものとして扱う。

## 10 評価と比較

評価は、指定したビルドと検索設定に対して、評価データの根拠をどれだけ拾えたかを測る。結果は上書きしない実行記録として残す。

```bash
dunlin eval
dunlin eval --build trial-3 --tag trial-3
dunlin eval --build trial-3 --split test --tag trial-3-test
dunlin report show trial-3
dunlin report list
dunlin report compare baseline trial-3
```

### 10.1 実行の規則

- `eval` は構築を暗黙に実行しない。対象の索引が現在の設定や文書より古い場合は、その旨を表示する。
- 対象のビルドは `--build` で明示できる。省略時は採用中のビルドを使う。試行を比べるときは必ず明示する。
- 評価データが未選択、空、または対象ケースがない場合は、コード3で終了する。
- 同じ条件でも、実行するたびに新しい実行IDを付ける。構築の再利用と、評価結果の上書きや再利用を混同しない。
- ビルドを指定した評価では、設定の検索・評価部分だけを使う。設定の構築部分がビルドと違っていても、作り直したり評価を止めたりしない。

### 10.2 指標

指標はチャンク単位ではなく、根拠単位で測る。チャンク設定が違っても同じ基準で比べられる。

| 指標 | 定義 |
| --- | --- |
| `evidence_recall@context` | 実際に組み立てて提供する文脈が回収した根拠の割合。既定の目的指標 |
| `evidence_recall@k` | 上位 k 件のチャンク範囲の和集合が回収した根拠の割合 |
| 速度 | 検索の所要時間の分布（中央値、95%、99%） |

- **回収の判定**: 根拠の長さが短い場合（初期値の案40文字以下）は全体、それより長ければ一定割合（初期値の案0.8）以上を覆ったとき、回収済みとする。この閾値が表や短い根拠で適切かは、実際のケースで確かめて調整する。
- **範囲の表現**: 文字の単位はUnicodeスカラー値、コーパス上の範囲は半開区間で記録する。
- **重複の扱い**: 同じ根拠を何度覆っても加点しない。渡した文章の重複は、文脈予算を消費する。
- **集計**: 質問ごとの根拠回収率の平均とする。根拠数で重みを付ける集計は、別の指標として追加する。
- **順位系の指標は後続**: 「新しい根拠を初めて覆った結果にだけ加点する」方針は決めているが、計算の定義を固定するまで、一般的な指標と同じ名前では実装しない。
- **件数指定の指標と検索件数**: 検索結果の件数が指標の k より小さい場合は、評価時にエラーにする。

### 10.3 位置が未解決の根拠の扱い

ケース状態による対象選択を先に固定し、その後にコーパスごとの位置対応を判定する。

| 出力 | 計算と用途 |
| --- | --- |
| 保守スコア | 対象ケースの全根拠を分母にし、位置が未解決の根拠を未回収と数える。既定の目的指標 |
| 診断スコア | 全根拠の位置が確定したケースだけで計算する。検索処理の診断用 |
| 対応状況 | 確定・未解決の根拠数、全根拠が確定したケース数、理由 |
| 文脈状況 | 実際の文字数、予算に届かなかったケースの数と割合、その理由 |

- 未解決の根拠を黙って除外しない。除外すると、抽出が根拠を壊した設定ほど良く見えてしまう。
- 診断の対象がゼロなら、診断スコアは値なしとする。0や満点に置き換えない。
- 人が位置を確認した候補は、新しい対応表で評価し直す。古い結果も残す。
- 抽出方法の違うコーパスをまたぐ比較では、引用の生成元に近い側が有利になり得る。その場合の順位は暫定と表示する。

### 10.4 比較できる条件

4つの条件（ビルド、検索設定、評価データ、評価方法）のIDは、すべて同じであることを要求するためではなく、何が違う評価なのかを特定するために使う。

| 比較の目的 | 変えてよい条件 | そろえる条件 |
| --- | --- | --- |
| 構築設定の比較 | ビルド | 検索設定、評価データ、評価方法、対象ケース |
| 検索設定の比較 | 検索設定 | ビルド、評価データ、評価方法、対象ケース |
| 構築と検索の組み合わせ | ビルドと検索設定 | 評価データ、評価方法、対象ケース |
| 同条件の再実行 | 実行条件のみ | 4つの条件と位置対応表 |
| 評価条件の変更を伴う比較 | 評価データや評価方法 | 条件の差を明示し、共通ケースだけを分けて比べる |

### 10.5 表示と統計

- **一覧**: `report list` は、評価データ、評価方法、分割が同じ結果をまとめ、指標順に並べる。列には、結果の間で値が違う設定項目だけを出す。
- **設定の列の出どころ**: 構築系の列はビルドを作った設定から、検索・評価系の列は評価に使った設定から取る。評価記録には両方の設定IDを別々に持たせる。
- **文脈予算が違う結果**: 予算の列を必ず表示し、同じ文脈量での改善として扱わない。
- **2つの比較**: 共通ケースについて、差分、勝ち・負け・同点の件数、グループ単位で再標本化した95%信頼区間を出す。区間が0をまたぐ場合は「差は不確か」と明示する。
- **グループが少ない場合**: 区間を意味のある形で推定できないときは、その旨を示して区間を出さない。件数だけで誤差の大きさを決めつけない。
- **承認のための表示**: 比較は「何を変えて、どれだけ良くなり、差は確かか」が一目で分かる形にする。

### 10.6 最終確認用の分割

- 既定の分割は調整用とする。最終確認用は `--split test` を明示したときだけ使う。
- 一覧の既定表示には、最終確認用の結果を含めない。
- 同じ評価データの最終確認用で評価した回数を記録し、実行時に表示する。名前やタグを変えてもゼロに戻さない。
- 手順は「調整用で探索して候補を選ぶ」「選んだ候補を最終確認用で確かめる」の順とする。最終確認の結果を見て再調整した場合、それはもう独立した確認ではない。
- エージェントには集計値だけを返し、質問別の詳細は人の明示操作でのみ見せる案とする（未決、21章）。

## 11 試行、採用、外部エージェントによる最適化

設定違いの試行は、設定ファイルを少し変え、途中の段階から構築し直し、評価して比べる繰り返しで行う。探索の判断は外部エージェント（または人）が担い、Dunlin は実行と測定を担う。

### 11.1 繰り返しの流れ

```bash
# 候補の設定ファイルを作る（本体の設定はそのまま）
dunlin validate --config candidates/trial-3.yaml --json
dunlin build --from transform --config candidates/trial-3.yaml --tag trial-3 --json
dunlin eval --build trial-3 --tag trial-3 --json
dunlin report compare baseline trial-3 --json
```

1. 評価レポートを読み、品質や速度の弱点を特定する。
2. 設定の変更案を、候補の設定ファイルとして作る。
3. 設定を検証する。
4. 変更が影響する段階から構築する。
5. 固定した調整用の評価データで評価する。
6. 改善がなければ破棄し、あれば候補として残す。
7. 選んだ候補を最終確認用で確かめ、人が承認して採用する。

#### ユーザー辞書を試行する例

`candidates/dict.yaml` は基準の設定から作った候補設定とする。相対パスは候補設定の位置に合わせる。`selected.csv` は利用者が選んだ辞書の行、`BASELINE_BUILD_ID` は `report show dict-baseline` に表示されるビルド ID とする。

```bash
dunlin eval --tag dict-baseline
dunlin dictionary suggest --report dict-baseline
dunlin dictionary add selected.csv --config candidates/dict.yaml
dunlin build --from index --input BASELINE_BUILD_ID --config candidates/dict.yaml --tag dict
dunlin eval --build dict --tag dict-eval
dunlin report compare dict-baseline dict-eval
```

- 辞書の変更は索引段階に反映する。`--from index --input` で、基準ビルドに保存された抽出とチャンク化の結果を再利用する。比較する評価データ、検索設定、評価方法はそろえる。
- `report compare` では、質問ごとに根拠回収率の変化を示し、回収できるようになった質問、悪化した質問、未回収が残った質問を確認できるようにする。候補ごとに生成した2つの問い合わせでも、基準と試行を `search --build <ref> --json` で指定し、同じ検索件数で根拠を含む結果の `rank` を見比べる。上位に現れなければ「上位 k 件に含まれない」と記録する。
- 根拠の回収と部分語での検索への影響を確認したうえで、11.3節の手順に沿って `dunlin use dict` で採用する。

### 11.2 試行は提供内容を変えない

| 操作 | 提供に使う構成 |
| --- | --- |
| `build`（タグなし、本体の設定） | 成功すれば、その結果に更新される |
| `build --tag <name>` | 変えない。試行として記録する |
| `build --config <file>` | 変えない |
| `build --until <段階>`、失敗 | 変えない |
| `use <tag>` | 指定した試行のビルドと設定に切り替える |

- エージェントが試行を重ねても、`serve` と既定の `search` が見る内容は変わらない。
- 試行の結果を手元で確かめるときは、`search --build <tag>` で明示する。

### 11.3 採用

```bash
dunlin eval --build trial-3 --split test --tag trial-3-test
dunlin use trial-3
dunlin status
```

- `use` は、試行のビルドと検索設定の組を提供に使う構成として採用し、候補の設定を本体の設定ファイルへ反映する。変更前の設定も記録する。
- 設定ファイルへ反映するので、次の素の `build` で採用前の構成に戻ることがない。
- 採用に評価を通すことは強制しない。未評価であれば、その旨を表示する。
- 以前の構成への切り戻しも `use` で行う。
- ビルドと設定のIDを複数のコマンドへ貼り付ける必要はない。タグが組を表す。

### 11.4 評価条件の固定

最適化を行うエージェントが評価方法や正解まで書き換えられると、見かけの点数だけを改善できてしまう。

- 試行で変えてよいのは、構築と検索に関する設定だけとする。評価器や根拠の判定基準を、目的指標と一緒に調整しない。
- 各試行は、使った評価データと評価方法のIDを記録する。
- 改善試行では調整用だけを使い、最終確認用は選んだ候補の確認まで使わない。
- 抽出方法を変えた試行でも、同じ評価データを使う。引用は評価対象のコーパス上で照合し直し、対応できなかった根拠は未回収として数える。
- 実際の改変防止は、ファイル権限や承認手順と組み合わせる。Dunlin 単独で完全な改変防止は保証しない。

### 11.5 試行の上限

エージェントに任せると、時間と外部APIの費用が読めなくなる。試行の回数、時間、外部APIの使用量の上限を設定で宣言できるようにする。上限に達した実行は、その旨を返して止まる。

### 11.6 エージェント向けの情報

| 情報 | 内容 |
| --- | --- |
| 設定できる項目の一覧 | 項目名、型、取り得る値、依存条件 |
| 構築の計画 | どの段階が実行されるか、変更の影響範囲、再利用の状況（`--dry-run`） |
| 評価レポート | 全体の指標と、質問別の成功・失敗・所要時間 |
| 実行の記録 | 検索、統合、文脈の組み立ての各段で何が起きたか |
| 検証の診断 | 誤った設定、欠けている成果物、不整合の理由 |

Dunlin の中に、エージェント固有の計画処理や会話履歴の管理は持たない。値の組み合わせをまとめて試す組み込みの一括試行は、初期の範囲に含めない（20章）。

## 12 文書の更新と提供内容への反映

文書が更新されたら、更新されたものだけを索引まで反映する。「文書の変更」と「構成の変更」を別の手続きとして扱う。

| 変わったもの | 手続き | 評価 |
| --- | --- | --- |
| 文書 | `build` を実行する。変更分が索引まで反映され、そのまま提供に使われる | 不要。鮮度の表示で知らせる |
| 構成（設定） | 試行として構築し、評価して比べ、`use` で採用する | 推奨。強制はしない |

### 12.1 文書が変わったとき

```bash
dunlin build --dry-run
dunlin build
dunlin status
```

- 追加、内容の更新、削除を区別して検出する。走査や取得に失敗した場合は不完全な走査として扱い、削除を確定しない。
- 変更のあった文書だけを、抽出から索引まで処理する。削除された文書は、新しい索引の対象から外す。
- リネームは削除と追加として検出する。内容が同じなら抽出結果は再利用するが、同じ文書が続いているとは見なさない。内容ハッシュだけで、評価の根拠や分割を自動で移し替えない。
- 更新した文書を参照している評価ケースの件数を表示する。評価データの状態は変えない。

### 12.2 提供に使う構成が固定するもの

採用中の構成が固定するのは、構築と検索の設定であって、索引の中身ではない。

- 索引の中身は、`build` のたびに最新の文書へ追従する。
- 評価した時点の索引に固定したい場合のために、明示的に固定する指定を後から足せるようにしておく。初期の範囲には含めない。

### 12.3 試行中に文書が更新された場合

設定を試している最中に文書が更新されると、索引が2系統あることになる。

- `build` は、採用中の構成の索引を必ず更新する。提供内容を古くしないためである。
- 試行の索引は、`--from` で前段を固定している限り更新されない。試行どうしの比較は、同じ原文のまま続けられる。
- 試行を新しい文書で評価し直すときは、`--from` を付けずに試行を構築し直す。

### 12.4 稼働中のサーバーへの反映

- サーバーは、設定を起動時のまま固定する。
- 完成した新しい索引には、要求の合間に切り替える。文書更新のたびに再起動を求めない。
- 新しい索引は別ファイルに作り、完成してから切り替える。構築途中の索引を読ませない。
- 更新が途中で失敗した場合は、古い索引を使い続ける。
- 採用する構成を `use` で変えた場合は、設定が変わるので再起動で反映する。

### 12.5 評価の鮮度

文書更新のたびに評価を要求しない代わりに、評価結果がどの時点の文書に対するものかを見せる。

`status` は次を表示する。

- 提供に使うビルドと検索設定、それに対応する評価の有無と指標（先頭に1行で）
- 最後の評価の後に更新された文書の件数
- 本体の設定と、採用中のビルドを作った設定の差分
- 飛ばしたファイルと理由
- 最後に情報源を確認した日時。走査していない原文を最新とは断定しない
- 評価データの陳腐化、位置が未解決の根拠、容量

## 13 LLM Wiki/PARA側の概要

Wiki/PARA側は、資料を読んで知識をページやノートに蓄積し、整理する系統である。書くのはAI、読んで指示するのが人、という役割を一貫させる。

### 13.1 コマンド

| コマンド | 役割 |
| --- | --- |
| `ingress` | 資料を受け取って保存し、読んでページやノートに反映する |
| `query` | ページやノートに対して質問し、出典付きの回答を得る |
| `verify` | 引用の実在、版の古さ、リンク切れ、文書間の不整合を検査する |
| `archive` | ページやノートをアーカイブへ移す、または戻す |
| `serve` | 構築したサイトをブラウザで閲覧し、指示を出せる画面を提供する |

入り口のコマンド名は `ingress` とする。LLM Wikiの文脈で定着している語は ingest であり、そろえるかどうかは未決である（21章）。

### 13.2 役割分担

| 役割 | 担い手 |
| --- | --- |
| 資料を選んで渡す、質問する、指示する | 人 |
| 資料を読む、ページやノートを書く、書き直す | AI（Dunlin が設定したモデルで実行する） |
| 引用の検証、保存、版の管理、作業の記録 | Dunlin |
| 読む | 人。HTMLとして読む |

- **実行役**: 指示を実行するのは、Dunlin が設定したモデルで行う方式を標準とする。画面だけで完結し、「入れれば解決」の軸に合う。
- **作業として記録する**: 指示はすべて「作業」として記録する。記録の部分を共通にしておくことで、実行役を後から外部エージェントに差し替えられる。
- **人は直接編集しない**: ページを直接編集する画面は置かない。修正も指示で行う。編集画面と引用検証の整合を考えずに済む。
- **画面とコマンドは同じ操作**: 画面でできることは、すべてコマンドでもできる。画面は同じ操作を呼ぶだけにする。

### 13.3 WikiとPARAの違い

|  | LLM Wiki | PARA |
| --- | --- | --- |
| まとまりの単位 | トピック別のページ | ノート |
| 階層の最上位 | トピックの区分 | Projects、Areas、Resources、Archives の4区分 |
| アーカイブ | 古くなったページを退避する | 終わったプロジェクトなどを Archives へ移す |
| トップの説明 | 各区分に何が入っているか | 4区分の説明と、進行中のプロジェクトの一覧 |

コマンド、画面の構成、出典の規則は両者で共通とする。

### 13.4 成果物

- ページとノートはHTMLで保存する。単体で読めるファイルとし、サーバーがなくても読めて、持ち出しもできる。
- 操作用の部品はページ本体に埋め込まない。`serve` の画面が外枠としてページを表示する。
- 取り込んだ原本は、版とともに保存する。ページが引用する版は、容量回収の対象から外す。

## 14 ingress、query、verify、archive の動作

### 14.1 ingress

```bash
dunlin ingress ./papers/maintenance-manual-v3.pdf
dunlin ingress ./inbox/
dunlin ingress --dry-run ./inbox/
```

`ingress` は次の順で進む。

1. 資料を受け取り、原本として版付きで保存する。
2. テキストを抽出し、根拠探し用のキーワード検索に加える。
3. 「未反映」として登録する。
4. AIが資料を読み、関連する既存ページを更新し、必要なら新しいページを作る。
5. 書いた内容の引用を検証し、通ったものだけを保存する。
6. 変更されたページの一覧と差分を返し、資料を「反映済み」にする。

- **範囲の判断**: トップの「目的と範囲」に照らし、範囲外の内容はページにしない。
- **反映の記録**: どの資料のどの版まで反映したかを残す。
- **資料の更新**: 同じ資料の新しい版を渡すと、古い版を引用しているページに改訂が必要な印を付け、改訂する。
- **取り消し**: 1回の `ingress` は複数のページを書き換える。作業単位で取り消せるようにする。
- **時間のかかる処理**: 数分かかり得るので、進行状況を表示する。複数の指示は順番に処理する。
- **原本だけを登録する指定**: 保存と未反映の登録までで止め、読み書きは後で行う指定を用意する。

### 14.2 query

```bash
dunlin query "フィルターの交換周期は"
```

- ページやノートを対象に検索し、出典付きの回答を返す。出典は、ページと、そのページが引用する原本の版と範囲まで辿れる。
- アーカイブ済みのページは、既定で対象から外す。
- 範囲外の質問には、対象外であると答える。
- 良い回答をページとして保存できる。保存時には、他のページと同じく引用を検証する。質問するほど資料が育つ。

### 14.3 verify

検査は2段に分ける。費用と確かさが大きく違うためである。

| 段 | 検査の内容 | LLM | 結果の性質 |
| --- | --- | --- | --- |
| 機械的な検査 | 引用が原文に実在するか、引用元の版が古くないか、リンク切れ、どこからも参照されないページ | 不要 | 確実。毎回同じ結果 |
| 内容の検査 | ページ同士の矛盾、新しい資料と既存ページの食い違い、同じ事柄の重複記述 | 必要 | 指摘の候補。誤検出がある |

```bash
dunlin verify
dunlin verify --content
```

- **既定は機械的な検査だけ**: 速くて費用がかからないので、`ingress` のたびに走らせられる。内容の検査は明示的に指定したときだけ実行する。
- **指摘は直さず、示すだけ**: 食い違う2か所の文章と、それぞれの引用元を並べて示す。どちらが正しいかは人が判断し、修正は指示で行う。
- **指摘の状態を記録する**: 未対応、対応済み、却下の状態を持たせる。「問題なし」と判断した指摘を毎回出さない。
- **比べる範囲を絞る**: 全ページの総当たりはページ数の2乗で増える。前回の検査以降に変わったページと、それに関連するページだけを比べる。
- **アーカイブ済みの扱い**: アーカイブ済みのページについては、版の古さを指摘しない。

### 14.4 archive

```bash
dunlin archive <ページ>
dunlin archive --restore <ページ>
```

WikiとPARAの両方で使う。アーカイブの意味は次のとおり。

- 目次と通常の `query` の対象から外れる。ページ自体は残り、読める。
- 他のページからのリンクは切れず、アーカイブ済みであることが表示される。
- 元に戻せる。
- PARAでは、終わったプロジェクトなどを Archives の区分へ移す操作に当たる。

## 15 画面（Wiki/PARA側の serve）

Wiki/PARA側の `serve` は、構築したサイトをブラウザで読み、取り込み・検査・アーカイブの指示を出せる画面を提供する。資料のHTMLを、指示のできる外枠の中に組み込んで表示する。

### 15.1 3列の構成

| 列 | 内容 | 補足 |
| --- | --- | --- |
| 左 | 資料の階層 | ページの階層を並べる。取り込んだ原本とアーカイブは別の項目に分ける |
| 中央 | コンテンツ | トップ、または開いたページやノート |
| 右 | チャット欄 | 質問と指示の入力、結果の表示、作業の履歴 |

- ページを読んでいる間もチャット欄が常に見えるので、「このページについて質問する」「このページを検査する」がその場でできる。
- 指示と結果が右側に時系列で並ぶので、作業の履歴を別枠に置かない。
- 原本とページを同じ階層に混ぜない。AIが書いたものと元の資料の区別を保つためである。
- 幅が足りない画面では、左の階層と右のチャット欄を折りたためる。
- PARAでは、左の階層の最上位が Projects、Areas、Resources、Archives の4区分になる。それ以外は同じ構成とする。

### 15.2 トップページ

トップは「この場所が何か」を最初に伝える。中央の列の最上部に説明を置き、その下に状態の件数と最近の更新を置く。

| 項目 | 内容 | 書き手 |
| --- | --- | --- |
| 目的と範囲 | 何のための場所で、何を扱い、何を扱わないか | 人。作成時に1〜2行で指定し、設定として保存する。AIは書き換えない |
| 構成 | 各区分に何が入っているかを1行ずつ | AI。取り込みやアーカイブのたびに更新する |
| 元になっている資料 | 取り込んだ資料の件数、種類、最終取り込み日 | AI |
| 使い方 | 質問と指示のしかた | 固定の案内 |
| 状態 | 未反映の資料の件数、未対応の指摘の件数 | Dunlin |
| 最近の更新 | 最近更新されたページ | Dunlin |

- **説明はAIへの方針を兼ねる**: 目的と範囲は、人向けの紹介であると同時に、AIが作業するときの基準になる。取り込み時の範囲の判断、区分の判断、範囲外の質問への応答に使う。人が読む説明とAIが従う方針を同じ文章にすることで、両者がずれない。
- **状態は次の行動への入口**: 未反映があれば取り込み、指摘があれば確認、と開いた時点で次にすべきことが分かる。件数から一覧へ移れる。
- **運用の決まり**: 区分の基準やページの書き方などの細かい決まりは、説明とは別のページとして持ち、トップからリンクする。

### 15.3 チャット欄

- **受け付ける範囲**: 入力は `ingress`、`query`、`verify`、`archive`、およびページの内容への指示（16章）のどれかに振り分ける。どれにも当たらない依頼は、できないと答える。範囲を広げると汎用のエージェントを作ることになり、非目標と衝突する。
- **1回ごとの指示として扱う**: 1つの入力が1つの作業になる。やり取りを重ねる会話にはしない。文脈として渡すのは、今開いているページと選択範囲だけとする。
- **対象の表示**: どのページ（または選択範囲）が対象になっているかを、入力欄の上に表示する。
- **よく使う操作はボタンにする**: 「資料を追加」「検査」は、入力しなくても押せるボタンにする。
- **結果の下に次の操作を置く**: 取り込みの結果には「変更を見る」「取り消す」、質問の回答には「引用元」「ページとして保存」を置く。
- **進行状況**: 時間のかかる作業は、実行中の表示と結果を返す。同時に来た指示は順番に処理する。

### 15.4 ページごとの操作

個々のページを開いたとき、次の操作をそのページに対して行える。

- このページの引用元を開く
- このページを検査する
- このページをアーカイブする
- このページについて質問する、または内容について指示する

中央のコンテンツで文章を選択すると、チャット欄の対象が「この部分」になる。対象の粒度は、ページ全体、節、選択した範囲の3段階とする。

## 16 内容への指示と出典の規則

人が直接編集しない前提では、ページの誤りを直す手段が指示しかない。そのため、ページの内容に対して指示を出せるようにする。ただし、指示の種類によって扱いを変える。

### 16.1 指示の種類と扱い

| 指示の種類 | 例 | 扱い |
| --- | --- | --- |
| 構成や表現の変更 | 短くして、表にして、2ページに分けて | そのまま実行する。新しい事実は足さず、引用は保つ |
| 資料に基づく修正 | この記述は資料と違う、もっと詳しく | 引用元を読み直して書き直す |
| 資料にない内容の追加 | 実際は3か月で交換している | 利用者の補足として記録し、それを出典にして書く |
| 資料と食い違う変更 | 交換周期を12か月に直して | 黙って上書きしない。食い違いを示し、補足として記録するか確認する |

### 16.2 出典の規則

- **すべての記述に出典がある**: ページやノートの記述は、原本の版と範囲を指す引用を持つ。保存時に引用の実在を検証する。
- **利用者の補足も資料として扱う**: 資料にない内容は、日付と指示者を付けた小さな資料として保存し、ページはそれを引用する。補足も他の資料と同じ仕組みで検証でき、後から「これは誰の判断か」を辿れる。
- **原本は書き換えない**: 指示で変えられるのは、AIが書いたページとノートだけとする。原本の誤りは、新しい版を取り込んで直す。引用が指す版と範囲がずれないようにするためである。
- **版を保持する**: ページが引用する原本の版は、新しい版が取り込まれた後も保持する。引用時の原文をいつでも辿れる。

### 16.3 その場の指示と、今後の決まり

| 種類 | 例 | 扱い |
| --- | --- | --- |
| その場の指示 | このページを表にして | 1回限りで実行する |
| 今後の決まり | 今後、手順は番号付きで書いて | 運用の決まりのページに追記し、その旨を返答で示す。以後のすべての作業に効く |

どちらの意味か区別がつかない指示は、確認する。

### 16.4 変更の確認と取り消し

- 内容への指示も、1件の作業として記録する。
- 完了時に、変更されたページの一覧と差分を見せる。
- 作業単位で取り消せる。取り込みのときと同じ仕組みを使う。

## 17 保存、並行実行、安全

### 17.1 保存

| 保存先 | 内容 |
| --- | --- |
| SQLite | 抽出テキスト、文書構造、チャンク本文、出典と位置、評価ケース、根拠対応表、設定の記録、工程キーと出力の対応、タグ、実行記録、作業の記録 |
| ファイル | 原本や画像などの大きなバイナリ、索引、ページやノートのHTML |

- 実体は内容単位で共有し、同じ内容を二重に持たない。抽出結果とチャンクはコーパスに1つだけ持つ（28.3節）。構築では、テキスト文書の原本ファイルを作らない（28.14節）。索引の本文に残る写しは、28.8節で扱う。
- 既存の記録と評価結果は上書きしない。
- 初期の版では自動の容量回収を行わず、容量を表示する。表示では、その記録だけが使う容量と他と共有する容量を分ける。
- 将来の容量回収では、採用中の構成、評価記録、タグ、ページの引用から参照されるものを保護する。

### 17.2 並行実行

- **長時間の処理だけを排他にする**: `build`、`eval`、`ingress` など、走査や計算を伴う処理は、プロジェクト単位で同時に1つとする。競合した場合は待たずにコード4を返す。
- **短い操作は妨げない**: タグ付け、評価データの取り込み、設定の変更などは、長時間の処理の実行中でも行える。試行を回しながら、完了した結果に名前を付けられる。
- **読み取りは常にできる**: `search`、`serve`、`status`、一覧表示、`--dry-run` は、書き込み中も動く。SQLiteはWALモードで使う。
- **長い処理をDBのトランザクションで囲まない**: OCRや外部APIの待ち時間を1つのトランザクションに含めない。成果物を完成させてから、参照を確定する。
- **実行開始時に入力を固定する**: 設定、タグ、入力を開始時に固定し、その後の変更を進行中の実行へ混ぜない。設定ファイルの直接編集も同じ扱いとする。
- **採用を上書きしない**: `build` の実行中に `use` で別の構成が採用された場合、完了した `build` は提供内容を自動で切り替えず、その旨を警告で返す。

### 17.3 秘密値

- APIキー本体、URLに含まれる資格情報、認証用のクエリ値を、設定の記録、ログ、出力に含めない。
- 環境変数名と、取り違えを防ぐための非秘密の接続先情報は保持する。
- エラーメッセージにも、生の秘密値を出さない。
- 外部のLLMへ送るデータの範囲を、設定で制御できるようにする。

### 17.4 画面の安全

ページはAIが資料から書いたHTMLであり、画面にはファイルを書き換える操作がある。資料に紛れ込んだ文字列が原因で、ページ内のスクリプトが勝手に操作を実行する事態を防ぐ。

- ページのHTMLからスクリプトを取り除くか、外枠から隔離して表示する。
- 操作の受け口は、画面からの正当な要求だけを受け付ける。
- 既定では、自分のPCからだけ接続できるようにする。
- 資料の本文に含まれる指示文を、利用者の指示として扱わない。AIが従うのは、チャット欄とコマンドからの指示、および運用の決まりだけとする。

### 17.5 外部コマンドの実行

`loader.command`（6.7）は、設定ファイルに書かれたコマンドを構築のたびに実行する。

- `Dunlinfile.yaml` は、実行するスクリプトと同じ信頼度で扱う。他人から受け取った設定で `build` する前に `source` を確認するよう、文書で案内する。`build --dry-run` は外部コマンドを起動せず、実行予定のコマンドを表示する。
- シェルを通さず、引数の配列のまま起動する。ファイル名に記号が含まれていても、コマンドとして解釈されない。
- 原本は一時ファイルの写しか標準入力で渡し、外部コマンドに原本を書き換えさせない。
- 画面や HTTP など、外部から届くファイルに対しては実行しない。このため、`loader.command` は Wiki/PARA の `ingress` では使えない。
- `env` に秘密値を直接書かず、`${ENV_NAME}` で参照する。設定の記録には展開前の値を残す（17.3）。

## 18 利用シナリオ

使い勝手を確かめるための場面を、7つ挙げる。コマンドの構文やタグ名は説明用である。

### 18.1 最初の5分: 手元のマニュアルをエージェントから引けるようにする

```bash
npm install -g dunlin
dunlin init mcp ./kb --source ~/manuals
cd kb
dunlin build
dunlin search "手順"
dunlin serve
```

- 構築が終わると、文書数、飛ばしたファイル、次に打つコマンドが表示される。
- フォルダに未対応のファイルが混ざっていた場合は、一覧と除外方法が表示され、`dunlin build --skip-unsupported` で進められる。
- エージェントへの登録は、接続設定を出力するコマンドの結果を貼り付ける。

### 18.2 月曜の朝、文書が更新されている

マニュアルが3件改訂され、1件が削除された。

```bash
dunlin build --dry-run
dunlin build
dunlin status
```

- 変更のあった4件だけが処理され、索引まで反映される。稼働中のサーバーは再起動なしで新しい索引を使う。
- `status` に「最後の評価の後に文書が4件更新されている」と出る。測り直すかどうかは利用者が決める。

### 18.3 検索が外れたので、評価を始める

「交換周期」で検索したのに、該当の節が上位に出なかった。

```bash
dunlin search "フィルターの交換周期"
dunlin eval-data add --question "フィルターの交換周期は" --doc manuals:maintenance.md --quote "フィルターは6か月ごとに交換する。"
dunlin eval --tag baseline
dunlin report show baseline
```

- 外れた検索をその場で評価ケースにする。数件たまったところで評価する。
- レポートに、どの質問で根拠を拾えなかったかが出る。
- 件数が増えたら、`eval-data split` で調整用と最終確認用に分ける。

### 18.4 改善をエージェントに任せる

評価ケースが50件ほどたまり、検索品質の改善を外部エージェントに依頼する。

```bash
# エージェントが繰り返す
dunlin report show baseline --json
dunlin validate --config candidates/trial-3.yaml --json
dunlin build --from transform --config candidates/trial-3.yaml --tag trial-3 --json
dunlin eval --build trial-3 --tag trial-3 --json
dunlin report compare baseline trial-3 --json

# 人が確かめて採用する
dunlin report compare baseline trial-3
dunlin eval --build trial-3 --split test --tag trial-3-test
dunlin use trial-3
```

- 試行の間、提供内容は変わらない。原文も固定されているので、設定の違いだけが比べられる。
- 人が見るのは「何を変えて、どれだけ良くなり、差は確かか」である。

### 18.5 資料からWikiを立ち上げる

```bash
dunlin init wiki ./wiki
cd wiki
dunlin ingress ~/manuals/maintenance-manual.pdf
dunlin serve
```

- 作成時に、目的と範囲を1〜2行で指定する。
- 取り込みが終わると、作られたページの一覧が返る。
- ブラウザで開くと、左に階層、中央に説明付きのトップ、右にチャット欄が並ぶ。

### 18.6 画面から資料を足し、検査する

1. チャット欄の「資料を追加」から、改訂版のマニュアルを渡す。
2. 完了すると「4ページを更新しました」と表示され、変更の確認と取り消しができる。
3. 「検査」を押すと、機械的な検査の結果が返る。
4. 内容の検査を指示すると、食い違う2か所が引用元付きで並ぶ。どちらが正しいかを判断し、修正を指示するか、却下する。

### 18.7 ページの内容に指示を出す

1. ページを開き、文章を選択して「この部分を表にして」と指示する。新しい事実は足されず、引用は保たれる。
2. 「実際は3か月で交換している」と指示する。利用者の補足として記録され、ページはそれを出典にして書き直される。
3. 「今後、手順は番号付きで書いて」と指示する。運用の決まりに追記され、その旨が返る。
4. 良い回答が得られた質問は、「ページとして保存」で残す。

## 19 実装の順序

「最速で構築できる」の軸に合わせ、標準構成で動くものを先に通す。拡張の枠組みは、動くものから切り出す。

### 19.1 RAG/MCP側

| 段階 | 範囲 | 確かめること |
| --- | --- | --- |
| 1 | `init`、`build`（`source`、`transform`、`index`）、キーワードの `search`、`serve`、未対応ファイルの扱い、`status` | 3コマンドで検索に届くか。2文字の問い合わせが通るか |
| 2 | 差分更新、`build --from` / `--until` / `--force` / `--dry-run`、再利用の仕組み、稼働中サーバーへの反映 | 変更分だけが処理されるか。途中から実行できるか |
| 3 | `eval-data add` と最小形式の取り込み、位置対応の自動作成、`eval`、`report show` / `list` | 引用が一意に一致する割合。文脈予算に届かないケースの割合 |
| 4 | 試行（`--config`、`--tag`）、`report compare` と統計、`use`、分割、機械可読の出力一式 | 外部エージェントが繰り返しを回せるか |
| 5 | 埋め込みとベクトル索引、評価データの生成・確認・同期、位置対応の対話確認 | — |
| 6 | 持ち運び（書き出しと復元）、容量回収、URLからの取得、追加の検索方式 | — |

段階3まで動いた時点で、実際の文書を使って次の値を測る。紙の上では決められない項目である。

- 引用が一意に一致する割合
- 文脈予算に届かないケースの割合
- 根拠の回収判定の閾値と、2文字検索の妥当性

### 19.2 Wiki/PARA側

| 段階 | 範囲 |
| --- | --- |
| 1 | `init`、`ingress`（保存、抽出、反映、引用の検証）、HTMLの出力、作業の記録と取り消し |
| 2 | `serve`（3列の画面、トップの説明、チャット欄）、`query`、回答のページ保存 |
| 3 | `verify` の機械的な検査、`archive`、内容への指示、利用者の補足、運用の決まり |
| 4 | `verify` の内容の検査、指摘の状態管理、資料の更新に伴う改訂 |

### 19.3 順序についての方針

- 最初に出すのはRAG/MCP側の段階1とする。
- 共有する内部部品（原本の保存、抽出、引用の検証）は、RAG/MCP側の実装で作ったものをWiki/PARA側で使う。
- 拡張のための契約（外部モジュール、差し替え可能な検索エンジン）は、標準構成が使われてから決める。利用者がいない段階の契約は外しやすい。
- データの識別子、位置対応表、実行記録の形式は、初版から持つ。後から変えると過去の記録との互換性が壊れる。

## 20 非目標

3つの軸のどれにも必要でないものは、作らないか後続に回す。

| 項目 | 扱い |
| --- | --- |
| Dunlin 内の汎用的な最適化エージェント | 作らない。探索は外部エージェントが担う |
| 包括的なエージェントの枠組み | 作らない。Wiki/PARA側のチャット欄も、決まった操作に限る |
| 値の組み合わせをまとめて試す組み込みの一括試行 | 初期の範囲に含めない。途中からの構築と評価を外から繰り返す |
| 提供構成の検証必須化 | しない。評価は鮮度の表示であり、関門ではない |
| 回答の自然言語生成を必須にすること | しない。検索結果は根拠と出典を中心に返す |
| 特定のベクトルDBや検索技術への固定 | しない |
| 利用者ごとの権限制御と権限漏れの検証 | 初期の範囲外。手元の資料を1人または小さなチームで使う前提とする |
| 種別 mcp でのHTTPによる公開（種別 rag の serve はHTTPで提供する） | 後続 |
| 外部モジュールや外部検索エンジンの差し替え | 後続。標準構成が使われてから決める |
| 多段の探索 | 後続 |
| 大規模な分散検索サービス | 対象外 |
| ゲートウェイの認証、監査、ルーティングの再実装 | しない |
| 多数の小さなパッケージへの分割 | しない。1つのパッケージで提供する |

## 22 受け入れ条件

### 22.1 最速で構築できる

- 文書フォルダを指定し、`init`、`build`、`search` の3コマンドでキーワード検索に到達できる。
- 設定ファイルを編集しなくても、標準構成で構築と提供ができる。初期化で書き出された設定に、標準構成で使うモジュールと引数がすべて書かれている。
- 未対応ファイルで止まったときに、対象の一覧と除外方法が示され、明示して検索へ進める。
- 「手順」のような2文字の日本語の問い合わせで、該当文書を検索できる。
- 分かち書きした日本語の自然文で該当文書を検索でき、ユーザー辞書を登録したビルドでは専門用語を登録した単位で扱える。
- 未使用のLLMに、認証や接続を要求しない。

### 22.2 入れれば解決

- 1つのパッケージの導入だけで、別のデータベースや検索サーバーなしに動く。
- RAG/MCP側とWiki/PARA側のどちらも、同じパッケージから初期化できる。
- エージェントへの登録に必要な接続設定を、コマンドで出力できる。

### 22.3 構築と再利用

- 文書が更新されたとき、`build` の1回で変更分だけが索引まで反映される。
- `build --from transform` が、情報源を走査せずに既存の出力から実行される。
- 個別の段階コマンドが、前段を暗黙に実行しない。
- チャンク設定の変更で抽出をやり直さない。トークナイザだけの変更で埋め込みを再計算しない。
- 検索設定だけの変更で、ビルドIDが変わらない。
- 出力互換性を維持する依存更新で、再利用が無効にならない。
- 走査の失敗を削除と誤認しない。
- 後続の段階が失敗しても、成功した段階の出力を失わない。

### 22.4 提供と採用

- 構築途中の索引を、`search` や `serve` が読まない。
- 稼働中のサーバーが、再起動なしに新しい文書の索引を使う。
- タグや候補設定を指定した試行のビルドが、提供内容を変えない。
- `search` と `serve` の既定の対象が一致する。
- `use` の後に素の `build` を実行しても、採用前の構成に戻らない。
- `status` の先頭だけで、提供に使うビルド、検索設定、評価の状態を確認できる。

### 22.5 評価

- 質問、文書のパス、引用だけで評価ケースを追加でき、そのまま評価へ進める。
- 一致しない引用や複数箇所に一致する引用を、取り込み時に知らせる。
- `eval` が構築を暗黙に実行しない。
- チャンク設定の違うビルドを、同じ文脈予算と組み立て方で比較できる。小さいチャンクが検索件数の上限で不利にならない。
- `search`、MCPの応答、評価が、同じ検索設定に対して同じ文脈を組み立てる。
- あいまい一致だけで対応づけた位置が、人の確認なしに採点へ使われない。
- 位置が未解決の根拠を未回収と数えるスコアが既定であり、診断用のスコアと区別される。
- ケースの追加、分割の変更、無関係な文書の追加で、人が確認した位置対応が失われない。
- ビルドを指定した評価の一覧で、構築系の列がそのビルドを作った設定から表示される。
- 評価データ、評価方法、対象ケースが違う結果を、単純な改善率として表示しない。
- 最終確認用の分割は明示したときだけ使われ、使用回数が記録される。
- タグの付け替えで、過去の記録の参照先が変わらない。

### 22.6 Wiki/PARA側

- 保存されるすべての記述が、実在する引用を持つ。検証に通らない記述は保存されない。
- 資料にない内容の追加が、利用者の補足として記録され、出典として辿れる。
- 指示で原本が書き換わらない。
- ページが、サーバーなしで単体のHTMLとして読める。
- 画面でできる操作が、すべてコマンドでもできる。
- 1回の指示による変更を、差分で確認でき、作業単位で取り消せる。
- 既定の `verify` がLLMを呼ばずに完了する。
- 却下した指摘が、次の検査で再び未対応として出ない。
- アーカイブしたページが目次と通常の質問の対象から外れ、リンクは切れず、元に戻せる。
- トップの「目的と範囲」をAIが書き換えない。
- ページ内のスクリプトから、画面の操作を実行できない。

### 22.7 運用

- 長い処理の実行中も、タグ付けと評価データの取り込みができる。
- ロックや同時更新の競合を、コード4と構造化されたエラーで識別できる。
- すべての操作が非対話で完結し、終了コードとスキーマ版付きの出力で成否と出力IDを判定できる。
- APIキーやURL内の資格情報が、記録、ログ、出力に漏れない。
- 容量の表示で、共有されている分とそうでない分が区別される。

## 23 検討の経緯: 途中で変更した決定

以前の文書と食い違う点を、変更の理由とともにまとめる。古い文書を読むときは、この表で読み替える。

### 23.1 全体

| 以前の案 | 現在の決定 | 理由 |
| --- | --- | --- |
| 名前は durlin、コマンドは `durlin rag ...` | 名前は Dunlin、コマンドは最上位に平らに置く | 正式名の確定。系統は `init` の種別で決まるため、用途名を毎回付けなくてよい |
| RAGを設定違いでたくさん試すためのCLI | 最速で構築できるナレッジ基盤。MCPとRAGに加え、LLM WikiとPARAも支える | 位置づけの確定（3つの軸） |
| 共通の構築を4つの用途が共有する | 取り込みの入り口から2系統に分ける。共有するのは内部部品だけ | 「索引を作る」と「読んでページに反映する」は性質が違う |
| `init` で用途を1つ選び、同じコーパスを共用する | 作業ディレクトリを系統ごとに分ける。同じ資料は両方に渡す | 入り口を分ける決定に合わせた |
| 標準構成は設定に書かず、変えたい箇所だけを書く | 標準構成でも、使うモジュールと引数をすべて書き出す。区切りごとにモジュールと引数を並べる | 中が見えない箱にしない。分からない利用者は触らず、分かる利用者は踏み込める |
| RAG/MCP側の種別は rag の1つ | mcp と rag に分ける。mcp は search、rag は ask、wiki と para は query を使う | 回答を作るのがエージェントか Dunlin かを、種別で区別するため |

### 23.2 RAG/MCP側

| 以前の案 | 現在の決定 | 理由 |
| --- | --- | --- |
| 工程は抽出、チャンク、埋め込み、索引の4つ | 利用者に見せる段階は `source`、`transform`、`index` の3つ。内部の再利用はより細かい | 操作の粒度を単純にする |
| 構築の入り口は `ingest` | `build`。`ingest` の語はWiki/PARA側のもの | LLM Wikiの文脈での意味と衝突する |
| 後ろの段階が前段を自動で実行する | `build` がまとめて実行し、個別の段階は前段を実行しない | `build` ができたので、暗黙の実行は不要になった |
| `--from` は「指定工程以降の強制再実行」、後に `--rerun-from` | `--from` は「その段階から実行。前段は既存の出力を使う」。強制は `--force` を併用 | 原文を固定した試行に使うため |
| 評価は必要なら構築を暗黙に実行する | `eval` は構築しない。古ければ表示する | 「作る」と「測る」を分ける |
| 最終検証を通った構成だけを公開する（`verify`、`publish`、release） | 評価は関門にしない。試行は `use` で採用する | 文書更新のたびに評価を通すのは重すぎる |
| 提供構成は索引そのものを固定する | 固定するのは設定。索引の中身は文書に追従する | 文書の変更をすぐ提供に反映するため |
| サーバーは起動時のビルドを使い続け、更新は再起動 | 設定は固定し、新しい索引には要求の合間に切り替える | 文書更新のたびの再起動は不便 |
| 組み込みの最適化（`optimize`）、後に一括試行（`sweep`） | 初期の範囲に含めない。外部エージェントが途中からの構築と評価を繰り返す | 探索の判断は外に置き、Dunlinは実行と測定に徹する |
| 一時上書き `--set` | 候補の設定ファイルを `--config` で指定する | 試行の設定をファイルとして残し、本体を書き換え続けないため |
| チャンク単位の指標（recall、nDCG） | 根拠単位の指標。文脈量をそろえて比べる | チャンク設定が違うと公平に比べられない |
| 根拠はあいまい一致で照合する | 採点は確定した位置で行い、あいまい一致は候補探しにだけ使う | 似た文章や定型文の誤認を避ける |
| 位置対応表のキーは評価データとコーパスの組 | 根拠1件と文書の抽出結果の組を単位に再利用する | 人が確認した結果を、無関係な変更で失わないため |
| 依存ライブラリの版を再利用キーに含める | 工程ごとの出力互換性バージョンを使う | 更新のたびに全体が無効になるのを避ける |
| 検索件数で文脈を作る | 文脈予算を満たすまで候補を取る | 小さいチャンクが不利にならないようにする |
| 対応外ファイルは停止のみ | 停止が既定。明示的に飛ばす指定を用意する | 最初の構築で止まりやすい |
| 評価データは完全形式のJSONL | 質問、文書、引用だけの最小形式と、1件追加のコマンド | 手で書ける形でないと評価まで届かない |
| ロックはすべての書き込みを排他 | 長時間の処理だけを排他にし、短い操作は妨げない | 試行中に名前付けなどができないのは不便 |

### 23.3 Wiki/PARA側

| 以前の案 | 現在の決定 | 理由 |
| --- | --- | --- |
| ページを書くのは外部エージェント。DunlinはMCPで編集機能を提供する | 標準はDunlinが設定したモデルで実行する。指示は作業として記録する | 画面のチャット欄から指示して完結させるため |
| `serve` はMCPで編集機能を提供する | `serve` はブラウザ向けの画面を提供する | 読むことと指示することを1か所で行う |
| 取り込みはMCPの操作として置き、CLIには置かない | CLIに `ingress` を置く | 入り口を系統ごとに分ける決定 |
| チャット欄をトップの最上部に置く2列構成 | 左に階層、中央にコンテンツ、右にチャット欄の3列構成 | ページを読みながら指示できる |
| トップは状態と最近の更新 | 最上部に説明（目的と範囲、構成）を置く | 「この場所が何か」を最初に伝える |
| `verify` は引用の検証 | 文書間の不整合も検査する。機械的な検査と内容の検査の2段 | ページ同士の矛盾を見つけたい |
| `archive` はPARAの操作 | Wikiでも使う | 古いページを退避する手段が要る |

## 24 モジュール一覧（案）

標準的に必要なモジュールを、区切りごとにまとめる。「標準」は `init` が書き出す構成に含まれ、本体だけで動くもの。「追加」は利用者が設定に書き足して使うものである。モジュール名は案とする。

### 24.1 source（取得と抽出）

| モジュール | 役割 | 区分 | 必要なもの |
| --- | --- | --- | --- |
| `source.filesystem` | フォルダを走査し、追加・更新・削除を検出する | 標準 | なし |
| `loader.auto` | ほかのパーサが受け持たなかったファイルの種類を判定し、下の標準のパーサに振り分ける。未対応形式の扱いを決める | 標準 | なし |
| `loader.text` | テキスト、Markdown、HTMLを読む。見出しの構造を保持する | 標準 | なし |
| `loader.office` | Word、Excel、PowerPointを読む。見出し、表、スライドの区切りを保持する | 標準 | なし |
| `loader.pdf` | テキスト層のあるPDFを読む。ページ番号を保持する | 標準 | なし |
| `loader.ocr` | 画像と、テキスト層のないPDFを文字認識で読む | 追加 | 文字認識のモデル |
| `loader.command` | `match` に一致したファイルを、利用者が指定した外部コマンドで読む（6.7） | 追加 | 外部コマンド |

- パーサは上から順に照合し、最初に受け持ったものが読む。標準のパーサも `match` で受け持つ範囲を絞れる（6.7）。
- パーサはすべて、抽出したテキストが原本のどこにあったか（ページ、見出し、セル範囲など）を記録する。出典の表示と評価の位置対応がこれに依存する。
- テキスト層のないPDFを `loader.pdf` だけで読むと、中身が空になる。空の抽出結果は警告として表示し、`loader.ocr` の追加を案内する。
- Excelの表をどうテキストにするか（行ごと、シートごと）は、検索の当たりやすさを左右する。引数で選べるようにする。

### 24.2 transform（前処理とチャンク化）

| モジュール | 役割 | 区分 | 必要なもの |
| --- | --- | --- | --- |
| `text.normalize` | 全角半角や空白などの表記をそろえる。元の位置へ戻せる対応を保つ | 標準 | なし |
| `chunk.length` | 長さで分ける。段落や文の切れ目を優先し、重なりを指定できる | 標準 | なし |
| `chunk.structure` | 見出し、表、スライドなど文書の構造で分ける | 追加 | なし |
| `chunk.semantic` | 意味の切れ目で分ける | 追加 | 埋め込みモデル |

- チャンクは、コーパス上の範囲を必ず持つ。どの分け方でも、本文を書き換えず範囲だけを決める。
- `chunk.structure` は一覧になかったが、候補として加えた。マニュアルのような見出しのある文書では効果が出やすく、モデルも要らない。
- `chunk.semantic` は構築時に埋め込みを計算するので、時間と費用がかかる。結果はモデルに依存するため、再利用キーにモデルの識別情報を含める。

### 24.3 index（索引）

| モジュール | 役割 | 区分 | 必要なもの |
| --- | --- | --- | --- |
| `index.keyword` | キーワード索引を作る。BM25の検索がこれを使う | 標準 | なし |
| `index.vector` | チャンクの埋め込みを計算し、ベクトル索引を作る | 追加 | 埋め込みモデル |

- `index.keyword` のトークナイザは引数で指定する。日本語ではこの選択が検索の当たり方を大きく変える。
- 埋め込みは `index.vector` の中で計算し、チャンク単位で再利用する。独立したモジュールにはしない。
- 標準のベクトル検索は総当たりとし、本体に実装する（25章）。別のデータベースを立てさせない。

### 24.4 search（検索と文脈）

| モジュール | 役割 | 区分 | 必要なもの |
| --- | --- | --- | --- |
| `query.normalize` | 問い合わせの表記を、索引と同じ規則でそろえる | 標準 | なし |
| `retrieval.keyword` | BM25でキーワード索引を検索する | 標準 | `index.keyword` |
| `retrieval.vector` | 問い合わせを埋め込み、ベクトル索引を検索する | 追加 | `index.vector` と同じ埋め込みモデル |
| `fusion.rrf` | キーワードとベクトルの結果を1つの順位にまとめる | 追加 | 2つ以上の検索モジュール |
| `rerank.model` | 候補をモデルで並べ直す | 追加 | 再ランク付けのモデル |
| `context.assemble` | 重複を統合し、文脈予算の範囲で渡す文脈を組み立てる | 標準 | なし |

- `fusion.rrf` は一覧になかったが、キーワードとベクトルを併用するには必要になる。
- `retrieval.vector` を書いて `index.vector` がない、といった組み合わせは、検証でエラーにする。索引と検索で埋め込みモデルが違う場合も同じとする。
- `rerank.model` は問い合わせのたびにモデルを呼ぶので、検索が遅くなる。評価の速度の指標と並べて効果を判断する。並べ直す候補数は引数で指定する。
- 候補の順位を変えるモジュールは、本文を書き換えない。文脈の位置追跡を保つためである。

### 24.5 標準構成と、よくある拡張

| 構成 | source | transform | index | search |
| --- | --- | --- | --- | --- |
| 標準 | フォルダ、テキスト、Office、PDF | 正規化、長さチャンク | キーワード | BM25、文脈の組み立て |
| スキャン文書を含む | 標準 + OCR | 標準 | 標準 | 標準 |
| 意味検索を足す | 標準 | 標準 | キーワード + ベクトル | BM25 + ベクトル + 統合 |
| 精度を優先する | 標準 | 構造または意味のチャンク | キーワード + ベクトル | 上記 + 再ランク付け |

### 24.6 モジュール全般の決まり

- **入出力の型を宣言する**: 各モジュールは、受け取るものと返すものの型を持つ。区切りの中で型がつながらない並びは、検証でエラーにする。
- **必要なものを宣言する**: モデルや他のモジュールへの依存を持つ。満たされていない場合は、何を足せばよいかを示す。
- **出力互換性バージョンを持つ**: 出力が変わる変更でこの番号を上げ、再利用の判定に使う（7章）。
- **一覧と説明をコマンドで返す**: 名前、役割、引数と既定値、入出力の型、必要なものを、人向けと機械可読の両方で出力する。
- **モデルを使うモジュールの実行方式は未決**: 文字認識、埋め込み、再ランク付けはモデルを必要とする。外部の実行環境やAPIに任せるか、Dunlin が自分でモデルを取得して動かすかを決める必要がある（21章）。

評価のモジュール（根拠の回収率、速度）と、Wiki/PARA側のモジュール（執筆、引用の検証、各種の検査）は、5.5節と13.5節の設定例に現れるものを出発点とし、別途一覧にする。

## 25 標準の保存先とツールの追加

標準の保存先と索引は本体に同梱し、導入した時点で動くようにする。それ以外への切り替えは、後から `dunlin add` でツールを足して行う。

### 25.1 標準の構成

| 役割 | 標準 | 備考 |
| --- | --- | --- |
| 記録（状態、抽出結果、チャンク、評価データ） | SQLite | 本体に同梱する |
| キーワード索引 | Tantivy | RAG/MCP の標準は同梱の Lindera と IPADIC で日本語を分かち書きする |
| ベクトル検索 | 総当たりの検索を本体に実装する | 外部のライブラリに依存しない |

ベクトル検索を総当たりで自作する理由は次のとおり。

- **作る量が小さい**: 必要なのは、ベクトルを並べたファイル、距離の計算、上位の選別だけである。
- **Dunlin の決まりをそのまま実現できる**: 索引を別ファイルの不変な成果物にする、差分だけ更新する、同じ入力なら同じ結果になる、といった決まりを、外部の部品の都合に合わせずに済む。
- **評価が素直になる**: 総当たりは正確なので、検索結果の違いを設定の違いだけで説明できる。近似による揺れが混ざらない。
- **配布が楽になる**: 依存が増えず、事前にビルドした本体を配りやすい。

### 25.2 自作する範囲と、しない範囲

|  | 内容 |
| --- | --- |
| 自作する | 総当たりのベクトル検索。ベクトルを1つのファイルに `f32` で連続して並べ、メモリマップで読む。候補数と次元数に応じて内積計算を並列化する |
| 自作しない | 近似探索（グラフや木を使う方式）。正しく速く作るのは難しく、保守の負担も大きい |
| 将来の余地 | 件数が増えたときのために、ベクトルを小さい型に丸めて持つ選択肢を残す |

標準の総当たり検索は対象の行を `f32` の内積で走査する。丸め誤差の上限を使って上位に入り得る候補を残し、元の問い合わせベクトルを使って `f64` で再計算する。最終順位と返却スコアは従来の `f64` の計算にそろえる。同点は索引の行番号順とする。全候補が要求件数以内の場合や、問い合わせの成分を有限の `f32` に変換できない場合は、直接 `f64` で計算する。

中断は処理の開始時、計算ブロックの開始時、走査・再計算・最終選別の区切りで確認する。計算ブロックは次元数に応じて最大256行かつ65,536要素とする。中断を検知した場合は `ABORTED` を返す。

近似探索が必要な規模になった利用者は、既存のライブラリを追加先として使う。現時点の第一候補は hannoy とする。追加と削除に追従できる点が差分更新と合う。ベータ段階なので、組み込む時点で改めて状況を確かめる。

### 25.3 差し替えを簡単にする前提

- **差し替えられるのは索引だけ**: 原文、抽出結果、チャンク、評価データは、常に Dunlin 自身の保存領域に置く。
- **索引はいつでも作り直せる**: 索引はチャンクから再構築できるので、保存先を切り替えてもデータの移行は要らない。
- **決まった口を通して呼ぶ**: 索引の作成と検索は、内部の決まった口を通す。標準の実装も、その口の1つとして作る。

### 25.4 dunlin add

```bash
dunlin add --list
dunlin add hannoy
dunlin add ocr          # tools に記録された OCR の方式を準備する
dunlin add oar-ocr
dunlin add lightonocr
dunlin remove hannoy
```

- **1つのツールが複数のモジュールを提供する**: 追加すると、そのツールのモジュールが一覧に現れ、設定ファイルで使えるようになる。
- **設定ファイルに記録する**: 追加したツールの名前と版を設定ファイルに書く。使うものをすべて書き出す方針と同じで、別の環境でも同じ構成を再現できる。
- **構成の書き換えは利用者が行う**: 追加しただけでは構成は変わらない。該当する区切りに書くべき内容を表示する。
- **入手元を限定する**: 外部のコードを実行することになるので、最初は公式の一覧にあるものだけを対象にする。版を固定し、取得したものの整合性を検証する。
- **モデルを使う機能も同じ経路で足す案**: 文字認識、埋め込み、再ランク付けの実行環境も、`dunlin add` で追加する形を候補とする。本体は軽いままで、別の道具を自分で導入する必要もなくなる。

設定ファイルへの記録と、切り替え後の区切りの例を示す。名前とキーは案である。

```yaml
# 追加したツール
tools:
  - name: hannoy
    version: 0.2.0

index:
  modules:
    - use: index.keyword
      with:
        tokenizer: lindera
        user_dictionary: null
    - use: hannoy.index           # 標準の index.vector から切り替え
      with:
        model: local-embed
```

設定を書き換えた後、`dunlin build --from index` を実行すれば、索引だけが作り直される。試行として構築して評価し、標準の索引と比べてから採用することもできる。

### 25.5 切り替えの目安

- 検索の所要時間は評価の指標に含まれる。総当たりが遅くなってきたら、切り替えを案内する。
- どの件数まで総当たりで実用になるかは、実際に測って決める。実装の早い段階で測る項目とする。

## 26 モジュールの仕様

すべてのモジュールは、同じ宣言、同じ生成の手続き、同じ実行口に従う。設定ファイルの `use` に書かれた名前と `with` の辞書から、共通の手続きでインスタンスを作る。名前や引数が正しくないときの振る舞いも、モジュールによらず一貫させる。

### 26.1 モジュールが宣言するもの

| 項目 | 内容 |
| --- | --- |
| 名前 | 「種類.名前」の形。設定ファイルの `use` に書く名前 |
| 版 | 出力互換性バージョン。出力が変わる変更で上げる |
| 所属する区切り | どの区切りで使えるか |
| 役割 | 区切りの中での役割（パーサ、チャンク作成、索引作成、候補の取得、文脈の組み立てなど） |
| 入力と出力の型 | 受け取るものと返すもの |
| 引数 | 名前、型、既定値、取り得る範囲、説明 |
| 引数ごとの影響 | 結果を変える引数か、速度だけを変える引数か |
| 必要なもの | モデルの種別、対になるモジュール、追加のツール |
| 性質 | 同じ入力で同じ結果になるか。外部を呼ぶか。処理の単位は文書ごとか全体か |

結果を変える引数だけを、再利用の判定に使う。並列数のような引数を変えても、作り直しにならない。

### 26.2 区切りの間を流れる型

| 型 | 中身 | 作る区切り |
| --- | --- | --- |
| 原文集合 | 原本とその版 | `source` |
| コーパス | 抽出したテキスト、構造、原本上の位置 | `source` |
| チャンク集合 | コーパス上の範囲の集まり | `transform` |
| 索引 | 検索用の構造 | `index` |
| 候補列 | 順位の付いたチャンクの並び | `search` |
| 文脈 | 渡す文章と、元の範囲への対応 | `search` |

型の種類は増やしすぎない。型が増えるほど、つなぎ方の組み合わせが増える。

### 26.3 すべてのモジュールが守る約束

- **位置を失わない**: 出力のどの部分も、原本のどこから来たかを辿れる。出典の表示と評価がこれに依存する。
- **入力を書き換えない**: 受け取ったものは変更せず、新しい出力を返す。
- **宣言していない外部呼び出しをしない**: 費用の見積もりと、外部へ送るデータの制御のためである。
- **失敗を黙って握りつぶさない**: 処理できなかった対象と理由を返す。
- **エラーの文面を自分で作らない**: 共通のエラーの型で返す（26.8節）。

### 26.4 区切りの中の並びの決まり

- 前のモジュールの出力の型が、次のモジュールの入力の型とつながること。
- 区切りごとに、必ず要る役割があること。
- 同じ役割を複数置けるかどうかが、役割ごとに決まっていること。

| 区切り | 必ず要る役割 | 複数置ける役割 |
| --- | --- | --- |
| `source` | 情報源、パーサ（各を1つ以上） | 情報源、パーサ |
| `transform` | チャンク作成（1つ） | 前処理 |
| `index` | 索引作成（1つ以上） | 索引作成 |
| `search` | 候補の取得（1つ以上）、文脈の組み立て（最後に1つ） | 問い合わせの前処理、候補の取得、並べ直し |

候補の取得を2つ以上置いた場合は、結果をまとめるモジュールが必要になる。

### 26.5 生成の仕組み

実行時のリフレクションの代わりに、名前から生成関数を引く登録表を使う。

| 部品 | 役割 |
| --- | --- |
| 登録表 | モジュール名から、そのモジュールの「説明」と「生成関数」を引く |
| 説明 | 26.1節の宣言内容。インスタンスを作らずに取得できる |
| 生成関数 | 引数の辞書を受け取り、インスタンスを返す |
| 共通の実行口 | エンジンがすべてのモジュールを同じ呼び方で実行する |

- **引数は、外は辞書、中は型**: 辞書で受け取り、生成時に型付きの構造へ変換する。以後は型で扱い、辞書を内部で持ち回らない。
- **引数の定義を唯一の正本にする**: 同じ定義から、検証、説明の出力、`init` が書き出す標準構成を作る。説明と実際の動作がずれない。
- **説明はインスタンスなしで取れる**: 検証や事前確認のたびにモデルを読み込む作りにしない。
- **登録はモジュール側で行う**: 各モジュールが自分を登録表に載せる。中央の一覧を手で保守しない。

### 26.6 実行口

実行口は2種類とし、それぞれの中で統一する。構築と検索は性質が違うので、1つの口に押し込まない。

| 種類 | 使う区切り | 形 | 性質 |
| --- | --- | --- | --- |
| 構築モジュール | `source`、`transform`、`index` | データを受け取り、データを返す | まとめて処理する。結果を再利用する |
| 検索モジュール | `search` | 検索の状態を受け取り、更新した状態を返す | 問い合わせごとに動く。速さが重要 |

検索側は、問い合わせ、候補列、文脈をまとめた「検索の状態」を順に渡す。正規化、取得、統合、並べ直し、文脈の組み立てがすべて同じ形になる。

実行時には、モデルの解決、保存先、進捗の報告、中断、費用と時間の上限を、共通の文脈として渡す。

### 26.8 名前や引数が正しくないときの振る舞い

どのモジュールでも、どのコマンドからでも、同じ誤りは同じコードと同じ形式で報告する。

**基本の決まり**

- **実行の前にすべて検証する**: `build`、`eval`、`search`、`serve` は、処理を始める前に `validate` と同じ検証を行う。設定の誤りが、時間のかかる処理の途中で見つかることがない。
- **見つかった問題を一度に列挙する**: 最初の1件で止めず、検証できる範囲の問題をすべて返す。
- **黙って無視しない、黙って直さない**: 知らないキーを読み飛ばさない。型の違う値を勝手に変換しない。範囲外の値を丸めない。
- **終了コードをそろえる**: 設定の誤りはコード2、検証を通った後の実行時の失敗はコード1とする。
- **検証はエンジンの1か所で行う**: 型、範囲、知らないキーの検査は、引数の定義をもとにエンジンが行う。モジュールが独自に検査するのは、引数同士の組み合わせのように定義で表せないものだけで、その結果も共通のエラーの型で返す。

**エラーの種類**

| コード | 状況 | 添える案内 |
| --- | --- | --- |
| `MODULE_UNKNOWN` | 登録表にない名前 | 近い名前の候補。追加ツールのモジュールなら `dunlin add` の案内 |
| `MODULE_WRONG_STAGE` | その区切りでは使えないモジュール | 使える区切り |
| `ARG_UNKNOWN` | 定義にない引数 | 近い引数名の候補、使える引数の一覧 |
| `ARG_MISSING` | 既定値のない必須の引数がない | 引数の型と例 |
| `ARG_TYPE` | 型が違う | 期待する型と、受け取った値 |
| `ARG_RANGE` | 範囲外、または選択肢にない値 | 取り得る範囲や選択肢 |
| `ARG_CONFLICT` | 引数同士の組み合わせが成り立たない | 衝突している引数と理由 |
| `TYPE_MISMATCH` | 並びの前後で型がつながらない | 前の出力の型と、次の入力の型 |
| `ROLE_MISSING` | 必ず要る役割のモジュールがない | その役割を持つモジュールの例 |
| `ROLE_DUPLICATE` | 1つだけの役割が複数ある | 重複しているモジュール |
| `REQUIREMENT_MISSING` | 必要なモデルや対のモジュールがない、種別が合わない | 何をどこに足せばよいか |
| `SECTION_MISSING` | 必須の区切りがない | 標準構成を再出力する方法 |
| `VERSION_UNSUPPORTED` | 設定やツールが要求する版を満たせない | 必要な版と現在の版 |
|  |  |  |

**エラーが持つ情報**

すべてのエラーは、次の項目を同じ形で持つ。

| 項目 | 内容 |
| --- | --- |
| コード | 上の表のコード |
| 場所 | ファイル、行、区切り、モジュール名、引数名 |
| 受け取った値 | 実際に書かれていた値。秘密値は伏せる |
| 期待 | 型、範囲、選択肢など |
| 候補 | 近い名前があればその候補 |
| 直し方 | 1行の案内 |

```text

  MODULE_UNKNOWN  この名前のモジュールはありません。

Dunlinfile.yaml:35  search > retrieval.keyword > top_k
  ARG_TYPE  整数が必要ですが、文字列 "ten" が書かれています。
  期待: 1 以上の整数
```

**警告**

実行を止めない問題は、同じ形式の警告として返す。

- 古い引数名や、廃止予定のモジュールを使っている。
- 文脈予算に届きにくい組み合わせになっている。
- 結果を変える引数が省略され、モジュールの既定値に頼っている。

引数名を変えるときは、古い名前を警告付きで受け付ける期間を設ける。黙って意味を変えない。

**実行時の失敗**

検証を通った後に起きる失敗（モデルに接続できない、ファイルが読めないなど）も、同じ形式で返す。区切り、モジュール、処理していた対象、再試行できるかどうかを含める。接続できるかを事前に確かめたい場合は、接続まで確認する検証を明示的に実行する。

**一貫性を保つための手段**

- すべてのモジュールに、共通の適合テストを実行する。知らない引数を拒否するか、型と範囲の誤りを正しいコードで返すか、説明をインスタンスなしで返せるかを確かめる。
- 追加ツールのモジュールにも、同じ適合テストを課す。

### 26.9 統一された手続きでエンジンが行えること

- **検証**: 名前、引数、並びの型、役割、必要なもの。
- **再利用の判定**: 名前、版、結果を変える引数から鍵を作る。
- **一覧と説明**: 登録表を回して出力する。
- **事前確認**: インスタンスを作らず、説明だけで実行計画を出す。
- **記録**: 何をどの引数で実行したかを、同じ形式で残す。
- **標準構成の書き出し**: 引数の定義から、`init` が設定ファイルを作る。

### 26.10 追加ツールとの関係

`dunlin add` で足したツールも、「説明、生成、実行」の3つを提供する。別のプロセスで動くツールは、この3つをやり取りする変換役を間に置く。エンジンからは、標準のモジュールと区別なく扱える。

外部のツールとの技術的な接続方式は、今は決めない。標準のモジュールを数個作ってから、何を外に開くべきかを決める。

## 27 search と ask の返却形式、種別 rag の serve

`search` はJSON形式で根拠を返し、`ask` は OpenAI の Responses API の形式で回答を返す。種別 `rag` の `serve` は、この2つを提供する。

| 種別 | `serve` が提供するもの | 相手 |
| --- | --- | --- |
| `mcp` | MCPサーバー。検索の道具が `search` と同じJSONを返す | エージェント |
| `rag` | HTTPサーバー（`ask` を Responses API 形式、`search` をJSONで）と、MCPサーバー（種別 `mcp` と同じ検索の道具） | アプリケーション、エージェント |
| `wiki`、`para` | ブラウザ向けの画面 | 人 |

### 27.1 search の返却形式

コマンドの `search --json`、MCPの検索の道具、種別 `rag` の `serve` の検索の口は、同じ形のJSONを返す。キーと値は案である。

```json
{
  "schema_version": 1,
  "query": "フィルターの交換周期",
  "build_id": "bld-example",
  "search_config_id": "sc-example",
  "results": [
    {
      "rank": 1,
      "score": 12.4,
      "document_id": "manuals:maintenance.md",
      "document_version": "<内容ハッシュ>",
      "range": [1840, 2610],
      "heading": "消耗品の交換",
      "page": null,
      "text": "フィルターは6か月ごとに交換する。"
    }
  ],
  "context": {
    "text": "<組み立てた文脈>",
    "chars": 3920,
    "budget_chars": 4000,
    "stop_reason": "budget_filled",
    "segments": [
      {
        "output_range": [0, 412],
        "document_id": "manuals:maintenance.md",
        "document_version": "<内容ハッシュ>",
        "source_range": [1840, 2252],
        "kind": "body"
      }
    ]
  },
  "warnings": []
}
```

- `results` は検索結果の一覧、`context` は渡すために組み立てた文脈である。2つを区別して返す。
- `segments` は、文脈の各部分がどの文書のどの範囲から来たかを示す。見出しや出典表示などの装飾は、`kind` で本文と区別する。
- 呼び出し側が件数や予算を上書きした場合は、その要求の `search_config_id` を計算し直して返す。
- コマンドの `--json` では、共通の外枠（4.4節）の `data` にこの内容を入れる。

### 27.2 ask の返却形式

`ask` は、OpenAI の Responses API の応答と同じ形で回答を返す。既存のクライアントやライブラリから、接続先を変えるだけで使えるようにするためである。値は説明用である。

```json
{
  "id": "resp_example",
  "object": "response",
  "created_at": 1794700000,
  "status": "completed",
  "model": "<設定したモデル名>",
  "output": [
    {
      "id": "msg_example",
      "type": "message",
      "role": "assistant",
      "status": "completed",
      "content": [
        {
          "type": "output_text",
          "text": "フィルターは6か月ごとに交換します。",
          "annotations": [
            {
              "type": "file_citation",
              "file_id": "manuals:maintenance.md",
              "filename": "maintenance.md",
              "index": 17
            }
          ]
        }
      ]
    }
  ],
  "usage": {
    "input_tokens": 1250,
    "output_tokens": 24,
    "total_tokens": 1274
  },
  "metadata": {
    "dunlin_build_id": "bld-example",
    "dunlin_search_config_id": "sc-example"
  }
}
```

- **出典の返し方**: 回答文の注釈（`annotations`）に、ファイルへの引用として文書を示す。文書の論理IDを `file_id` に入れる。
- **版と範囲の詳細**: 標準の注釈には、原文上の範囲を入れる欄がない。版と範囲は、拡張の欄で返す。どの欄に入れるかと、既存のクライアントが未知の欄を許容するかは、実物で確かめて決める（未決）。
- **使ったビルドと検索設定**: `metadata` に入れて返す。評価の記録と照らし合わせられる。
- **根拠が見つからない場合**: 設定に従い、答えられない旨を回答文として返す。注釈は空になる。
- **コマンドでの表示**: `dunlin ask` は、既定では回答文と出典を読みやすく表示する。`--json` では、共通の外枠の `data` に上の形式を入れる。

### 27.3 種別 rag の serve

```bash
dunlin serve
```

| 口 | 形式 | 内容 |
| --- | --- | --- |
| `POST /v1/responses` | Responses API の要求と応答 | 質問を受け取り、検索して回答を返す（`ask`） |
| `POST /v1/search` | JSON | 検索して根拠を返す（`search`） |
| /mcp | MCP（HTTPを使う接続方式） | 検索の道具。種別 mcp と同じ内容を返す |

- **要求の扱い**: `/v1/responses` は、質問（`input`）を受け取る。質問の文字列、またはメッセージの並びの最後の利用者の発言を、検索の問い合わせに使う。
- **対応しない指定はエラーにする**: 道具の呼び出し、以前の応答の引き継ぎ、背後での実行など、対応しない指定を受け取った場合は、黙って無視せずエラーを返す。互換とするのは形式であり、機能の全体ではない。
- **状態を持たない**: 応答を保存せず、1回の要求で完結する。
- **モデルの指定**: 回答に使うモデルは設定ファイルで決まる。要求の `model` が設定と違う場合の扱い（エラーにするか、設定を優先して応答に実際の名前を返すか）は未決とする。
- **逐次の返却**: 回答を少しずつ返す方式への対応は、最初の版に含めるかどうかを未決とする。
- **接続の範囲**: 既定では自分のPCからだけ接続できるようにする。
- **固定と追従**: 種別 `mcp` の `serve` と同じく、設定は起動時に固定し、索引は文書の更新に追従する（12章）。

設定ファイルでは、`serve` の区切りが次のようになる。

```yaml
# 提供する（種別 rag）。1つのポートで3つの口を出す
serve:
  transport: http               # http または stdio
  host: 127.0.0.1               # 待ち受けるアドレス。既定は自分のPCだけ
  port: 4318
  endpoints:
    - responses                 # /v1/responses  ask。Responses API 形式
    - search                    # /v1/search     search。JSON
    - mcp                       # /mcp           検索の道具。種別 mcp と同じ
  access:
    allowed_hosts:              # 要求の宛先名として受け付けるもの
      - localhost
      - 127.0.0.1
    allowed_origins: []         # ブラウザの別のページから許す送信元。空は許さない
    auth:
      type: none                # none または token
      token_env: null           # token のとき、合言葉を入れた環境変数の名前
  limits:
    max_request_bytes: 1048576
    request_timeout_seconds: 120
    max_concurrent: 8
```

**MCPでの提供**

種別 `rag` でも、MCPで検索を提供できる。内容は種別 `mcp` の `serve` と同じで、検索の道具が `search` と同じJSONを返す。

- **1つのサーバーで同時に提供する**: `dunlin serve` を1回実行すると、1つのポートでHTTPの2つの口とMCPの口が同時に立ち上がる。MCPはHTTPを使う接続方式で提供する。
- **MCPで提供するのは検索だけ**: `ask` はMCPには出さない。エージェントは自分で回答を作れるので、根拠があれば足りる。
- **どの口も同じ結果を返す**: 同じプロセスが同じビルドと検索設定を使うので、HTTPの `search`、MCPの検索の道具、`ask` の中の検索が、同じ問い合わせに同じ根拠を返す。文書更新後の索引の切り替えも、3つの口で同時に起きる。
- **プロセスを起動する方式にも対応する**: 標準入出力でしか接続できないエージェントのために、標準入出力のMCPだけを起動する指定も用意する。種別 `mcp` の既定はこちらである。
- **接続元を確かめる**: 既定では自分のPCからだけ接続できるようにし、ブラウザ経由の意図しない要求を受け付けないよう、要求の送信元を検証する。

### 27.4 評価との関係

評価が測るのは、どの種別でも検索が返す根拠までである。`ask` が作る回答文の正しさや読みやすさは測らない。`ask` の応答に含まれるビルドと検索設定のIDを使えば、その回答がどの評価済みの構成から生まれたかを辿れる。

### 27.5 serve の設定項目

サーバーの待ち受け先と接続元の制限は、設定ファイルの `serve` の区切りに書く。4.2節の方針のとおり、`init` は標準の値をすべて書き出す。項目は4つの種別で共通とし、種別 `wiki` と `para` の画面にも同じ規則を適用する。

| 項目 | 標準の値 | 内容 |
| --- | --- | --- |
| `transport` | `mcp` は `stdio`、ほかは `http` | 接続方式。`stdio` は標準入出力のMCPだけを起動する |
| `host` | `127.0.0.1` | 待ち受けるアドレス。標準では自分のPCからだけ接続できる |
| `port` | `rag` は 4318、`wiki` と `para` は 4319 | 待ち受けるポート |
| `endpoints` | 種別ごとの全部 | 出す口の一覧。書かなかった口は立ち上げない |
| `access.allowed_hosts` | `localhost`、`127.0.0.1` | 要求の宛先名として受け付けるもの。一覧にない宛先名の要求は拒否する |
| `access.allowed_origins` | 空 | ブラウザの別のページからの要求を許す送信元。空のときは許さない |
| `access.auth.type` | `none` | `none` または `token`。`token` は要求ごとに合言葉を確かめる |
| `access.auth.token_env` | なし | 合言葉を入れた環境変数の名前 |
| `limits.max_request_bytes` | 1048576 | 1回の要求の大きさの上限 |
| `limits.request_timeout_seconds` | 120 | 1回の要求の制限時間 |
| `limits.max_concurrent` | 8 | 同時に処理する要求の数の上限 |

**規則**

- **秘密は設定ファイルに書かない**: 合言葉そのものは書かず、環境変数の名前だけを書く。設定ファイルは共有され、内容から識別子が計算されるためである。環境変数が空のまま起動した場合は設定エラーにする。
- **外に開くときは認証を必須にする**: `host` が自分のPC以外から届くアドレスで、`auth.type` が `none` の場合は、設定エラー（終了コード2）にして起動しない。`validate` でも同じ検査をする。
- **宛先名と送信元を確かめる**: `allowed_hosts` にない宛先名の要求と、`allowed_origins` にない送信元からのブラウザの要求は拒否する。ブラウザで開いた別のページが、自分のPCのサーバーに要求を送る経路を塞ぐためである。
- **矛盾する指定はエラーにする**: `transport` が `stdio` のときに `host`、`port`、`endpoints`、`access`、`limits` を書いた場合は `ARG_CONFLICT` とする。種別にない口を `endpoints` に書いた場合は `ARG_RANGE` とする。
- **ポートが使用中なら止まる**: 別のポートに黙って移らず、実行エラー（終了コード1）にする。接続する側の設定がずれるのを防ぐ。
- **一時的な上書き**: `dunlin serve --host` と `--port` で、その起動に限って値を変えられる。上書き後の値にも上の検査を適用し、実際に使った値を起動時に表示する。
- **結果には影響しない**: `serve` の値は、ビルドIDと検索設定IDには含めない。ポートを変えても、再ビルドや再評価は要らない。
- **書き込みを伴う画面はより慎重に扱う**: 種別 `wiki` と `para` の画面は `ingress` や `archive` の指示を受け付ける。外に開く場合の認証の必須は同じとし、指示を出した接続の情報を作業の記録に残す。

**持たないもの（案）**

- 通信の暗号化と、接続元のアドレス範囲による制限は、最初の版では持たない。社内に公開するときは、前段に置く中継サーバーに任せる。
- 利用者ごとの権限の区別は持たない。合言葉は1つで、接続できる人は全員同じことができる。

## 28 実装の境界とデータの持ち方

2章の「前提とする実装方針」のとおり、Dunlin の中核は Rust の単一 crate で作る。モジュールのエンジン（登録表と実行口）と各モジュールも、26.5〜26.7節のとおり Rust で作る。JavaScript（Node.js）で作るのは、npm から起動する入口と、どうしても JavaScript でないと使えないライブラリを使う部分だけとする。

0.5 の開発中は、モジュールの登録表と多くのモジュールを JavaScript で作り、遅い処理から順に Rust へ移した。その結果、この方針から実装がずれ、データが言語の境界を往復する継ぎ目と、同じ本文を何か所にも持つ状態が残った。この章は、ずれを戻す移行の範囲と順序を決める。移行は段階を分けて進め、利用者から見える結果は変えない。

### 28.1 現状の継ぎ目

| 継ぎ目 | いまの流れ | 問題 |
| --- | --- | --- |
| 登録表とモジュールが JavaScript にある | `project-modules.mjs` が登録表、引数の定義（zod）、検証、説明を持ち、段階の進行、文脈の組み立て、評価、回答の生成も JavaScript で動く | 26章の設計と違う。Rust の部品を呼ぶたびに境界を渡る |
| 原本のバイト列の往復 | Rust が読む → JavaScript がハッシュを計算し、キャッシュを判定し、パースする → JavaScript が原本のバイト列を Rust に渡して保存する | 同じバイト列が境界を2回渡る |
| チャンクの往復 | Rust がチャンクを作る → JavaScript が `state.sqlite` に保存する → `index` で JavaScript が本文とチャンクを Rust に渡し直す | Rust が作ったものを JavaScript が預かり、Rust に返している |
| 本文の多重保存 | テキスト文書1件の本文を、原本ファイル、`loaded_files` の行、`stage_payloads`、`corpus.sqlite`、Tantivy の保存領域に持つ。チャンクの `searchText` も本文に近い大きさになる | 17.1節の「同じ内容を二重に持たない」に反する。どれが正本か分かりにくい |
| 実装の二重化 | 評価（`evaluate.rs` と `project-eval.mjs`）、Wiki（`wiki.rs` と `project-wiki.mjs`）、フォルダの走査（`source.rs` と `project-content.mjs`）、取り込み（`ingestFiles` と `loadCorpus`）が、Rust と JavaScript に別々にある | 直す場所が2つある。仕様に合う方がどちらか分かりにくい |

### 28.2 分担の原則

標準は Rust とする。JavaScript で作るのは次の2つに限る。

| 区分 | 内容 | JavaScript にする理由 |
| --- | --- | --- |
| npm から起動する入口 | npm の `bin` が呼ぶ小さな起動役。ネイティブ部分を読み込み、コマンドライン引数を Rust に渡し、終了コードを返す | npm で配布し、Node.js から起動するため |
| JavaScript でないと使えないライブラリを使うモジュールの実装 | 下の表の「JavaScript のまま」 | 同等の Rust のライブラリがない、または導入の手間が大きく変わる |

それ以外は Rust に置く。モジュールのエンジン（登録表、引数の定義と検証、説明の出力、実行口）、各モジュール、段階の進行、試行・採用・タグ、状態の記録、モデルの呼び出し、評価、Wiki/PARA の執筆の進行、コマンドの解釈と表示、HTTP と MCP のサーバー、画面の配信が含まれる。画面がブラウザで動かすスクリプトは、この区分の対象外とする。

いま使っている JavaScript のライブラリの扱いを次のように決める。

| ライブラリ | 用途 | 扱い |
| --- | --- | --- |
| `pdfjs-dist`、`@napi-rs/canvas` | PDF の文字層とページ位置の抽出、OCR の前のページの画像化 | Rust の `pdf_oxide` に置き換えた（段階2a）。pdfjs は比較の記録（28.9節）を再現するベンチマークの開発用の依存にだけ残す |
| `tesseract.js` と言語データ | GPU を使わない OCR | 外した（段階2a）。GPU を使わない OCR は `oar-ocr`（4.1節）が受け持つ |
| `@modelcontextprotocol/server` | MCP のサーバー | Rust の公式 SDK（`rmcp`）と Rust の HTTP サーバーに置き換えた（段階3c）。返却形式（27章）と道具の名前は変えない。旧サーバーと比べるテストの基準にだけ、開発用の依存として残す |
| `docling.rs`（npm） | Office と PDF の変換 | 同じ版の crate（`docling`、`docling-core`）を直接使うようにした（段階6a）。npm の docling.rs は比べるテストの基準にだけ開発用の依存として残す |
| `@ast-grep/napi` と言語の文法 | コードの宣言の位置 | 旧形式の設定の取り込みでだけ使っていたので、その経路とともに外した（段階2a）。コードの宣言の位置を使う機能を作るときは、`ast-grep-core` などの crate を直接使う |
| `cheerio` | HTML から本文を取り出す | Rust の `scraper` に置き換えた（段階6a）。cheerio は比べるテストの基準にだけ開発用の依存として残す |
| `markdown-it` | Wiki/PARA のページを HTML にする | Rust の `pulldown-cmark` に置き換えた（段階5a）。markdown-it は、比べるテストの基準にだけ開発用の依存として残す |
| `yaml` | `Dunlinfile.yaml` と設定の読み書き | 読み込み（段階1）と書き出し（段階6b）を Rust に置き換えた。yaml は比べるテストの基準にだけ開発用の依存として残す |
| `zod` | 引数と設定の検証 | Rust の検査に置き換えた（段階1、Wiki/PARA は段階6c）。zod は比べるテストの基準にだけ開発用の依存として残す |
| `sqlite-vec` | ベクトル索引の保存先の1つ | 使われていなかった JavaScript のベクトル検索とともに外した（段階6）。ベクトル索引は標準の総当たり検索と hannoy が受け持つ |

- **外部プロセスとネットワークも Rust で呼ぶ**: `loader.command`（6.7節）、LightOnOCR のサーバー、Ollama や OpenAI 互換のモデル、Qdrant や Chroma は、プロセスの起動か HTTP なので、JavaScript のライブラリは要らない。
- **JavaScript のモジュールも登録表は Rust に置く**: 名前、引数の定義、説明、要るものは Rust で宣言する。実装だけを JavaScript が受け持ち、Rust のエンジンが Node.js の呼び出し口を通して呼ぶ（26.10節の変換役）。検証と説明は、実装がどちらの言語でも同じ規則で動く。
- **境界を渡すもの**: JavaScript の実装に渡すのはバイト列と引数、返すのは本文と位置だけとする。段階の進行や保存は Rust が行う。

### 28.3 データの正本

| データ | 正本 | 置き場所 | 段階の記録に残すもの |
| --- | --- | --- | --- |
| 原本 | Rust | `artifacts/originals/`。構築では、UTF-8 のテキスト文書の原本は作らず、コーパスの版から復元する（28.14節） | なし |
| 抽出結果（本文、位置、由来） | Rust | `corpus.sqlite` の版 | 入力のハッシュと抽出設定から版への対応 |
| チャンク | Rust | `corpus.sqlite`。版とチャンク設定の組で引く | チャンク集合の識別子 |
| 索引 | Rust | ビルドごとの索引ディレクトリ | ビルドの記録 |
| 段階・ビルド・タグ・採用の記録、評価データとレポート、Wiki/PARA の状態 | Rust | `state.sqlite` | 本文は持たない |

- `state.sqlite` の `extractions` 表は、抽出のキャッシュキー（入力のハッシュと抽出設定）から、コーパスの版（情報源、オブジェクト、版の識別子）への対応を持つ。同じ入力と設定なら、パーサを呼ばずにコーパスの版を使う。版の識別子には URL が入るので、同じファイルが別の場所にあれば、本文を写した版を新しく作る。このときもパーサは呼ばない。
- `source` 段の出力は、情報源ごとに、文書の `objectId`、版の識別子、原本の SHA-256、更新時刻を並べた一覧とする。`transform` 段の出力は、文書ごとのチャンク集合の識別子（チャンクの JSON の SHA-256）とする。段階の識別子の計算は、本文の代わりにこれらの識別子を使う。
- チャンク集合は `corpus.sqlite` の `chunk_sets` 表に置く。`version_chunkings` 表が、版とチャンク設定の組からチャンク集合を引く。変わっていない文書は、本文を読まずにチャンク集合が決まる。見つからない文書は本文を読み、`chunkings` 表で、本文・形式・ページの境界とチャンク設定の組から引く。同じ本文のチャンクは1つにまとまる。
- Tantivy に本文を保存するのをやめ、抜粋はコーパスから読むかは、移行の後半で決める（28.8節）。

### 28.4 段階ごとの流れ

すべての段階を Rust のエンジンが進める。JavaScript は、入口から Rust の口を1回呼び、JavaScript で実装したモジュールの呼び出しにだけ応える。

| 段階 | Rust | JavaScript |
| --- | --- | --- |
| `source` | 走査、パーサの振り分け（6.7節）、読み込みとハッシュ、キャッシュの判定、パース（テキスト、HTML、Office、PDF、OCR、外部コマンド）、原本と抽出結果の保存 | なし（HTML と Office のパースは段階6aで移した） |
| `transform` | 正規化とチャンク化、チャンクの保存。`chunk.semantic` の埋め込みも Rust からモデルを呼ぶ | なし |
| `index` | キーワード索引とベクトル索引の作成。埋め込みも Rust からモデルを呼ぶ | なし |
| `search` / `ask` / `serve` | 取得、統合、並べ替え、文脈の組み立て、回答の生成、返却形式の組み立て、HTTP と MCP のサーバー | なし |
| `eval` | 評価データの管理、根拠の位置対応、指標の計算、レポートと比較 | なし |
| Wiki/PARA | 取り込み、執筆と引用の検証の進行、検査、ページの HTML 化、画面の配信 | なし |

### 28.5 Node.js API の範囲

Node.js API（`dunlin` パッケージ）は、Rust のエンジンをそのまま公開する口とする。CLI と同じエンジンの機能を、Node.js から呼べるようにする。CLI にしかない処理を JavaScript に持たない。

- いまの Node.js API にある上位機能（`evaluate`、`optimize`、検索方式の切替、`explore`、`wiki.*`、`addSource` と `syncSource`）は、外さずに CLI と同じエンジンの機能へまとめる。仕様（9〜16章）に合う方の動作を残し、もう一方は消す。
- 口の名前と引数は、移行の中で CLI のコマンドと対応が取れる形に整える。npm での公開前なので、非推奨の期間を置かずに変えてよい。公開後に変える場合は、1つのマイナー版で非推奨を表示してから変える。
- JavaScript の `ingestFiles`、`prepareLocalFile`、`loadCorpus` は、Rust の取り込みに置き換えて消す。

### 28.6 移行の順序

各段階で、チャンクの範囲、検索結果、返却形式、評価の根拠の位置は変えない。旧実装を基準にした差分テストと、ベンチマークで確かめてから次に進む。

| 段階 | 内容 | 主に解消する継ぎ目 |
| --- | --- | --- |
| 1 | 登録表、引数の定義と検証、説明、`Dunlinfile.yaml` の読み込みを Rust に移す。`validate` と `modules` は Rust の口を呼ぶだけにする | 登録表とモジュールが JavaScript にある |
| 2 | 構築の段階（`source`、`transform`、`index`）の進行と記録を Rust に移す。JavaScript で実装するパーサは、Node.js の呼び出し口から呼ぶ。原本と抽出結果をコーパスに置き、本文の写しを減らす | 原本の往復、チャンクの往復、本文の多重保存、取り込みの二重化 |
| 3 | 検索モジュール、文脈の組み立て、返却形式、回答の生成と並べ替えのモデル呼び出し、HTTP と MCP のサーバーを Rust に移す | 登録表とモジュールが JavaScript にある |
| 4 | 評価データ、評価、レポートと比較、試行と採用を Rust に移し、`evaluate.rs` とまとめる | 評価の二重化 |
| 5 | Wiki/PARA の取り込み、執筆の進行、検査、ページの HTML 化、画面の配信を Rust に移し、`wiki.rs` とまとめる | Wiki の二重化 |
| 6 | 残った JavaScript のライブラリ（`cheerio`、`markdown-it`、`yaml`、`zod`）を外し、`docling.rs` を crate で使えるか確かめる。コマンドの解釈と表示を Rust に移し、入口を起動役だけにする | JavaScript のライブラリへの依存 |

### 28.7 既存プロジェクトの扱い

- 段階2の後の最初の構築（`build`、`source`、`transform`、`index`、Wiki の取り込み）で、Rust が一度だけ移す。`loaded_files` の抽出結果はコーパスの版と `extractions` の対応に、`stage_payloads` の本文とチャンクはコーパスの版とチャンク集合に、`document_chunks` のチャンクのキャッシュは `chunkings` に移す。パーサ、OCR、埋め込みモデルはやり直さない。
- 保存済みの段階の記録は、識別子を変えずに新しい形に書き換え、`migrated` を付ける。以前のビルドを `--input` に使える。移したあとは古い表を消し、`state.sqlite` を詰める。
- 段階の識別子の計算方法が変わるため、新しく作る段階とビルドの識別子は一度だけ変わる。移行した構築は `DATA_LAYOUT_MIGRATED` の警告を返す。最新の評価レポートが移行前のビルドを測ったものなら、`status` が `REPORT_BEFORE_LAYOUT_CHANGE` の警告で、新しいビルドと比べるには評価をやり直す必要があることを知らせる。
- 識別子が変わっても、チャンクの範囲と根拠の位置対応は変わらないので、評価データの作り直しは要らない。

### 28.8 未決事項

| 論点 | 現時点の考え |
| --- | --- |
| テキスト文書の原本 | 決めた（28.14節）。構築の `source` 段は、UTF-8 のテキスト文書の原本ファイルを作らず、コーパスの版から復元する。Wiki/PARA の取り込みは、ページの引用がリンクするので作る |
| 索引に本文を持つか | 当面は持つ（28.14節）。コーパスから読むと、根拠の読み出しが3〜4倍遅くなった。コーパスから本文だけを速く読めるようになれば、改めて決める |
| チャンクの `searchText` | 決めた（28.14節）。チャンク集合には保存せず、読むときに NFKC で作り直す。チャンク集合の識別子は作り直した文字列を含めて計算するので変わらない |
| `state.sqlite` と `corpus.sqlite` | 分けたままにする（28.14節）。コーパスはエンジンの一部で、Node.js API の単独の索引も使う。書き込みの待ち合わせと、大きさと扱いの違いからも、分けておく方がよい |
| 入口 | JavaScript の起動役を残すことにした（28.13節）。ネイティブ部分は Node.js の拡張として読み込むので、Rust の実行ファイルを別に配ると同じネイティブ部分を2つ配ることになる |

### 28.9 段階2の進め方

段階2では、構築（`source`、`transform`、`index`）のモジュールの実行と、段階の進行・記録を Rust のエンジンに移す。範囲が大きいので、次の小段階に分ける。各小段階の終わりで、旧実装と同じ入力に対して段階の識別子、出力、ビルドID、検索結果が変わらないことを差分テストで確かめる。

| 小段階 | 内容 |
| --- | --- |
| 2a | Rust から `state.sqlite` を読み書きする部品を作る。`source` 段（走査、振り分け、読み込みとハッシュ、キャッシュ、テキストと Markdown とコードのパース、`loader.command`、原本と抽出結果の保存）を Rust で実行する。PDF は `pdf_oxide` で読み、OCR は `oar-ocr` を Rust から、`lightonocr` を別プロセスとして呼ぶ。HTML と Office は JavaScript の実装を呼び出す |
| 2b | `transform` 段（`text.normalize`、`chunk.length`、`chunk.structure`、`chunk.semantic`）を Rust で実行する。埋め込みモデルは Rust から HTTP で呼ぶ |
| 2c | `index` 段（キーワード索引、ベクトル索引、hannoy）と、ビルド・タグ・採用の記録を Rust で実行する |
| 2d | `build`、`source`、`transform`、`index` の各コマンドの進行（`--from`、`--until`、`--input`、`--tag`、`--config`、`--dry-run`）と `tag` コマンドを Rust に移し、JavaScript の `buildProject` を Rust の口の呼び出しだけにする |
| 2e | 28.3節のデータの持ち方に移る。抽出結果とチャンクの正本をコーパスにし、`state.sqlite` には識別子だけを置く。ソースのフォルダの走査と並べ替えを Rust に移す。28.7節の移行を行う |

#### JavaScript の実装を呼び出す仕組み

- Rust のエンジンは、ワーカースレッドで構築を進める。JavaScript で実装したパーサが要るときは、要求に番号を付けて Node.js のメインスレッドに渡し、結果が届くまでその文書の処理を待つ。
- JavaScript は、構築を始めるときに「種類、バイト列、ファイル名、引数」を受け取ってパース結果（本文、形式、位置、由来）を返す関数を渡す。結果やエラーは番号を付けて Rust に返す。
- 中断（利用者の中断、試行の上限）は、待っている要求にも伝える。

#### 2a から 2d の間に変えないもの

- `state.sqlite` の表と、段階の出力・ビルドの記録の形式は変えない。旧実装で作ったプロジェクトをそのまま続けて構築でき、途中の小段階のまま公開しても困らないようにするためである。
- キャッシュのキー、段階の識別子の計算方法、ビルドIDも変えない。
- データの持ち方を変えるのは 2e だけとし、識別子が一度だけ変わることをそこで扱う（28.7節）。

#### HTML の抽出

- いまの HTML の抽出は cheerio を使い、その HTML 構文解析器は HTML5 の標準の解析と細部が違う。Rust の HTML ライブラリに移すと、崩れた HTML で抽出結果が変わり得る。
- 2a から 2e までは JavaScript の実装のまま呼び出す。2e では移さず、抽出結果が変わる文書の数を実際の資料で確かめてから、移すかどうかを決める。移すときは、PDF と同じくキャッシュのキーにパーサの名前と版を加え、HTML の文書だけを読み直す。

#### PDF と OCR

- PDF の文字層の抽出は `pdf_oxide` を標準とする。文字の並べ方や改行の入れ方が pdfjs と違い、抽出結果が変わり得る。抽出結果のキャッシュのキーに PDF だけパーサの名前と版（`pdf_oxide@<版>`）を加えるので、切り替え後の最初の構築では PDF だけが読み直される。版は固定し、上げると PDF を読み直す。
- 日本語の PDF（横書き、縦書き、表、段組み）で pdfjs と抽出結果を比べ、差のある文書の数と内容、ページ位置の一致、処理時間を記録として `docs/pdf-extraction.md` に残す。比較の結果は、標準を決める条件にはしない。
- `oar-ocr` は ONNX Runtime とモデルを使う。どちらも本体には含めず、`dunlin add oar-ocr` で準備する（25.4節）。日本語のスキャン文書で認識の精度と速度を測り、標準の方式として十分かを確かめる。
- `lightonocr` は、今の管理された Python の実行環境とサーバーを、Rust から別プロセスとして起動する。

#### 埋め込みモデルの呼び出し（2b）

- `chunk.semantic` の埋め込みモデルは Rust から HTTP で呼ぶ（Ollama の `api/embed`、OpenAI の `embeddings`）。要求の本文は JavaScript の実装と同じ JSON にし、ベクトルの検査と正規化も同じ順で計算する。キャッシュのキー、段階の識別子、チャンクの結合結果は変わらない。
- 接続先の URL、API キー、`max_input_bytes` は JavaScript が `models` から解決して渡す。HTTPS の検証には Mozilla のルート証明書（Node.js の `fetch` の既定と同じ）を使う。リダイレクトは追わず、環境変数のプロキシも使わない（`fetch` と同じ）。1回の要求は120秒で打ち切る。
- 試行の上限（API の要求数と送信量）は、送る前に JavaScript に問い合わせて数える。上限の記録は段階4で評価とともに Rust に移す。

#### 索引の作成とビルドの記録（2c）

- `index` 段は Rust で実行する。キーワード索引、ベクトル索引（`exact` と hannoy）、埋め込みのキャッシュ（`embeddings` 表）、ビルドの記録（`builds`、`build_runs`、`index_outputs`、`build_search`、`build_config`）を Rust が書く。`--tag` を付けた構築のタグの記録と、採用中のビルドの切り替え（`project`、`serving_generations`）も同じトランザクションで行う。
- ビルドID、設定ID、`builds` の JSON、`vectors.json`、`vectors.f32`、hannoy のスロットの割り当ては JavaScript の実装と同じにする。既存のビルドはそのまま再利用でき、差分の更新（前のビルドのキーワード索引の写しと hannoy のグラフ）も続けて使える。
- JavaScript は設定から決まる値だけを渡す。キーワードとベクトルの引数、埋め込みの接続先、検索の設定、ビルドに保存する設定である。構築中に設定ファイルが変わったかの確認、hannoy の版と完全性の検査、試行の上限の計数は、Rust から JavaScript に問い合わせる。hannoy の検査は、道具の管理（`dunlin add`）を Rust に移すときに合わせて移す。
- 単独の `tag` コマンドは 2d で Rust に移した。`use` コマンドは設定ファイルの書き換え（`yaml`、段階6）と評価の状態の確認（段階4）を伴うので、それらとともに移す。

#### コマンドの進行（2d）

- `build`、`source`、`transform`、`index` の進行を Rust で行う。段階の選択（`--from`、`--until`）、入力にするビルドの解決（`--input`、`--from` と `--tag`）、保存済みの段階の読み出しと `STALE_STAGE` の警告、`--tag` と `--config` での採用の扱い、結果の組み立て、`--dry-run` の分析（ファイルごとの変化の判定と、各段階の再利用か再実行か）が含まれる。`tag` コマンドの記録も Rust で行う。
- JavaScript は設定から決まる値を求めて Rust の口を1回呼ぶ。ソースのフォルダの走査と並べ替えは、識別子が変わる 2e で Rust に移した。
- 実行ロックと試行の記録（`trial_runs`）は JavaScript が Rust の呼び出しを包んで行う。試行は評価（`eval --build`、`eval --config`）と共通なので、段階4で評価とともに Rust に移す。
- 埋め込みモデルの接続先は、段階を始める前に解決する。設定が正しくない場合、前の段階を実行する前に失敗する。

#### データの持ち方（2e）

- `source` 段は、抽出結果をコーパスの版として `corpus.sqlite` の `revisions` 表に保存する。版の識別子と記録の形は、索引を作るときに保存していたものと同じなので、既存のコーパスの版はそのまま使える。記録の行の範囲は文書の全行とする。
- `transform` 段と `index` 段は、段階の記録にある識別子から、コーパスの本文とチャンクを読む。チャンクの範囲、検索結果、根拠の位置は変わらない。
- `index` 段が前のビルドのキーワード索引を写して更新するときは、版とチャンク集合が前のビルドと同じ文書をコーパスから読まず、写した索引に残す。ベクトル索引を作る場合は、すべてのチャンクを書き出すので、すべての文書を読む。
- ソースのフォルダの走査と並べ替えは Rust で行う。並べ替えは `objectId` の符号位置の順とし、OS や言語の設定に左右されない。JavaScript の `localeCompare` の順とは、大文字と小文字、記号、数字の並びが違う。並びは段階の識別子に入るが、識別子が一度変わる 2e で合わせて変える。
- 3,000文書（各40行）の構築で 2d と比べた。`state.sqlite` と `corpus.sqlite` の合計は 67 MB から 31 MB に減った。変更のない再構築は 0.90 秒から 0.80 秒に、初回の構築はほぼ同じ（3.3 秒と 3.4 秒）だった。1文書を変えた再構築は 1.20 秒から 1.01 秒に縮んだ。
- 旧実装を基準にした段階ごとの差分テスト（`source`、`transform`、`index`、コマンドの進行）は、記録の形が変わったので外した。代わりに、2d の実装で作ったプロジェクトの記録を移し、パーサを呼ばずに構築できることと、検索結果が変わらないことを確かめる。

### 28.10 段階3の進め方

段階3では、検索の側（`search`、`ask`、`serve`）のモジュールの実行と結果の組み立てを Rust のエンジンに移す。範囲が大きいので、次の小段階に分ける。各小段階の終わりで、旧実装と同じビルドと質問に対して、検索結果、返却形式、`search_config_id`、モデルへの要求の本文が変わらないことを差分テストで確かめる。

| 小段階 | 内容 |
| --- | --- |
| 3a | 検索の実行を Rust に移す。`query.normalize`、`retrieval.keyword`、`retrieval.vector`、`hannoy.search`、`fusion.rrf`、`context.assemble`、`search_config_id` の計算、27.1節の返却形式の組み立てが含まれる。`search` コマンド、`serve` の検索、評価の検索は、Rust の口を1回呼ぶ。`rerank.model` は JavaScript の実装を呼び出す |
| 3b | 生成モデルの呼び出しを Rust に移す。OpenAI の `responses`、Ollama の `api/chat`、Strata の `chat/completions` を Rust から HTTP で呼ぶ。`rerank.model` と `answer.generate`、27.2節の返却形式を Rust で組み立てる。`ask` コマンドと `/v1/responses` の回答は Rust の口を呼ぶ |
| 3c | HTTP と MCP のサーバーを Rust に移す。27.3節の口、接続先と送信元の確認、合言葉、要求の大きさの上限、提供中のビルドの切り替え（12章）、MCP の道具（`knowledge.search`、`knowledge.read`）を Rust で動かす。MCP は `rmcp` を使い、`@modelcontextprotocol/server` を外す。`serve` は Rust の口を1回呼ぶ |

#### 3a から 3c の間に変えないもの

- 検索結果の順位、スコア、範囲、文脈の組み立て（区切り、見出し、出典の行、切り詰め、止まった理由）、27.1節と27.2節の返却形式、エラーの番号と終了コード。
- `search_config_id` の計算方法。評価レポートの比較の条件に入っているため、変えると以前のレポートと比べられなくなる。
- モデルへの要求の本文（指示、入力の JSON、出力の形を決める JSON Schema、温度などの引数）。同じ要求を送り、モデルの応答の扱いも同じにする。
- MCP の道具の名前、入力の形、返却の内容（27章）と、HTTP の口の状態コードとエラーの本文。

#### 検索の実行（3a）

- Rust の口は、ビルドの記録、検索のモジュールの設定、問い合わせ、上書きの指定（`limit`、`budget_chars`、`source_ids`）を受け取り、27.1節の返却形式を返す。`search` コマンド、`serve`、評価（`eval`）は同じ口を使う。評価そのものは段階4で移すが、検索は 3a から Rust で動く。
- 埋め込みモデルの接続先、並べ替えのモデルの設定は、段階2と同じく JavaScript が `models` から解決して渡す。`search_config_id` の計算に入る値も同じものを使う。
- `hannoy.search` は、索引の道具（`dunlin add hannoy`）を Rust から別プロセスとして呼ぶ。いまと同じく検索ごとに1回起動し、道具の検査（版と完全性）も同じ規則で行う。
- `rerank.model` は、2a の JavaScript のパーサと同じく、番号を付けた要求で JavaScript に渡す。候補の本文は Rust が読んで渡す。
- 試行の上限（モデルへの要求の数と送信量）は、段階2と同じく送る前に JavaScript に問い合わせて数える。
- 検索は開いた索引の口（Node.js API の `searchProject`）で行う。`vectors.json` は開いた索引ごとに一度だけ読み、索引を閉じると捨てる。`search_config_id` も Rust の計算（`Dunlin.searchConfigId`）を `status`、`tag`、`use` が使う。
- 評価は、返却形式の `results` の根拠と、文脈の各抜粋の根拠、文脈が止まった理由（`budget` などの内部の値）を受け取って、これまでと同じ記録を作る。
- `rerank.model` のモデルの設定は、`search_config_id` に入るため検索を始める前に解決する。設定が正しくない場合のエラーは、これまでと同じ番号と文言だが、モジュール名（`rerank.model`）が付かない。
- 旧実装を写した基準（テストの `search-reference.mjs`）と、同じビルドと問い合わせで比べる。キーワード、`exact` のベクトル、hannoy、統合、並べ替え、上書きの指定、エラーについて、返却の JSON の文字列（値とキーの順）が一致することを確かめる。

#### 生成モデルの呼び出し（3b）

- 要求の本文と JSON Schema は、いまの JavaScript の実装（zod から作った JSON Schema を含む）と同じ文字列にする。差分テストでは、テスト用のモデルのサーバーが受け取った本文を比べる。
- 接続、証明書、リダイレクト、プロキシ、打ち切りの時間は、2b の埋め込みモデルの呼び出しと同じ扱いにする。
- 評価データの生成（`eval-data generate`）と Wiki/PARA の執筆も生成モデルを使うが、それぞれ段階4と段階5で移す。それまでは JavaScript の実装が残る。
- 接続先の URL、API キー、`max_input_bytes` は、埋め込みモデルと同じく JavaScript が `models` から解決して渡す。解決に失敗したモデルは、そのモジュールを動かすときに同じエラーで止まる。
- `rerank.model` は、候補の本文の先頭 800 単位（UTF-16 の単位）をモデルに渡す。サロゲートペアの途中で切れた場合も、JavaScript と同じエスケープ（`\ud83d` など）で送る。
- 回答は Node.js API の `Dunlin.answerQuestion` で作る。応答の `id` と `created_at` は呼び出しごとに変わる。
- `serve` で要求が時間切れになると、JavaScript はその要求の呼び出しをすぐに終える（`fetch` を中断したときと同じ）。Rust 側のモデルへの要求も、すぐ後に止まる。
- 接続できない場合と、応答が JSON でない場合のメッセージ（`<提供元> request failed: ...` と `<提供元> returned invalid JSON`）は、`fetch` のメッセージと文言が違う。
- 比較のテストは、テスト用のモデルのサーバーが受け取った要求の本文がバイト単位で一致すること、応答が `id` と `created_at` を除いて一致することを確かめる。Ollama、OpenAI、Strata の3つの形式の回答と並べ替え、引用の有無、文脈がない場合、範囲外の引用、JSON でない出力、要求の大きさの上限を含む。

#### サーバー（3c）

- MCP は公式の Rust SDK（`rmcp`）を使い、stdio と HTTP の2つの接続方式を出す。HTTP は `rmcp` が使う非同期の実行環境（tokio）と HTTP のライブラリで受ける。どのライブラリを使うかは、配布物の大きさと構築の時間を測ってから決める。
- 27.3節の `/v1/responses` と `/v1/search` も同じ HTTP のサーバーで受ける。接続先と送信元の確認、合言葉、要求の大きさの上限は、いまの JavaScript の実装（`project-serving.mjs`）と同じ規則にする。
- Wiki/PARA の `serve` も同じ HTTP の部品を使うが、画面の配信とあわせて段階5で移す。それまでは JavaScript の実装が残る。
- Node.js API の `serveMcp` は Rust のサーバーを起動する口にした。`createMcpHttpHandler` は外し、プロジェクトの提供には `Dunlin.serveProject` を足した（28.5節）。
- 3c は2回に分ける。先に stdio の MCP（MCP 種別の `serve` と、Node.js API の `serveMcp`）を移し、次に HTTP のサーバー（`/v1/search`、`/v1/responses`、`/mcp`）と提供中のビルドの切り替えを移す。
- stdio の MCP は `rmcp` と tokio で動かす。追加した依存で、配布物は約 2.4 MB（2.5%）大きくなった。
- MCP 種別の `serve` では、HTTP を移すまでは、`knowledge.search` と `knowledge.read` が JavaScript の検索と読み出し（提供中のビルドの切り替えと、以前のビルドからの読み出し）を呼ぶ。Node.js API の `serveMcp` で検索を渡さない場合は、4つの道具（`knowledge.search`、`knowledge.read`、`knowledge.explore`、`knowledge.wiki_get`）を Rust が索引に対して実行する。
- 道具の入力は Rust で検査し、旧サーバーと同じ文言（zod の文言）で返す。JSON-RPC の応答のキーの順と、`structuredContent` のキーの順は SDK によって違うが、値は同じである。
- 旧サーバーを写した基準（テストの `mcp-reference.mjs`）と同じ要求を送り、道具の一覧と入力の形、結果、入力の誤り、範囲外の読み出し、知らない道具への答えが一致することを確かめる。`@modelcontextprotocol/server` は、3c の後半で HTTP の `/mcp` も移したので、テストの基準だけが使う開発用の依存にした。
- 3c の後半では、`serve` のすべてを Rust で行う。提供中のビルドの切り替え（起動時の採用の世代で置き換わったビルドを、キーワードとベクトルの設定が同じあいだ使う。索引はビルドごとに一度だけ開き、使わなくなったら閉じる）、プロジェクトの検索と回答、以前のビルドからの読み出し、HTTP のサーバーが含まれる。JavaScript は、設定とモデルの解決（ビルドごとに Rust から問い合わせる）と、待ち受けた場所の表示だけを行う。
- HTTP のサーバーは hyper と tokio で動かす。配布物はさらに約 0.6 MB 大きくなった（3c 全体で約 3.0 MB、3.1%）。接続先と送信元の確認、CORS、合言葉、同時接続の上限、要求の大きさの上限、時間切れ、エラーの本文は、旧サーバーと同じ規則にした。応答は `Content-Length` 付きで返し、旧サーバーの `Transfer-Encoding: chunked` とは違う。
- `/mcp` は、TypeScript SDK の状態を持たない方式と同じに答える。要求ごとに結果を1つのイベントとする server-sent events で返し、受け付ける形式、`Content-Type`、JSON の誤り、空の一括要求、プロトコルの版の誤りには、同じ状態コードと JSON-RPC のエラーを返す。
- 開いた索引ごとに、Node.js の `diagnostics_channel` の `dunlin:index-open` に `{ path }` を知らせる。購読者がいないときは何もしない。
- 旧サーバーを写した基準（テストの `rag-http-reference.mjs`）を同じプロジェクトで並べて起動し、49通りの要求（検索、回答、MCP、接続先・送信元・合言葉・パス・大きさの誤り、CORS の事前確認）に、同じ状態コード、ヘッダー、本文で答えることを確かめる。

### 28.11 段階4の進め方

段階4では、評価（`eval`）、根拠の位置対応、レポートと比較、試行と採用、評価データの管理を Rust のエンジンに移し、Node.js API の `evaluate.rs` とまとめる。範囲が大きいので、次の小段階に分ける。各小段階の終わりで、旧実装と同じビルドと評価データに対して、根拠の位置、評価レポート、根拠の対応表、比較の結果、識別子（`evaluation_config_id`、`method_id`、`evidence_map_id`、位置のキー）が変わらないことを差分テストで確かめる。

| 小段階 | 内容 |
| --- | --- |
| 4a | 評価の採点を Rust に移す。根拠の位置対応（NFKC と空白の正規化、前後の文字列、ページと見出しの手がかり、近い候補の提示、位置のキーと `evidence_positions`・`evidence_overrides` の表）、範囲の被覆の判定、指標と遅延の集計、レポートと根拠の対応表の保存が含まれる。検索は Rust の中で続けて行い、質問ごとに JavaScript を経由しない。`evidence-map` のコマンドも同じ位置対応を使うので、ここで移す |
| 4b | レポートの読み出しを Rust に移す。`report show`、`report list`（設定の違いの列）、`report compare`（対の差、勝ち負け、グループ単位のブートストラップの信頼区間、ケースごとの変化）、評価の状態（`status` と `use` が使う）、辞書の提案に渡す取りこぼしの一覧が含まれる |
| 4c | 試行と採用を Rust に移す。試行の記録（`trial_runs`）、上限の判定、経過時間の打ち切り、モデルへの要求の数と送信量の計数を Rust で行い、計数のために JavaScript へ問い合わせるのをやめる。`use` の記録（採用の履歴、提供中のビルド、世代）も Rust で行う。設定ファイルの書き出しは、YAML を移す段階6までは JavaScript に問い合わせる |
| 4d | Node.js API の `evaluate` と `optimize` を、CLI と同じ評価のエンジンにまとめる（28.5節）。仕様（9〜11章）に合う方の動作を残す |
| 4e | 評価データの管理（`eval-data` の `add`、`import`、`export`、`list`、`show`、`split`、`review`、`sync`、`diff`、`use`、`generate`）を Rust に移す。`generate` は 3b の生成モデルの呼び出しを使う。作業中の評価データの変更が入ってから行うため、段階4の最後に置く |

#### 4a から 4e の間に変えないもの

- `state.sqlite` の評価の表（`evaluation_datasets`、`evaluation_dataset_tags`、`evaluation_reports`、`evidence_positions`、`evidence_maps`、`evidence_overrides`、`trial_runs`）と、保存する JSON の形とキーの順。
- 識別子の計算方法。`evaluation_config_id`、`method_id`、`evidence_map_id`、位置のキーは、以前のレポートと比べる条件や、保存済みの位置対応を引く鍵に入っている。
- 根拠の位置対応の規則。範囲は原文のバイト位置で、文字の単位は書記素のまとまりとする。指標の値、エラーの番号と終了コード、`eval` と `report` の返却形式も変えない。

#### 評価の採点（4a）

- Rust の口は、ビルドの記録、検索のモジュールの設定、評価の設定（JavaScript が検証した `eval` の節、文脈の予算、構築の設定、検索のモジュール）、評価データの参照、`--split` と `--tag` を受け取り、レポートを保存して返す。検索は 3a の口と同じ処理で行う。
- 評価の設定は JavaScript から受け取った順のまま `evaluation_config_id` に入れる。JSON の数値は JavaScript と同じ書き方にする。
- 遅延は質問ごとの検索の時間で、Rust で測る。値は実行ごとに変わるので、差分テストでは比べない。
- 試行の打ち切り（`eval --build`、`eval --config`）は、試行の中断を Rust の呼び出しの中断として渡す。打ち切られた評価はレポートを保存しない。試行の記録は 4c までは JavaScript に残る。
- `evidence-map` の `create`、`import`、`confirm` は、確認した範囲を `evidence_overrides` に保存し、新しい対応表を作る。`list`、`show`、`export` は保存済みの対応表を読む。
- 旧実装を写した基準（テストの `eval-reference.mjs`）と、同じプロジェクトで比べる。一意に見つかる引用、見つからない引用と近い候補、複数に一致する引用、前後の文字列、ページと見出しの手がかり、文書がない根拠、保存済みと確認済みの位置、調整用と最終確認用の分割、`--tag` の重複について、保存したレポートと対応表の JSON が遅延を除いて一致することを確かめる。
- 評価は Node.js API の `evaluateProject`（開いたビルドの索引の口）で行い、根拠の対応表は `evidenceMap`（`create`、`import`、`confirm`）と `Dunlin.evidenceMaps`（`list`、`show`）で扱う。`export` は `show` の結果を JavaScript がファイルに書く。表示と書き出しは段階6で移す。
- 書記素のまとまりは `unicode-segmentation`、NFKC は `icu_normalizer` で求める。Node.js の `Intl.Segmenter` と `String.prototype.normalize` とは Unicode の版が違い得るので、まれな文字の並びで範囲の端が変わる可能性がある。位置のキーは文書の本文から作るので、範囲が変わっても保存済みの位置と確認済みの範囲はそのまま使われる。
- `eval-data` の管理（4e）と辞書の提案（4b）は、同じ位置対応を JavaScript の実装のまま使う。どちらも移すときに JavaScript の実装を消す。
- 差分テストでは、同じプロジェクトを写した2つで、CLI と基準に同じ手順（調整用と最終確認用の評価、対応表の作成、確認、取り込み、確認済みの範囲を使う再評価、誤りの入力）を行い、保存した記録と出力が一致することを確かめた。確認の時刻は比べない。

#### レポートと状態（4b）

- `report show`、`report list`、`report compare` は Node.js API の `Dunlin.evaluationReports` を呼ぶ。評価の状態は `Dunlin.evaluationStatus` で、`status` と `use` が使う。どちらも `state.sqlite` を読むだけなので、同期の呼び出しにした。`state.sqlite` は WAL なので、`use` の書き込みのトランザクションの中で読んでも待たない。
- 辞書の提案は、使うレポートと評価データを `Dunlin.dictionaryEvaluation` で選び、取りこぼした根拠と前後の行を開いたビルドの `dictionaryMisses` で読む。提案の組み立て（Lindera の解析）は JavaScript に残り、レポートの検査のあとで取りこぼしを読む順も変えない。
- `report list` の並びは、評価データと評価方法の識別子を符号位置の順で比べる。識別子は共通の接頭辞と小文字の16進数なので、`localeCompare` の順と同じである。
- 比較の信頼区間は、JavaScript と同じ乱数の種と線形合同法で1000回引き直すので、同じ値になる。
- 旧実装を写した基準（テストの `report-reference.mjs`）と同じプロジェクトを読み、表示、一覧（調整用と最終確認用）、比較（比べられる組、文脈の予算が違う組、分割が違う組、最終確認用どうし、根拠ごとの記録がない旧形式のレポート）、評価の状態、辞書の提案に使う取りこぼしが一致することを確かめた。

#### 試行と採用（4c）

- 試行は、`build --tag`・`--config` と `eval --build`・`--config` の Rust の口（`runBuild`、`evaluateProject`）に `trial`（`state.sqlite`、実行ID、コマンド、上限）を渡して行う。Rust が `trial_runs` の行を作り、回数と経過時間の上限を確かめ、1秒ごとに経過時間を記録し、時間の上限で実行を止め、終わりに状態（`succeeded`、`limited`、`failed`）を書く。中断された行の扱い、エラーの番号と文言、`data`（`limit`、`maximum`、`used`）は以前と同じである。
- モデルへの要求の数と送信量は、送る前に Rust で数える。JavaScript への問い合わせ（`charge`）はなくなり、Node.js API の `runTransform` と `answerQuestion` の `host` の引数と `TransformStageHost` の型も外した。
- 試行の行は Rust の口を呼んだときに作るので、その前の JavaScript の準備（モデルの設定の解決、評価のビルドを開くこと）で失敗した場合は、試行の行を残さない。以前は準備も試行に含め、回数の上限をその前に確かめていた。
- 時間の上限に達したとき、JavaScript で変換中の Office 文書があれば、その変換が終わってから止まる。以前は変換にも中断を伝えていた。
- `status` の試行の使用量は `Dunlin.trialUsage` で読む。
- `use` の記録（採用の履歴、提供中のビルド、世代）は `Dunlin.adoptBuild` で、1つのトランザクションとして Rust が書く。設定ファイルは、トランザクションの途中で JavaScript が書く（YAML は段階6まで JavaScript）。書いたあとで失敗したら、Rust がトランザクションを戻し、JavaScript が前のファイルに戻す。評価の状態も同じ口で求める。設定の組み合わせと検証は JavaScript に残る。
- 評価データの生成（4e で移す）は試行の中で動かないので、`trialCheckpoint` は何もしない関数として 4e まで残す。
- 試行の上限の既存のテスト（回数、要求の数と送信量、時間、使用量）に加え、評価の試行の上限と、`use` の途中の失敗で設定ファイルと記録が元に戻ることをテストで確かめた。

#### Node.js API の評価（4d）

- `evaluate` と `optimize` は残し、指標を根拠単位（10章）に変えた。評価セットは、質問と根拠の引用（`doc` は `ソースID:資料の相対パス`、`quote`、手がかりの `prefix`、`suffix`、`page`、`heading`）を並べたもので、`eval-data import` と同じく引用が1つなら直接書ける。文書単位の `relevant` と Recall@K・nDCG@K はやめた。
- 引用の位置対応と被覆の判定は、`eval` と同じ部品（`evidence_match`）を使う。上位 `limit` 件の結果が引用の範囲を覆えば回収とし（短い引用は全体、長い引用は `minCoverage`）、質問ごとの回収率の平均を `evidenceRecallAtK` として方式ごとに返す。見つからない引用は回収できなかったものとして数え、件数を返す。文脈の組み立てはこの API の検索にないので、`@context` の指標はない。
- `optimize` は、遅延の予算内の方式を `evidenceRecallAtK`、P95 の順で比べて選ぶ。保存したプランの評価は記録として持つだけにし、以前の版で保存した文書単位のレポートのプランも開ける。
- 評価データの保存、レポート、試行は、Dunlinfile のプロジェクト（CLI）だけにある。直接開いた索引の評価は、比べた結果を返すだけで保存しない。

#### 評価データの管理（4e）

- 4e は2回に分ける。先に `generate` 以外（`list`、`tag`、`show`、`diff`、`use`、`export`、`split`、`review`、`sync`、`add`、`import`）を移し、次に生成モデルを使う `generate` を移す。
- `eval-data` のコマンドは Node.js API の `Dunlin.evalData` を呼ぶ。文書を読むコマンド（`add`、`import`、`sync`、確認済みにする `review`）は、提供中のビルドを開いて `evalData` を呼ぶ。`review` は引数を確かめてから文書を読むので、`BUILD_NEEDED` を返したときにビルドを開いて呼び直す。
- ケースの検査と保存の形（引用の位置対応、文書の解決、グループと分割、ケースIDと評価データIDの計算、キーの順）は以前と同じである。グループの既定値に使う文書名の並べ替えは、JavaScript と同じく UTF-16 の順にした。
- 取り込むファイルの読み込み、書き出し、評価データを選んだときの設定ファイルの書き換えは JavaScript に残す。Rust は選ぶ評価データを `select` で返す。
- 旧実装を写した基準（テストの `eval-data-reference.mjs`）と、写した2つのプロジェクトで同じコマンドを実行し、出力、エラー、選ばれた評価データ、保存した評価データとタグが一致することを確かめた。時刻と、写したプロジェクトごとに違う文書の版は、出てきた順の記号に置き換えて比べる。
- `generate` も Rust で行う。JavaScript は使う対話用モデル（`--model`、または対話用モデルが1つだけならそれ）を選び、接続先と API キーを解決して渡す。モデルが選べないこと、件数、`--doc`、解決できない設定の誤りは、以前と同じ順に Rust が返す。
- 抜粋は以前と同じく UTF-16 の単位で切り出す（4000 単位、後半に改行があればそこで切る）。ケースのない文書を先に読み、長い文書は次の周回で続きを読む。1回の要求は 16000 単位までにまとめる。サロゲートペアの途中で切れた抜粋は、JavaScript と同じエスケープ（`\ud83d` など）で送る。
- モデルへの要求の本文（指示、抜粋の JSON、zod から作った JSON Schema）は、以前とバイト単位で同じである。候補の検査（形の誤り、抜粋にない引用、重複、一意に定まらない引用）と、理由ごとの件数、エラーの番号も変わらない。
- モデルの出力に対になっていないサロゲートのエスケープがあると、Rust はそれを U+FFFD に置き換えてから読む。その引用は抜粋と一致しなくなり、その候補だけが「抜粋にない引用」として除かれる。JavaScript の `JSON.parse` はそのまま受け取っていた。
- 旧実装を写した基準（`eval-data-reference.mjs` の生成）と、テスト用のモデルで比べ、要求の本文が一致すること、出力、エラー、保存した評価データが一致することを確かめた。複数の要求、JSON でない出力、抜粋の境界で切れた絵文字、`--doc` の指定、2回目の生成を含む。

#### 段階4の終わり

- 評価、根拠の位置対応、対応表、レポートと比較、評価の状態、辞書の提案に渡す取りこぼし、試行と採用の記録、評価データの管理と生成を Rust で行うようになった。Node.js API の `evaluate` と `optimize` も同じ部品で根拠単位に採点する。
- JavaScript に残るのは、設定の検証と組み合わせ、モデルの解決、設定ファイル（YAML）の書き換え、ファイルの読み書き、辞書の提案の組み立て（Lindera の解析）、表示である。設定ファイルと表示は段階6で移す。

### 28.12 段階5の進め方

段階5では、Wiki/PARA の取り込み、執筆と引用の検証の進行、検査、ページの HTML 化、画面の配信を Rust のエンジンに移し、Node.js API の `wiki.rs` とまとめる。次の小段階に分ける。各小段階の終わりで、旧実装と同じプロジェクトと指示に対して、モデルへの要求の本文、出力、エラー、`state.sqlite` に保存するページ・資料・作業・指摘、公開する HTML ファイル、画面の応答が変わらないことを差分テストで確かめる。

| 小段階 | 内容 |
| --- | --- |
| 5a | Markdown の HTML 化と、Wiki/PARA のコマンド（`ingress`、`query`、`verify`、`archive`、`undo`、`issue`、`cite`、`rules`、`instruct`、`save-answer`、`progress`）を Rust に移す。執筆と内容の検査のモデル呼び出し、引用の検証、ページの公開、作業の記録が含まれる |
| 5b | 画面（Wiki/PARA の `serve`）を Rust に移す。段階3cの HTTP の部品を使い、画面からの指示は作業として順に実行する |
| 5c | Node.js API の `wiki.*` を CLI と同じエンジンにまとめる（28.5節） |

#### 5a から 5c の間に変えないもの

- `state.sqlite` の Wiki の表（`wiki_pages`、`wiki_sources`、`wiki_jobs`、`wiki_issues`、`wiki_work`、`wiki_reviewed_material`、`wiki_content_pairs`）と、保存する JSON の形とキーの順。
- 公開する HTML ファイル（本文、出典の一覧、末尾に埋め込むページの記録）と、原本へのリンク。
- モデルへの要求の本文（指示、入力の JSON、zod から作った JSON Schema）と、応答の検査。エラーの番号、文言、終了コード。
- 画面の HTML、状態コード、ヘッダー、フォームの値、指示を受け付ける規則と断る規則。

#### コマンド（5a）

- Wiki/PARA のコマンドは Node.js API の `Dunlin.wiki` を呼ぶ。JavaScript は、設定の検証（`validateWiki`。段階6で移す）、参照される対話用モデルの設定の解決（設定か、使えない理由）、OCR の実行環境の解決、HTML と Office のパースを受け持つ。
- 作業の記録（`wiki_work` の順番待ち、実行中の段階と件数、結果やエラー）と実行の排他（`execution.lock`）も Rust で行う。作業の行は排他を取る前に記録するので、排他が取れないときも失敗した作業として残る。進行状況の行は Rust が標準エラーに書く。
- 取り込みは、パスの解決とフォルダの走査、資料ごとの ID、パーサの振り分け、読み込み（段階2の `source_load`）、キーワード索引（`wiki-keyword`）への登録を Rust で行う。チャンクの設定（800 文字、重なり 100、NFKC）も以前と同じである。
- Markdown の HTML 化は、`pulldown-cmark` の出来事を markdown-it 15（`html: false`）と同じ形で書き出す。改行の位置、`<hr>` と `<br>`、表、リンクの検査（`javascript:` などを断る）、URL の符号化（punycode を含む）、生の HTML を文字として書くことを合わせた。104 通りの Markdown で markdown-it と同じ HTML になることを確かめた。HTML のブロックとして読める行は、markdown-it と違って段落の中の Markdown を解釈せず、文字のまま段落にする。`~~~a~~~` のように `~` が3つ並ぶ書き方は、markdown-it と違って取り消し線にしない。
- 質問の順位づけと内容の検査に使う単語の区切りは、ICU4X の辞書（`icu_segmenter`）で求める。Node.js の `Intl.Segmenter`（ICU4C）とは辞書の版が違うため、まれに区切りが変わる（「か月」をひとまとまりにするなど）。区切りが変わると、質問の順位と、内容の検査で比べる相手が変わり得る。
- 内容の検査で関連度が同じ相手の順は、`localeCompare` に代えて ICU4X の root の照合順序で決める。Node.js は実行環境の既定のロケールを使うので、日本語の ID が並ぶ場合に順が変わり得る。画面の「最近更新したページ」の順も同じ照合順序で決める。
- ファイルの読み書きの誤りは、Node.js と同じ番号と文言（`ENOENT: no such file or directory, open '...'` など）で返す。
- 旧実装を写した基準（テストの `wiki-reference`）と、写した2つのプロジェクト（Wiki と PARA）で同じコマンドを実行し、モデルへの要求の本文、出力、エラー、7つの表、公開した HTML ファイル、`rules.md` が一致することを確かめた。対応できない形式の資料、ページ数の上限、JSON でない応答、検証できない引用、補足の記録、規則の追記と取り消し、資料の更新による改訂、内容の検査の3種類の指摘、PARA のアーカイブと取り消しを含む。サロゲートペアの途中で切れる抜粋（ページの 1200 単位、資料の 4500 単位）も、以前と同じエスケープで送る。時刻、資料を読んだ時刻、プロセス番号、SHA-256 は、出てきた順の記号に置き換えて比べる。

#### 画面（5b）

- `serve` は Node.js API の `Dunlin.wikiServe` を呼ぶ。HTTP は段階3cの hyper と tokio の部品（接続先と送信元の確認、合言葉、同時接続と大きさの上限、時間切れ）を使い、画面に要る規則（自分の Origin を許す、Basic 認証、`Access-Control-Allow-Credentials`）を加えた。
- フォーム（URL エンコードと multipart）の解釈、アップロードの名前の検査と保存、指示から作業への変換、ページの HTML は旧実装と同じにした。指示は作業として記録し、1つずつ順に実行する。止めるときは、受け付けた作業を終えてから戻る。
- アップロードの名前は、旧実装と同じく実行環境の `path.basename` の規則で取り出す。Windows では `a:b.txt` のドライブ名を落として `b.txt` にする。
- 応答に `Connection: keep-alive` を付けない。HTTP/1.1 の既定と同じなので、接続の扱いは変わらない。
- 旧実装の画面（テストの `wiki-reference` の `serveWiki`）と並べて起動し、トップ、ページ、運用の決まり、作業の状態、接続先・送信元・合言葉・パス・大きさの誤り、CORS の事前確認、フォームの誤り、アップロードの名前、11種類の指示とその結果のページに、同じ状態コード、ヘッダー、本文で答えることを確かめた。
- 旧実装の HTTP の部品（`listenHttp`）、`project-wiki-work.mjs`、`project-wiki-inspection.mjs`、`authoring/html.mjs`、`authoring/uploads.mjs` を外した。`markdown-it` はテストの基準だけが使う開発用の依存にした。

#### Node.js API の Wiki（5c）

- Node.js API の `wiki.*` は、直接開いた索引の 2〜32 件の資料から抜粋でページを作り、同期のときに作り直し、MCP の `knowledge.wiki_get` で読むものだった。これは仕様（13〜16章）の Wiki と違うので、28.5節に従って仕様に合う CLI のエンジンを残し、`wiki.*`、`syncSource` と `syncDocuments` の結果の `wiki`、`knowledge.wiki_get`、エラーの番号 `WIKI_NOT_FOUND` と `WIKI_ERROR`、索引の `.dunlin-wiki-v1` への保存をなくした。npm での公開前なので、非推奨の期間は置かない。
- Node.js からは、CLI と同じエンジンを `Dunlin.wiki`（コマンド）と `Dunlin.wikiServe`（画面）で呼べる。以前の索引に残る `.dunlin-wiki-v1` は読まない。

#### 段階5の終わり

- Wiki/PARA の取り込み、執筆と引用の検証、検査、ページの HTML 化、作業の記録、画面を Rust で行うようになった。Node.js API の Wiki も同じエンジンになった。
- JavaScript に残るのは、設定の検証、モデルと OCR の実行環境の解決、HTML と Office のパース、表示である。設定の検証と表示は段階6で移す。
- 単語の区切り、照合順序、文字の種類に ICU4X のデータ（`icu_segmenter`、`icu_collator`、`icu_properties`）と `idna` を加えたので、配布物は約 5.1 MB（5.2%）大きくなった。大半は日本語・中国語と東南アジアの言語の単語の辞書である。
- JavaScript の `loadCorpus` と `chunkCorpus`（`project-content.mjs`）は、製品のコードからは使わなくなった。比べるテストが使うので残し、段階6で外す。

### 28.13 段階6の進め方

段階6では、残った JavaScript のライブラリを外し、コマンドの解釈と表示を Rust に移して、npm の入口を起動役だけにする。次の小段階に分ける。各小段階の終わりで、旧実装と同じ入力とコマンドに対して、抽出した本文、書き出す設定ファイル、出力、エラー、終了コードが変わらないことを差分テストで確かめる。

| 小段階 | 内容 |
| --- | --- |
| 6a | HTML の本文の取り出し（`cheerio`）と Office 文書の変換（npm の `docling.rs`）を Rust に移す |
| 6b | 設定ファイルの書き出し（`yaml` の `stringify`）と、モデルの設定と環境変数の参照の解決を Rust に移す |
| 6c | コマンドの解釈、プロジェクトの読み込みと検査（Wiki/PARA の設定の検査を含む）、各コマンドの実行、表示、初期化、利用者設定、ツールと OCR の準備を Rust に移し、入口を起動役だけにする |

#### パーサ（6a）

- HTML は `scraper`（html5ever）で読む。取り除く要素（`script`、`style`、`noscript`、`template`、`nav`、`footer`、`aside`、`hidden` 属性を持つ要素）、本文とする範囲（`main` か `role="main"`、なければ `article`、なければ `body`）、前後に改行を入れる要素、見出しの `#` を、cheerio を使った実装と同じにした。文書の版の識別子が変わらないよう、抽出結果のパーサ名は `cheerio` のまま記録する。
- Office 文書（`.docx`、`.xlsx`、`.pptx`）は、docling.rs の crate（`docling` と `docling-core`、npm と同じ 2.67.1）を直接使う。npm の docling.rs は同じ Rust のコードを包んだものなので、変換結果は変わらない。npm の約 58 MB のバイナリが要らなくなる代わりに、ネイティブ部分は約 13 MB 大きくなった。
- 10 通りの HTML、UTF-8 として読めない HTML、3 種類の Office 文書と壊れた `.docx` で、旧実装と同じ本文とエラーになることを確かめた（テストの `parser-parity`）。

#### YAML とモデルの設定（6b）

- 設定ファイルの書き出しは、yaml 2.9 の `stringify` を既定の設定のまま Rust に写した（`yaml_emit`）。引用符の選び方、ブロック文字列、80 桁での折り返し（UTF-16 の単位で数える）、字下げを合わせた。決まった値と、生成した 5000 通りの値で同じ YAML になることを確かめた（テストの `yaml-parity`）。読み込みは段階1の `yaml_config` を使う。
- `${NAME}` の参照、`api_key_env`、生成と埋め込みのモデルの接続先の解決も Rust で行う。エラーの番号と文言は以前と同じである。
- `dictionary add` は、候補の設定ファイルの `user_dictionary` の行だけを書き換える。旧実装は yaml の文書を書き直していたので、手で書いた書式（フロー形式やコメントの位置）が整えられることがあったが、Rust は他の行をそのまま残す。キーが1行の形で見つからないときだけ、ファイル全体を書き直す。

#### コマンド（6c）

- npm の入口（`tools/rag/cli.mjs`）は、Node.js API の `Dunlin.runCli` を呼ぶだけにした。引数を Rust に渡して終了コードを返し、サーバーが動いている間だけ SIGINT と SIGTERM でサーバーを止める。`dunlin:index-open` の通知も入口から出す。使用法の一覧は `Dunlin.cliCommands()` で読める。
- 引数の解釈は Node.js の `util.parseArgs`（strict）と同じ規則とエラーの文言にした。出力（JSON の結果と文字の表示）、エラーの番号と終了コード、診断と警告の表示も以前と同じである。以前と同じく、メッセージを持たない警告（設定の検査の警告）は、文字の表示で `undefined` と出る。
- Wiki/PARA の設定の検査（以前の zod のスキーマ）、プロジェクトの読み込み、候補の設定と試行の上限、`init` の雛形とコメント、利用者設定（`~/.dunlin/config.yaml`）、ツールの追加と削除（hannoy の検査と導入、oar-ocr と lightonocr の取得、GPU の判定）も Rust で行う。取得は ureq で行い、Node.js の fetch と同じく転送先に従い、プロキシの環境変数は使わない。通信に失敗したときの文言は変わる。
- 以前は `node:sqlite` で行っていた `state.sqlite` の操作（表の作成、ビルドとタグの読み出し、状態の集計）も Rust で行う。使用中のときの待ち時間（500 ミリ秒）と `DB_BUSY` は以前と同じである。
- 旧実装の CLI を写した基準（テストの `cli-reference`）と Rust の CLI で、同じフォルダで順に 115 のコマンドを実行し、標準出力、標準エラー、終了コードと、書き出す 10 のファイルが一致することを確かめた（テストの `cli-parity`）。初期化と利用者設定、検査と診断、構築と候補での試行、検索、タグと採用、評価データ、評価とレポート、根拠の対応表、辞書、`serve --print-config`、Wiki/PARA のコマンド、引数とプロジェクトの誤りを含む。実行 ID、時刻、所要時間、時刻を含む評価データ・レポート・対応表の ID、索引の大きさは置き換えて比べる。構築、検索、評価、試行、辞書、Wiki、`serve` の既存のテストも、Rust の CLI でそのまま通る。
- その後、利用者が試した結果から、`--json` を付けないときの表示を人が読む短い文に変えた（`status`、`build`、`search`、`eval`、`report` など）。ヘルプにはコマンドの説明を加え、`--version` と、打ち間違えたコマンド・オプション・動作の候補を示すようにした。`serve --print-config` は `mcpServers` の項目を表示する。`--json` の結果は変えていない。`cli-parity` は、表示を変えた 31 のコマンドで終了コードともう一方の出力を比べ、新しい表示は Rust の側で確かめる。

#### 段階6の終わり

- JavaScript に残るのは、npm の入口（約 40 行）と、Node.js API の型と呼び出し口だけになった。`cheerio`、`markdown-it`、`yaml`、`zod`、npm の `docling.rs` は製品の依存から外し、比べるテストの基準にだけ開発用の依存として残した。
- 使われていなかった JavaScript のベクトル検索（`rag.mjs`、`vectors.mjs`、`vector-stores.mjs`、`vector-servers.mjs`、`vector-sqlite.mjs`）と、その保存先の `sqlite-vec` を外した。ベクトル索引は Rust の総当たり検索と hannoy が受け持つ。
- JavaScript の `loadCorpus` と `chunkCorpus`（`project-content.mjs`）も、他の CLI のモジュールとともに外した。比べるテストは、写した基準（`cli-reference`）を使う。
- 28.8節の「入口」は、JavaScript の起動役を残すことにした。ネイティブ部分は Node.js の拡張として読み込むので、Rust の実行ファイルを別に配ると、Node.js API と CLI のために同じネイティブ部分を2つ配ることになるためである。
- ネイティブ部分は、段階5の終わりから約 14 MB 大きくなった（Windows x64 で 107.5 MB から 121.5 MB）。大半は Office 文書の変換で、CLI の移行による増加は約 1 MB である。npm の docling.rs（約 58 MB）が要らなくなったので、導入する全体の大きさは小さくなった。

### 28.14 未決事項の測定

段階6の後、28.8節の論点を測った。構築の段ごとの時間は `benches/cli-build.mjs`、保存先ごとの大きさは `benches/storage.mjs`、検索と上位10件の根拠の読み出しの時間は `benches/read.mjs` で測る。数値は Windows 11 x64 で測ったものである。

#### テキスト文書の原本

- 原本ファイルの作成をやめると、Markdown 10,000 件の構築は 6.6 秒から 3.7 秒に（`source` 段は 4.4 秒から 1.6 秒に）、1,000 件では 0.79 秒から 0.47 秒になった。
- 構築の `source` 段は、テキスト、Markdown、コードの文書（UTF-8 として読んだバイト列をそのまま本文にする文書）の原本ファイルを作らない。原本の SHA-256 はこれまでどおりコーパスの版に記録するので、段階とビルドの識別子は変わらない。原本は版の本文から復元でき、そのバイト列の SHA-256 は記録と一致する。
- HTML、Office、PDF、画像、外部コマンドで読む文書は、本文が原本と異なるので、これまでどおり原本ファイルを作る。
- Wiki/PARA の取り込みは、テキスト文書の原本ファイルも作る。公開するページの引用が原本ファイルにリンクするためである。
- 構築の原本ファイルを読む処理はない（`status` が大きさを数えるだけ）。読む口を足すときは、ファイルがなければコーパスの版から復元する。既存のプロジェクトにある原本ファイルは消さない。

#### 索引に本文を持つか

- 根拠の読み出し（`read`、文脈の組み立て、再ランク付けの入力）で、本文を Tantivy の保存領域の代わりにコーパスの版から読むと、上位10件の読み出しは、大きな文書（`docs/` の17件）で 1.5 ミリ秒から 5〜6 ミリ秒に、小さな文書 10,000 件で 0.3 ミリ秒から 0.8 ミリ秒になった。コーパスの版は、位置の一覧を含む記録全体を JSON として読むためである。
- 索引に保存した本文と根拠は、`docs/` の17件で圧縮後 187 KB（索引全体の 52%）だった。
- 当面は索引に本文を持つ。コーパスから本文だけを速く読めるようになれば、改めて決める。

#### チャンクの `searchText`

- `docs/` の17件（331 KB）で、チャンク集合 417 KB のうち `searchText` が 387 KB（93%）を占めた。チャンクの重なりを含む範囲の NFKC の文字列を保存するためである。
- `chunk_sets` 表には、`searchText` がチャンクの `byteRange` の本文の NFKC と一致するとき、文字列の代わりに `true` を保存する。一致しないチャンク（`chunk.semantic` で文ごとに NFKC にした文字列をつないだものが、まとめて NFKC にしたものと異なる場合）は文字列のまま保存する。
- 読むとき（`transform` 段のチャンクのキャッシュと、`index` 段で記録を展開するとき）に、文書の本文から NFKC で作り直す。チャンク集合の識別子は、これまでどおり作り直した文字列を含む JSON の SHA-256 なので、段階とビルドの識別子は変わらない。以前の版と新しい版で同じ文書を構築し、`source`、`transform`、`index` の識別子と検索結果が一致することを確かめた。
- 以前の版が保存した文字列はそのまま読む。書き換えはしない。
- `docs/` の17件で、チャンク集合は 417 KB から 36 KB になった。10,000 件の構築時間は変わらなかった（3.7 秒）。

#### `state.sqlite` と `corpus.sqlite`

2つのファイルは分けたままにする。

- コーパスはエンジンの一部である。各ビルドの索引（`KnowledgeBase`）は共有のコーパスを開き、Node.js API の `Dunlin.open` は、`state.sqlite` を持たない索引ディレクトリに自分のコーパス（`.dunlin-corpus-v1`）を作る。まとめると、エンジンがプロジェクトの記録の形を知る必要があり、単独の索引には別の形が残る。
- SQLite は1つのファイルに同時に1つしか書き込めない。`source` 段はコーパスに最大 64 MB ずつ本文を書き、`transform` 段はチャンク集合を書く。`state.sqlite` は段階の記録、タグ、採用、評価、Wiki の状態を短い処理で書き、CLI は 500 ミリ秒待って使用中なら `DB_BUSY` を返す。まとめると、構築の大きな書き込みが状態の短い更新を待たせる。
- 大きさと扱いが違う。コーパスは資料の本文を持ち、資料とともに大きくなる。`state.sqlite` は記録と埋め込みのキャッシュ（`embeddings` 表）を持つ。キーワード検索だけなら小さい（`docs/` の17件で、`state.sqlite` が 184 KB、コーパスが 436 KB）。分けておくと、`status` で別々に大きさを示せ（受け入れ条件 A3）、別々に詰めたり退避したりできる。
- ファイルをまたぐ整合は、書く順序で保っている。本文の版とチャンク集合をコーパスに書いてから、それを指す抽出の対応と段階の記録を `state.sqlite` に書く。途中で止まっても、どこからも指されない版やチャンク集合が残るだけで、記録が存在しない版を指すことはない。2つのファイルを1つの処理で更新する必要が出たら、`ATTACH` で開く。
- 既存のプロジェクトを移すには、コーパスの全体を写す必要がある。上の理由から、その手間に見合う利点がない。
- コーパスは WAL ではなく、既定の削除ジャーナルで動く（`state.sqlite` は WAL）。削除ジャーナルでは、書き込みを確定する間、検索のための読み出しが待たされる。
- `benches/serve-during-build.mjs` で影響を測った。2,000 件（各 16,000 文字）を構築して `serve` で HTTP の検索を順に送り続け、3,000 件を足して構築した（構築は約 14.5 秒）。構築中の検索は、p50 が 16.5 ミリ秒で変わらず、失敗もなかった。p99 は 50〜52 ミリ秒、最大は 61〜73 ミリ秒だった。試しにコーパスを WAL にすると、p99 は 25 ミリ秒、最大は 37〜41 ミリ秒になった。WAL では `source` 段が約 0.4 秒遅く、`transform` 段が約 0.4 秒速く、構築全体の時間は変わらなかった。
- 待ちは構築中の検索の末尾の数十ミリ秒にとどまるので、いまはジャーナルを変えない。
