# PDF の文字層の抽出：pdf_oxide と pdfjs の比較

仕様 28.9 節の段階 2a で、PDF の文字層の抽出を pdfjs（JavaScript）から `pdf_oxide`（Rust）に切り替えた。標準は `pdf_oxide` とする。この文書は、切り替え前後の抽出結果の比較を記録する。比較の結果は、標準を決める条件にはしていない。

## 切り替えで変わること

- PDF は Rust のワーカーで読み、JavaScript を呼ばない。各ページの本文を `extract_text` で取り出し、前後の空白を除いて空でないページを空行で区切ってつなぐ。位置はページごとに `{ page, range: { startLine, endLine } }` を付ける。この形は pdfjs のときと同じである。
- 抽出結果の `parser` は `{ tool: "pdf_oxide", version: "0.3.78" }` になる。
- 抽出結果のキャッシュのキーに `pdf_oxide@0.3.78` を加えた。切り替え後の最初の構築では PDF だけを読み直し、それ以外の形式はキャッシュをそのまま使う。`pdf_oxide` の版は `Cargo.toml` で固定している。版を上げると PDF を読み直す。
- 本文が変わるので、PDF を含むプロジェクトでは `source` 段とそれ以降の識別子が変わる。
- OCR の対象として振り分けた PDF（`loader.ocr`、または `loader.auto` で `ocr: loader.ocr`）は、これまでどおり OCR で読む。

## 再現する

```sh
npm run build
python benches/pdf-compare/make-samples.py <出力先>
node benches/pdf-compare/compare.mjs <出力先> --runs 5 --show
```

`make-samples.py` は reportlab と Windows の日本語フォント（MS ゴシック）で比較用の PDF を作る。`compare.mjs` は、指定したフォルダの PDF を両方の方法で読み、本文の一致、空白を除いた一致、類似度（空白を除いた文字列の編集距離から求める）、文字のあるページの一致、処理時間の中央値を表にする。`--show` を付けると、差のある PDF の本文を両方とも出力する。手元の PDF のフォルダを渡せば、同じ表を作れる。

## 試料

| PDF | 内容 |
| --- | --- |
| `horizontal-embedded.pdf` | 横書きの本文 2 ページ。TrueType のサブセットを埋め込んだフォント |
| `horizontal-cid.pdf` | 同じ本文を、埋め込まない標準の日本語フォント（HeiseiMin-W3、UniJIS-UCS2-H）で書いたもの |
| `vertical-cid.pdf` | 縦書き 4 列（UniJIS-UCS2-V）。右の列から読む |
| `table.pdf` | 罫線で囲んだ 4 行 4 列の表 |
| `two-columns.pdf` | 見出しと 2 段組みの本文 |
| `blank-page.pdf` | 3 ページのうち 2 ページ目に文字がない |
| `long-100-pages.pdf` | 横書き 100 ページ、各 30 行 |

いずれも合成した試料である。実際の資料（スキャンを含む業務文書、組版ソフトで作った縦書き、複雑な表）での比較は、資料が手に入りしだいこの文書に追記する。

## 結果

Windows 11 x64、Node.js 22.17.1、リリースビルド。処理時間は 5 回の中央値（ミリ秒）。`pdf_oxide` の時間は `Dunlin.loadCorpus` を通した 1 ファイルの処理時間で、ファイルの読み込み、ハッシュ、キャッシュへの書き込みを含む。

| PDF | 本文が一致 | 空白を除いて一致 | 類似度 | ページが一致 | pdfjs | pdf_oxide |
| --- | --- | --- | --- | --- | --- | --- |
| blank-page.pdf | はい | はい | 1.000 | はい | 5.5 | 2.9 |
| horizontal-cid.pdf | いいえ | いいえ | 0.000 | いいえ（なし / 1,2） | 2.3 | 3.1 |
| horizontal-embedded.pdf | いいえ | はい | 1.000 | はい | 4.6 | 3.5 |
| long-100-pages.pdf | いいえ | はい | 1.000 | はい | 95.8 | 47.4 |
| table.pdf | いいえ | はい | 1.000 | はい | 1.8 | 3.3 |
| two-columns.pdf | いいえ | はい | 1.000 | はい | 2.1 | 3.3 |
| vertical-cid.pdf | いいえ | いいえ | 0.000 | いいえ（なし / 1） | 0.9 | 2.6 |

7 件中 6 件で本文が異なる。そのうち 4 件は空白と改行だけの違いで、文字の並びは同じである。

## 差の内容

### 埋め込まない日本語フォント

pdfjs は `horizontal-cid.pdf` と `vertical-cid.pdf` から文字を 1 つも取り出せなかった。Dunlin は pdfjs に CMap のファイルを渡していないので、埋め込まない日本語フォントの文字コードを Unicode に変換できない。`pdf_oxide` は標準の CMap を持っており、どちらの本文も取り出せた。古い業務文書には埋め込まない日本語フォントの PDF があるため、これは切り替えで読めるようになる文書である。

### 改行と空白

- `pdf_oxide` は、行の間隔が広い行の間に空行を入れた。試料の行送りは文字の大きさの 1.8 倍前後で、通常の文書より広い。空行が増えると、ページの範囲を表す行番号と、見出しや段落で区切るチャンク化の結果が変わる。
- 全角の空白（「第1章　設備の概要」）を、pdfjs は半角の空白 3 つにしたが、`pdf_oxide` は全角の空白のまま残した。
- 2 段組みでは、どちらも左の段を読んでから右の段を読んだ。pdfjs は見出しと左の段の 1 行目を 1 行につないだが、`pdf_oxide` は見出しを別の段落にした。

### 表

pdfjs はセルの間に空白を 3 つ入れた。`pdf_oxide` はセルの間に空白を 1 つ入れたが、最後の列では空白を入れず、「6か月2」「2年1」のように前のセルとつないだ。数量の列が前の列の値と区別できなくなるので、表の多い資料では注意が要る。`pdf_oxide` の `to_plain_text` は列をそろえて空白を入れるが、2 段組みでは左右の段の行を交互につなぐので採らなかった。

### 縦書き

`pdf_oxide` は縦書きの列を 1 列ずつ正しく読んだが、列の順を左から右とし、右の列から読む順と逆になった。reportlab で作った試料の縦書きが、実際の組版ソフトの出力と同じ形かは確かめていない。実際の縦書きの資料で確かめる。

### 処理時間

数ページの PDF では、どちらも数ミリ秒で終わった。`pdf_oxide` の時間には 1 ファイルあたり 2〜3 ミリ秒のキャッシュとハッシュの処理が入っている。100 ページの PDF では `pdf_oxide` が pdfjs の約半分の時間だった。

## OCR（oar-ocr）の確認

`oar-ocr` を標準の OCR とした（仕様 4.1 節）。PP-OCRv6 small の検出と認識のモデルを、ONNX Runtime 1.28.3 で CPU で動かす。`dunlin add oar-ocr` が ONNX Runtime とモデルを SHA-256 を確かめて取得し、Rust が実行時に読み込む。

日本語の画像 1 枚（PNG）と、文字層のない画像だけの PDF 1 ページで、`dunlin build` を試した。

- 日本語の行は、どちらも原文どおりに読めた。行ごとにページと位置（0〜1000 の座標）が付いた。
- 英数字の行「Model PX-200 / 2026年11月」は「ModelPX-200／2026年11月」になった。空白が落ち、半角の斜線が全角になった。
- `source` 段の時間は、モデルの読み込みを含めて 0.77 秒だった（32 論理コアの Windows 11 x64）。同じ入力で作り直すと、同じ段階 ID になった。

試料は Windows のフォントで描いた合成の画像である。実際のスキャン文書（傾き、かすれ、縦書き、表）での精度は、資料が手に入りしだい追記する。`lightonocr` は GPU と管理された Python の実行環境が必要で、この環境では試していない。
